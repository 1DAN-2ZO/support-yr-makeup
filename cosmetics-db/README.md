# 화장품 DB

사진에서 읽은 색과 **가장 가까운 화장품**을 찾아 주려고 모아 둔 데이터다.
앱 화면의 "○○ 계열 — 롬앤 쥬시 래스팅 틴트" 가 여기서 나온다.

```
브랜드 21 · 제품 77 · 호수 370 · 계열 57     (2026-10-15)
```

## 바로 열어 보려면

`nudy.db` 를 SQLite 뷰어로 열면 된다 (DB Browser for SQLite 등). 파이썬을 안 돌려도 된다.

```bash
sqlite3 nudy.db "SELECT b.name, p.name, s.code, s.name, s.hex, s.family
                 FROM shade s JOIN product p ON p.id=s.product_id
                 JOIN brand b ON b.id=p.brand_id WHERE s.part='lip';"
```

**`nudy.db` 는 `build.py` 가 만든 것이다.** 고칠 일이 있으면 이 파일을 손대지 말고
`seed/` 에 적고 다시 만들어라 (아래 "왜 디비를 손으로 안 고치나").

## 다시 만들기 — 두 줄

```bash
python3 build.py     # seed/*.sql → nudy.db 를 처음부터 다시 만든다
python3 export.py    # nudy.db → out/ 에 앱이 읽을 파일을 뽑는다
```

파이썬 3 과 sqlite3 만 있으면 된다. 따로 설치할 것 없다.

뽑은 `out/product-picks.data.ts` 를 **`client/src/core/product-picks.data.ts` 로 복사**하면
앱에 반영된다 (리액트판이 `@core` 별칭으로 그 폴더를 읽는다).

## ⚠️ 색 이름 규칙을 고치면 여기도 다시 뽑아야 한다

앱은 제품을 **색상값이 아니라 계열 이름**으로 찾는다 — `client/src/core/color-name.ts` 의
`describeColor` 가 지어낸 이름이다 (`product-picks.ts` 머리글 참고).

그래서 **디비의 계열 이름도 그 함수를 그대로 돌려서 붙인다** (`seed/ZZ1-family-from-app-name.sql`).
사람이 금을 긋지 않으므로 어긋날 수가 없다.

**`color-name.ts` 를 고치면 이 디비의 계열이 옛 이름으로 남는다.** 그러면 그 제품들이
조용히 추천에서 빠진다 — 오류도 경고도 안 난다. 실제로 그 일이 있었다:
한때 **199개 중 46개(23%)만** 앱 이름과 맞았고, 나머지 153개는 붙여도 영영 안 나왔다.

고쳤으면 반드시:

```bash
# 1. 호수마다 앱이 짓는 이름을 다시 뽑아 seed/ZZ1-… 을 새로 만든다
# 2. python3 build.py && python3 export.py
# 3. out/product-picks.data.ts 를 client/src/core/ 로 복사
```

(1 번 스크립트는 아직 손으로 돌린다 — 자동화는 다음 사람 몫이다.)

## 파일 짜임

| | |
|---|---|
| `schema.sql` | 표 넷 — `brand` · `product` · `family` · `shade` |
| `seed/*.sql` | **데이터 본체.** 파일 **이름 차례대로** 들어간다 |
| `build.py` | seed → `nudy.db`. 매번 **처음부터** 다시 만든다 |
| `export.py` | `nudy.db` → `out/products.json` · `out/product-picks.data.ts` |
| `tools/` | 계열을 데이터로 나눠 볼 때 쓴 것 |
| `review-needed.md` · `색이름-규칙-문제.md` | 사람이 봐야 할 것들 |

### 왜 디비를 손으로 안 고치나

**모든 변경은 `seed/` 의 파일로 적고 `build.py` 가 다시 만든다.** 까닭 둘:

1. 손으로 고치면 **왜 그 값이 됐는지가 안 남는다.** seed 파일에는 주석으로 까닭이 같이 적힌다
2. SQLite 는 `PRAGMA foreign_keys` 를 **연결할 때마다** 켜야 한다. 손으로 `sqlite3` 를 열면
   그걸 잊어 오타가 그대로 들어온다 — 실제로 `로즈색` 이라는 없는 계열이 들어간 적 있다.
   `build.py` 는 그 검사를 켜고, **일부러 틀린 줄을 넣어 거부되는지까지 확인**한다

### seed 파일 차례가 중요하다

이름 차례대로 들어가므로 **가리키는 것이 먼저 있어야 한다** (호수 → 계열).
숫자가 영문보다 앞이라 `99-…` 는 `A1-…` 보다 **먼저** 들어간다 — 그래서 계열을 덮어쓰는
파일은 이름이 **`ZZ1`** 이다 (맨 뒤에 와야 앞에서 더한 호수까지 닿는다).

새 파일을 더할 때는 **쓰는 계열을 그 파일이 스스로 만들어 둬라**
(`INSERT OR IGNORE INTO family(part, name)`). 차례가 어떻든 안 깨진다.

## 색을 어디서 읽나 — 부위마다 다르다

| 부위 | 어디서 | 왜 |
|---|---|---|
| 입술 · 블러셔 | **발색 사진**(피부에 바른 것) | 얇게 얹혀 밑색이 비친다. 통 안 색과는 범위가 거의 안 겹친다 (블러셔: 통 안 60~75 vs 피부 위 74~86) |
| 아이라이너 · 눈썹 | **색상칩 · 라벨띠 · 종이 발색** | 불투명하게 덮어 피부색이 안 비친다. 반대로 발색 사진은 **어두운 색의 그림자를 들어 올려** 검정이 회갈색으로 읽힌다 |

반대로 적용하면 **조용히 틀린다.** 값마다 `hex_source`(어디서) · `hex_note`(어떻게) ·
`trust`(믿을 만한가)를 같이 적는 까닭이 이것이다.

`trust` 는 `ok`(155) · `doubt`(글리터 · 보정 사진 · 조명이 수상) · `dark`(사진이 어두움).
**못 믿을 값을 버리지 않고 표시해 둔다** — 버리면 왜 없는지 아무도 모른다.

## 남은 일

- **입술 · 눈썹 제품이 5개씩**으로 얇다. 「브릭」·「체리」·「플럼」은 제품이 하나씩이라 늘 같은 것이 나온다
- **블러셔 · 아이섀도우의 `doubt` 가 3분의 1** — 보정 심한 모델 사진, 굵은 펄 때문이다
- 투쿨 **「투톤 볼륨 라이너」** 는 한 호수에 색이 둘이라 지금 표 모양에 안 들어간다. 어떻게 넣을지 정해야 한다
- **ZZ1 을 다시 뽑는 일이 손으로 돌리는 스크립트**다. `build.py` 안으로 넣으면 좋다
