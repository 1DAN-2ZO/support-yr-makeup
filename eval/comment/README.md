# eval/comment — 화면 6 총평은 LLM 이어야 하나 (#287)

VLM 개인화 보류(#286) 뒤, 텍스트 LLM 을 **화면 6(리뷰)** 으로 옮기자는 제안의 확인 실험. 사진은 넘기지 않고 채점 결과만 글로 넘긴다.

화면 6 에는 **부위별 결과와 한 줄 평(`review.ts` `reviewLine`)이 늘 나온다** — 그건 비교 대상이 아니라 맥락이다.
정하는 것은 그 맨 위에 놓을 **한줄평** 하나: 결과를 묶어 "다음에 무엇을 먼저 고칠지" 한눈에 알려 주는 한 문장.

| | 만드는 법 |
|---|---|
| B 규칙 한줄평 | 가장 잘된 부위 하나 + 먼저 고칠 부위 하나 (좌우 차면 "양쪽 균형부터", 확인만이면 "한 번 더 확인") — 한 문장 |
| C LLM 한줄평 | 같은 채점 결과(상태 · 잘됨/보통/아쉬움 · 부위별 한 줄 · 좌우 차)를 글로 → `praise_part` · `fix_part` · `comment` (제약 디코딩), 관문을 지남 |

- B 를 넣는 이유 — 간단한 규칙으로 같은 효과가 나면 LLM 자리가 아니다 (개인화가 무너진 이유와 같다)
- **앱 코드를 그대로 쓴다** — 채점 타입(`PartResult` · `SessionSummary`) · 한 줄 평 · 문구표 · 합산. `comment.ts` 를 `core.mjs` 가 esbuild 로 묶는다
- B · C 는 **같은 길이 상한(60자)**, 한 문장
- C 가 관문에서 거절되면 앱은 B 를 보여 준다 → 그 세션은 B 대 B 라 평가지에서 빼고 개수만 적는다

처음(2026-10-02 오전)엔 A(부위별 한 줄 이어 붙이기) · B · C 를 두세 문장 "종합 코멘트" 로 비교하게 만들었다가, A 는 어차피 화면에 나오므로 비교 대상이 아니라는 지적으로 한줄평 B 대 C 로 바꿨다 (`PROMPT_VER` comment-v3).

## 관문 (comment.ts `gateC`)

| 거절 | 왜 넣었나 |
|---|---|
| 길이 · 숫자 (화면 6 은 숫자 없이) · 한줄평이 아님(문장 셋 이상) | 화면 규칙 |
| 문장이 잘림 | 길이 상한에 걸려 "…권" 으로 끝남 (Gemma) |
| 영어 섞임 | "눈 liner" (Qwen3-14B) |
| 칭찬 부위가 잘된 부위가 아님 · 고칠 부위가 결과에 없음 · 고칠 부위를 글에서 말하지 않음 | 결과와 다른 말 |
| 잘된 부위를 고치라고 함 (마디 단위) | 전부 잘된 세션에서 "적당해요" 부위를 "더 신경 쓰라" (Gemma). 한줄평은 칭찬과 할 일이 한 문장에 오므로 쉼표로 나눈 마디로 본다 |
| 건너뛴 부위를 칭찬함 · 반대 방향 (진한데 더 진하게 등) | 지어낸 말 |

관문이 못 잡는 것: 오타("셔도우", "하일라이트"), 어색한 말("발라해요", "연마해보세요"), 결과에 없는 방법("진한 톤으로 바꿔") — 사람 평가에서 본다.

## 실행

```bash
# LLM 한줄평 (모델 설정은 eval/vlm/models.json — gguf 만, mmproj 없음). 세션 30개 × 2번
uv run --extra vlm python eval/comment/generate.py --model text-gemma4_e4b --max-tokens 200
uv run --extra vlm python eval/comment/generate.py --model text-qwen3_14b --max-tokens 200

uv run --extra vlm python eval/comment/results.py                          # 자동 지표 (관문은 지금 코드로 다시 건다)
uv run --extra vlm python eval/comment/results.py --sheet text-gemma4_e4b   # 평가지 (사진 없음)
uv run --extra vlm python eval/comment/results.py --ratings oneline-rating-*.json
```

**평가지 C 는 Gemma** — 글이 자연스럽고 빠르며 지금 서버 모델과 같다. Qwen3-14B 는 관문 통과율은 비슷하지만 관문이 못 잡는 오타 · 어색한 말 · 지어낸 방법이 많았다.
Gemma 의 거절은 "전부 잘됨" 세션 5개 모두와 1개 — "적당해요" 를 부족하다는 뜻으로 읽는다. 앱에선 그 세션에 B 가 나간다.

## 사람 평가 · 통과 기준 (미리 정함)

- 평가지 `$DHE_DATA_DIR/comment-eval/평가지-배포/한줄평-평가.html` (24문항, 사진 없음) — 문항마다 부위별 결과(막대 + 한 줄 평) + 한줄평 두 개 + 비슷함. **평가자마다 문항 순서와 글 자리를 섞는다** (seed 를 브라우저에 저장, 결과 파일에 기록). 누가 어느 글인지는 `.key.json` 에만
- **평가자 3명 이상**
- **C 를 B 보다 고른 비율(비슷함 뺌)의 95% 신뢰구간(Wilson) 하한 > 50% 이면 LLM 을 넣는다.** 못 넘으면 B 를 넣고 LLM 은 MVP 에서 뺀다
- 같이 보는 것: 세션 종류별 고른 수, 자리 쏠림(보인 순서 1·2번), 평가지에서 뺀 세션 수(= 앱에서 LLM 이 B 로 대신되는 비율)

## 1차 사람 평가 (2026-10-02, 한줄평 B 대 C, comment-v3) → 2차로 다시

평가자 3명 × 24문항: **C 66 · B 6 · 비슷함 0 → C 91.7% (95% 83~96%)**. 기준은 넘었지만 **B 가 너무 약했다** — B 는 "다음엔 눈썹부터 다듬어 봐요" 로 할 일이 없었고 C 는 "눈썹 사이 빈 곳을 채워주세요" 처럼 할 일을 말했다. C 가 이긴 이유가 LLM 이라서인지 할 일을 말해서인지 가를 수 없어 2차를 만들었다.

## 2차 (comment-v7) — 총평 · 입력값 전부 · 제품으로 할 일 · B′ 대 C

- **총평**: 한줄평 대신 한두 문장 100자 (사용자 요청)
- **C 입력값 전부**: 부위별 점수 · 진단 코드 · 확인만 이유 · 좌우 지수/차 · 확인받은 횟수 · 합산 점수 · 대칭/조화 보정 · 화장 의도(looks.json rationale) · **이 화장 제품 목록**. 글에는 숫자를 쓰지 않는다
- **세부 멘토링**: "옆에서 봐 주는 선생님처럼 — 이 화장 제품으로 '○○로 ~하듯이'". 목록에 없는 도구(면봉 · 스펀지, 펜슬 없는 화장의 펜슬 …)는 관문에서 거절
- **B′ (모델 없음)**: B 와 같은 부위 + 진단 코드별 제품으로 할 일 + 둘째 항목. 예 "입술은 잘 됐어요, 다음엔 아이라이너부터, 펜슬 라이너로 양쪽 눈꼬리 높이를 번갈아 보며 맞춰 그려 보세요. 눈썹도 펜슬로 빈 곳을 짧게 그리듯이 메워 보면 좋아요."
- 관문: 부위를 제품·자리 이름으로 말해도 됨("젤 라이너로 눈꼬리를…"), 문장 넷 이상이면 거절

| | 관문 | p50 / p95 | 길이 |
|---|---|---|---|
| Gemma 4 E4B (v7) | 56/60 (93%) | 1.9 / 2.1초 | 79자 |
| B′ | — | — | 57자 |

입력값을 늘리자 "전부 잘됨" 세션에서도 잘된 부위를 고치라고 하지 않고 "쉐딩·하이라이트를 꼭 확인해 보세요" 로 바뀌었다. 관문이 못 잡는 것: 진단과 다른 할 일("윗입술 선이 밖으로" 인데 "경계를 블렌딩") — 사람 평가에서 본다.

평가지 `$DHE_DATA_DIR/comment-eval/평가지-배포/총평-평가.html` (28문항, `results.py --sheet text-gemma4_e4b --rule B2`). 결과 파일 `total-rating-*.json` → `results.py --ratings`. 통과 기준은 같다 (C 대 B′, 비슷함 뺌, 95% 하한 > 50%).

## 3차 — 부위별 한 줄 (partline.ts, partline-v1~v3)

가짜 세션에 채점 수치를 진단과 맞게 넣고(`fillMetrics`, 채점 임계 기준) 고칠 말이 있는 완료 부위 50줄을 비교했다.
R(규칙: 진단 + 수치 구간으로 "조금 · 꽤 · 절반쯤" + 이 화장 제품으로 할 일) 대 LLM(요약 사실 + 진단). Gemma 관문 76~88%, 통과한 줄도 4줄에 1줄꼴로 진단과 다른 말(좌우 · 방향 · 지어낸 문제).
화장 전문가 말투 검수(바르다 통일 · 립은 두드리지 않음 · 점막 · "얇게 그려 봐요" · 밖으로 나가면 "지금 살짝 닦아 수정하거나, 다음엔" · 섀도우 블렌딩 그라데이션)를 규칙 문구 · 프롬프트(`STYLE_GUIDE`) · 관문에 넣었다. 앱 문구 쪽은 #295.

## 4차 — LLM 에 채점 수치를 **전부** 넣으면 (rawline.ts, rawline-v1, 2026-10-05)

VLM → 텍스트 LLM 전환이 정해져(사진 없음) 부위별 한 줄을 다시 봤다. 부위마다 채점기가 잰 수치 전부 + 채점 기준(임계)을 넘기고, **완료 부위 전부**(잘된 부위 포함)에 한 줄을 받는다. 답에 `issues`(문제 코드)를 같이 받아 수치를 맞게 읽었는지 자동으로 센다.

| 모델 · 입력 | 문제 찾기 정밀도 / 재현율 | 문제 부위 관문 | 잘된 부위 관문 | 세션당 p50 |
|---|---|---|---|---|
| **Gemma 4 E4B · 수치 + 진단** | 100% / 100% (진단을 받아 씀) | **92/100** | **174/174** | 4.7초 |
| Gemma 4 E4B · 수치만 (진단 없음) | 62% / 56% | 74/100 | 170/174 | 4.5초 |
| Qwen3-14B · 수치 + 진단 | 90% / 100% | 74/100 | 164/174 | 11.5초 |
| Qwen3-14B · 수치만 | 28% / 79% | 68/100 | 150/174 | 12.3초 |
| Qwen3-14B 생각 모드 · 수치만 | 54% / 91% | 38/50 | 71/87 | 37.2초 |

(관문 = 자동 검사. 같은 입력 같은 답은 모두 100%)

- **수치만 주면 LLM 은 문제를 제대로 못 찾는다** — 정밀도 28~62%. 큰 모델 · 생각 모드도 마찬가지(생각 모드는 맞는 섀도우 방향을 "반대" 로 읽는 일이 많았다). → **문제 판정은 채점 코드가 하고, LLM 에는 진단을 같이 준다**
- **수치 + 진단을 같이 주면 Gemma 가 가장 낫다** — 요약 사실만 줄 때(3차)보다 관문 통과가 오르고(76~88% → 92%), 통과한 문제 부위 46줄 중 진단과 다른 말은 6줄(약 13%, 3차는 약 25%): 섀도우 전제를 거꾸로("속눈썹 쪽이 더 진하게 발려야 하는데" 2줄), 문제인 두께를 칭찬, 좌우 바꿈, 밖으로 나간 입술 선에 "안쪽을 채우라" 2줄. 정도를 약하게 말함("가이드의 절반쯤" 인데 "조금 짧게")
- **Qwen3-14B 는 더 크지만 더 나쁘다** — 한국어 어색함("바렸어요" · "끊여"), 잘된 부위에 문제를 지어냄("섀도우 방향이 반대로 나갔어요"), 2.5배 느림
- **이점이 분명한 곳: 잘된 부위** — 지금은 "잘 됐어요" 한마디인데, 수치와 화장 의도로 구체적으로 칭찬한다 ("좌우의 꼬리 높이 차이가 거의 없어 아주 균형 잡힌 아이라인을 완성했고, 점막을 꼼꼼하게 채웠어요", "볼터치는 눈이 주인공인 세미 스모키에 맞춰 아주 옅고 은은하게 바르셨어요"). 자동 검사 174/174
- 기준에 가까운 값을 짚는 것은 확인 못 함 — 가짜 수치에 그런 경우가 거의 없었고, 있던 한 건(입술 안쪽 61%, 기준 50%)은 짚지 않았다

### 결론 (제안)
- 문제 판정: 채점 코드 (그대로)
- **문제 부위 한 줄: 규칙 R** — 사용자가 그대로 따라 하는 지시라 13% 의 조용한 오류가 크다
- **잘된 부위 한 줄: LLM** (수치 + 화장 의도로 구체적 칭찬) — 틀려도 피해가 작고 지금 문구보다 나은 자리
- 총평: LLM (2차 사람 평가 통과), 관문에 걸리면 B′
- 모델: Gemma 4 E4B (텍스트, 사진 없음). 한 세션 한 번 요청으로 총평 + 잘된 부위 칭찬

```bash
uv run --extra vlm python eval/comment/generate.py --model text-gemma4_e4b --task raw --reps 2 --max-tokens 900
uv run --extra vlm python eval/comment/results.py --raw text-gemma4_e4b raw
```
