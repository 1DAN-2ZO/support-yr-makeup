# 당화응 — 합성 데이터와 분할 모델 학습 (v6)

> 2026-09-16 · `poc/synth`에서 실제로 한 일을 처음부터 끝까지 적은 문서.
> **왜 학습하는가 → 무엇을 분류하는가 → 어떻게 라벨을 만들었는가 → 어떻게 학습했는가 → 무엇을 썼는가** 순서다.
> 코드는 `poc/synth/`, 요약은 `poc/synth/README.md`.

## 1. 왜 학습하나

### 1-1. 이 모델이 하는 일

기능 정의서 **F-08 부위 결과 인식**에서, 사용자가 "확인받기"를 누르면 이렇게 돈다.

```
랜드마크 정렬 → 조명 보정 → 맨얼굴 대비 Lab 색 차이(ΔE) 맵 → 부위 영역 추출 → 채점
```

문제는 **ΔE 임계값만으로는 영역이 지저분하다**는 것이다.

- 그림자가 진 곳이 화장으로 잡힌다 (오탐)
- 경계가 너덜너덜해서 겹침률 계산이 흔들린다
- 머리카락 그림자, 눈 밑 다크서클이 섞인다

그래서 **화장 영역 시맨틱 분할 모델**로 "여기까지가 실제로 바른 영역"을 정밀하게 잘라낸다.
기능 정의서 9장 모델 목록에서 **유일하게 "직접 학습"으로 표시된 모델**이다. 나머지는 전부 공개 모델을 가져다 쓴다.

> 모델이 실패해도 서비스는 멈추지 않는다. F-08에 "모델 실패 시 ΔE 임계만으로 진행"이 명시돼 있다.

### 1-2. 왜 남의 데이터로 안 하고 직접 만드나

원래 계획은 **FFHQ-Makeup**(맨얼굴-화장 쌍 108,000장)으로 학습하는 것이었다. 품질은 그쪽이 훨씬 낫다.
그런데 라이선스가 **CC-BY-NC-SA 4.0 (비상업)**이다.

**우리가 직접 학습하는 모델이라 이 조건이 우리 가중치에 따라붙는다.** 발표·과제는 되지만 사업화는 막힌다.
`tech-stack-v6.md` 8-4에서 이 위험을 정리하고 **"자체 합성 100%"**를 1순위 대체안으로 정했고, 이 문서가 그것을 실제로 해 본 기록이다.

| | 학습 데이터 | 라이선스 결과 |
|---|---|---|
| 원래 계획 | FFHQ-Makeup + 자체 합성 | **비상업 조건 승계** |
| **지금** | **자체 합성 100%** (맨얼굴도 우리 것) | **제약 없음** |

### 1-3. 이번 학습의 목적은 품질이 아니다

기능 정의서 13장 1주차 실기기 검증 7번이 이것이다.

> **7. 합성 데이터 생성기 100장 → 분할 모델 0차 학습 가능 여부**

즉 **"파이프라인이 돌긴 하는가"**를 확인하는 실험이다. 좋은 모델을 만드는 게 아니다.
실제로 쓸 모델은 해상도·데이터 양·실제 라벨 평가가 갖춰진 뒤에 나온다 (9장 한계 참조).

## 2. 무엇을 분류하나 — 클래스 설계

### 2-1. 6개 클래스

| 값 | 클래스 | 무엇 |
|---|---|---|
| 0 | 배경 | 화장이 안 된 모든 곳 (피부·머리카락·옷 포함) |
| 1 | 눈썹 | 그린 눈썹 |
| 2 | 아이라이너 | 속눈썹 선 위에 그린 라인 + 꼬리 |
| 3 | 섀도우 | 눈꺼풀에 얹은 색 |
| 4 | 입술 | 바른 입술 |
| 5 | 볼터치 | 광대 위 색 |

### 2-2. 왜 이 6개인가

**룩 템플릿이 담는 5부위 + 배경**이다. 기능 정의서 F-04에 "10개 룩은 눈썹·아이라이너·섀도우·입술·볼터치만 담는다"고 돼 있다.

**쉐딩·하이라이트는 일부러 뺐다.** 두 가지 이유다.

1. 룩 템플릿에 없다. 얼굴형 규칙(F-02·F-05)에서 오는 별도 단계다.
2. **항상 "확인만"이라 점수를 매기지 않는다** (F-09). 정밀한 영역이 필요 없다.

**좌우를 구분하지 않는다.** 왼쪽 눈썹과 오른쪽 눈썹이 같은 클래스 1이다.
좌우 비교는 **규칙 엔진이 랜드마크 좌표로** 한다(F-09 "맨얼굴 비대칭 뺀 좌우 차이"). 모델이 할 일이 아니다.
클래스를 11개로 늘리면 각 클래스의 데이터가 반으로 줄어 더 어려워지기만 한다.

### 2-3. 겹치면 어떻게 하나

한 픽셀에 클래스가 하나만 들어간다. 겹치는 부분은 **나중에 그린 것이 앞선 것을 덮는다.**
그리는 순서는 실제 화장 순서를 따른다.

```
섀도우 → 아이라이너 → 눈썹 → 입술 → 볼터치
```

그래서 예를 들어 섀도우 폴리곤 면적이 2,374px²라도 라벨에 남은 픽셀은 738개일 수 있다.
위에 아이라이너와 눈썹이 덮였기 때문이다. `manifest.json`에 **폴리곤 면적**과 **라벨 픽셀 수**를 따로 기록하는 이유다.

## 3. 어떻게 라벨링했나 — 이 프로젝트의 핵심

### 3-1. 사람이 라벨을 달지 않는다

보통 분할 모델 학습은 이렇게 한다.

```
사진을 모은다 → 사람이 한 장씩 부위를 칠한다 → 정답 마스크 완성
```

500장이면 한 장에 5분만 잡아도 **40시간**이다. 우리는 6명이 5주 안에 끝내야 한다.

그래서 순서를 뒤집었다.

```
맨얼굴 사진 → 랜드마크로 화장 폴리곤을 "그린다"
           → 같은 폴리곤을 두 군데에 쓴다
                ① 사진 위에 반투명 합성  → 합성 사진 (모델의 입력)
                ② 라벨 이미지에 정수로 채움 → 정답 마스크 (모델의 정답)
```

**우리가 그린 것이라 정답을 이미 알고 있다.** 라벨링 작업이 통째로 사라진다.

### 3-2. 폴리곤을 만드는 규칙

MediaPipe 랜드마크 **468점**(+홍채 10점)에서 부위별로 기하 규칙을 적용한다. 전부 `poc/synth/core.js`에 있다.

| 부위 | 만드는 방법 |
|---|---|
| 눈썹 | 자연 눈썹 테두리(위 능선 5점 + 아래 능선 5점)를 중심에서 `fill`배 키우고, 꼬리 쪽을 `tailLift`만큼 든다 |
| 아이라이너 | 윗속눈썹 선 9점을 바깥쪽으로 밀어 띠를 만든다. 바깥이 두껍고 안쪽으로 갈수록 얇아진다. 바깥 끝에 꼬리를 붙인다 |
| 섀도우 | 같은 속눈썹 선을 더 넓게 밀되, 가운데가 가장 높은 둥근 띠로 |
| 입술 | 바깥 테두리 20점을 중심에서 `1+overline`배. 음수면 안쪽으로 작게(인립) |
| 볼터치 | 눈 아래와 입꼬리 중간을 잡고, 얼굴 중심 반대쪽으로 얼굴 너비의 12% 밀어 타원 |

**모든 치수가 비율이다.** 두께는 "3px"가 아니라 "눈 너비의 8%"다. 그래서 해상도·얼굴 크기가 달라도 같은 모양이 나온다.

### 3-3. 정수 라벨을 지키는 것이 제일 중요했다

라벨 이미지의 픽셀값이 **곧 클래스 번호**다. 배경 0, 눈썹 1, …, 볼터치 5.
여기에 **경계가 흐려져 3.7 같은 값이 섞이면 학습이 깨진다.** 3.7은 섀도우도 입술도 아니다.

문제는 그래픽 라이브러리가 기본으로 **안티앨리어싱**(경계를 부드럽게)을 한다는 것이다.
경로가 두 개라 각각 다르게 풀었다.

| 경로 | 해결 |
|---|---|
| 파이썬 (`generate.py`) | **Pillow의 `polygon`은 안티앨리어싱이 없다.** 그냥 그리면 정수가 그대로 남는다 |
| 브라우저 (`app.js`) | 캔버스는 항상 안티앨리어싱이 걸린다. **부위마다 흰색으로 따로 그리고 알파 128을 기준으로 잘라** 정수만 남긴다 |

### 3-4. 라벨이 맞는지 기계로 검사한다

눈으로는 확인이 안 된다. 라벨 PNG는 값이 0~5뿐이라 **열어보면 거의 검은 화면**이다.
그래서 두 가지를 숫자로 검사한다.

1. **값 검사** — 이미지에 나타난 값이 전부 {0,1,2,3,4,5} 안에 드는가
2. **합계 검사** — 클래스별 픽셀 수의 합이 이미지 넓이와 정확히 같은가

500장 전수 검사 결과 **이상값 0장, 합계 불일치 0장**이었다.
(예: 168×364 사진에서 58,611 + 808 + 132 + 154 + 543 + 904 = 61,152 = 168×364)

### 3-5. 이 방식의 한계 — 반드시 알고 있을 것

**"정답"은 우리 규칙이지 실제 화장이 아니다.**

합성 데이터로 학습한 모델은 "사람이 진짜 그린 아이라이너"가 아니라 "우리 규칙이 그린 아이라이너"를 배운다.
실제 사진에서 잘 작동한다는 보장이 없다. 이것을 **합성→실제 일반화(sim-to-real gap)**라고 한다.

기능 정의서가 이미 대비해 두었다.

- 11장 평가 지표: "분할 모델 mIoU **(합성→실제 일반화)**"
- 15장 리스크: "분할 모델 합성→실제 일반화 실패 → **평가 라벨 200장으로 조기 판단, 실패 시 ΔE 임계만 사용**"

즉 **실제 사진 200~500장은 사람이 라벨을 달아야 한다.** 다만 학습용이 아니라 **평가 전용**이라 양이 훨씬 적다.

## 4. 어떻게 데이터를 만들었나

### 4-1. 규모

| | |
|---|---|
| 맨얼굴 | `poc/samples/phone-portraits-20/` 5명 (정면 눈 뜸) |
| 장수 | 사람당 100장 × 5명 = **500장** |
| 시드 | 1번 0~99, 2번 100~199, … 5번 400~499 (**겹치지 않게**) |
| 크기 | 얼굴 크롭 후 **256×256** |
| 생성 시간 | **10초** |

### 4-2. 매 장 무엇이 달라지나

시드 하나가 아래 값을 전부 정한다. 같은 시드는 **항상 같은 결과**를 낸다(재현 가능).

| 파라미터 | 범위 | 뜻 |
|---|---|---|
| 좌우 비대칭 | ±18% | 왼쪽·오른쪽 크기 차이 |
| 라이너 두께 | 눈 너비의 5~13% | |
| 라이너 꼬리 길이 / 각도 | 0~30% / 0.05~0.55 rad | |
| 눈썹 키움 / 꼬리 높이 | 1.00~1.18배 / −10~+22% | |
| 섀도우 높이 | 눈 너비의 15~42% | |
| 입술 오버립 | −4~+10% | 음수는 인립 |
| 볼터치 반지름 | 얼굴 너비의 22~40% | |
| 색 | 부위별 7~13종, 총 48개 | 조합 **69,888가지** |
| 농도 | 부위별 0.15~1.0 | |
| 섀도우·볼터치 유무 | 75% / 80% 확률 | 없는 날도 있다 |

**좌우 비대칭(±18%)을 일부러 넣는다.** 두 가지 이유다.

1. 초보자가 실제로 그리는 모습에 가깝다
2. **채점기의 좌우 차이 판정(F-09)을 학습시키는 데 쓴다.** 좌우가 완벽히 같은 데이터만 보면 차이를 못 잡는다

### 4-3. 색 계열 이름을 같이 기록한다

색마다 `COLOR_FAMILY`로 이름이 붙어 있다 — 레드, 코랄, MLBB, 누드베이지, 버건디, 라벤더…
**F-04 제품 목록이 쓰는 "색 계열"과 같은 어휘**다. `manifest.json`에 같이 기록되므로 나중에 룩 템플릿과 연결하기 쉽다.

> **이 팔레트는 임시값이다.** 룩 템플릿 10개의 색 계열이 정해지면 그것으로 교체한다.

## 5. 클래스 불균형 — 가장 큰 문제

### 5-1. 얼마나 심한가

500장 전체 픽셀을 세어 봤다.

| 클래스 | 비율 |
|---|---|
| 배경 | **94.69%** |
| 볼터치 | 1.50% |
| 눈썹 | 1.47% |
| 입술 | 1.33% |
| 섀도우 | 0.67% |
| **아이라이너** | **0.34%** |

**아이라이너가 배경보다 280배 드물다.**

### 5-2. 왜 위험한가

모델이 **모든 픽셀을 배경이라고 답해도 정확도 94.69%**가 나온다.
아무것도 못 배운 모델이 94점을 받는다. 정확도만 보면 잘 되는 줄 알고 넘어가게 된다.

### 5-3. 크롭만으로는 안 됐다

먼저 얼굴만 잘라 정사각형으로 만들어 봤다. 목·옷·배경이 빠지니 나아지긴 했다.

| | 배경 비율 | 아이라이너 |
|---|---|---|
| 원본 168×364 | 96.16% | 0.24% |
| **얼굴 크롭 256×256** | **94.69%** | **0.34%** |

**2%포인트 줄었을 뿐이다.** 얼굴 사진에서 화장 영역이 원래 좁아서 그렇다.
크롭은 여전히 쓴다(쓸데없는 배경이 빠지고 얼굴이 커진다). 다만 이것만으로는 부족하다.

### 5-4. 실제 대응 두 가지

**① 손실에 클래스 가중치**

드문 클래스를 틀리면 더 크게 벌준다. 가중치는 **빈도의 역제곱근**을 쓴다.

| 클래스 | 빈도 | 가중치 |
|---|---|---|
| 배경 | 94.68% | 0.11 |
| 눈썹 | 1.47% | 0.89 |
| **아이라이너** | **0.34%** | **1.85** |
| 섀도우 | 0.66% | 1.33 |
| 입술 | 1.34% | 0.94 |
| 볼터치 | 1.51% | 0.88 |

> 왜 역수가 아니라 **역제곱근**인가. 역수로 하면 아이라이너 가중치가 배경의 280배가 된다.
> 그러면 모델이 아이라이너를 과하게 칠해 오탐이 폭발하고 학습이 흔들린다. 제곱근이 그 사이를 잡아 준다.

**② 평가 지표를 정확도가 아니라 IoU로**

**IoU**(교집합 ÷ 합집합)는 클래스마다 따로 계산한다. 배경이 아무리 많아도 아이라이너 IoU는 아이라이너만 본다.
"전부 배경" 모델은 아이라이너 IoU가 **0**이 나온다. 속일 수 없다.

화면에 보고하는 값은 **배경을 뺀 화장 5부위의 평균 IoU**다.

## 6. 어떻게 학습했나

### 6-1. 데이터를 사람 단위로 나눴다

| | |
|---|---|
| 학습 | 1·2·3·4번 = **400장** |
| 검증 | **5번 = 100장 — 학습에 한 번도 안 쓴 얼굴** |

**왜 장 단위가 아니라 사람 단위로 나눴나.** 같은 얼굴의 다른 장이 학습과 검증에 섞이면,
모델이 그 얼굴을 외워 버려서 점수가 부풀려진다(데이터 누수).
사람 단위로 나눠야 **"처음 보는 얼굴에서도 되는가"**를 잰다.

### 6-2. 모델

**TinyUNet** — U-Net 구조를 작게 줄인 것. **482,822 파라미터**.

```
입력 256×256×3
  → 인코더 4단 (16 → 32 → 64 → 128 채널), 단마다 절반으로 축소
  → 디코더 3단, 인코더와 스킵 연결
  → 출력 256×256×6 (클래스별 점수)
```

**왜 작게 만드나.** 이 모델은 서버가 아니라 **사용자 폰에서** 돈다 (`tech-stack-v6.md` C-5).
웹은 WASM/WebGPU, 앱은 INT8로 돌릴 것이라 처음부터 작게 잡는 게 맞다.
크게 만들면 정확도는 오르지만 30fps를 못 맞춘다.

### 6-3. 학습 설정

| 항목 | 값 | 이유 |
|---|---|---|
| 손실 | 가중 CrossEntropy | 5-4 ① |
| 옵티마이저 | AdamW, lr 3e-3, weight decay 1e-4 | 무난한 기본값 |
| 스케줄러 | CosineAnnealing | 뒤로 갈수록 학습률을 낮춰 안정화 |
| 배치 | 8 | CPU 메모리 기준 |
| 에폭 | 30 | |
| 증강 | **좌우 뒤집기만** | 아래 참조 |
| 장비 | **CPU** (GPU 없음) | |

**왜 좌우 뒤집기는 안전한가.** 우리 클래스에 좌우 구분이 없다(2-2). 뒤집어도 눈썹은 눈썹이다.
반대로 **회전·색 변경은 넣지 않았다.** 색을 바꾸면 우리가 통제한 색 분포가 망가지고,
회전은 실제 촬영에서 안 생기는 상황이다(품질 게이트가 정면성 ±15°를 강제한다).

### 6-4. 비교군을 같이 돌렸다

클래스 가중치가 실제로 효과가 있는지 확인하려고 **가중치를 끈 것도 같은 조건으로** 돌렸다.

### 7-3. 검증 (이 프로젝트에서 제일 신경 쓴 부분)

| 방법 | 무엇을 잡나 | 결과 |
|---|---|---|
| `tests.mjs` **27개** | 폴리곤 기하, 시드 재현성, 파라미터 범위, 단조성, 좌우 대칭, 구성 순서 | 27/27 |
| `parity.py` | **파이썬 이식본이 JS 원본과 같은 결과를 내는지** 시드 500개 대조 | 전부 일치 |
| 라벨 전수 검사 | 값이 0~5인지, 픽셀 합이 넓이와 같은지 | 500장 이상 0 |
| 사람 단위 검증 분할 | 처음 보는 얼굴에서 되는지 | 8장 |
| 헤드리스 크롬 캡처 | 브라우저 화면이 실제로 그려지는지 | 스크린샷 |

**검증이 실제로 버그를 두 개 잡았다.**

1. **왼쪽 눈 꼬리가 아래로 뻗고 있었다.** 좌우 회전 부호가 같아서 한쪽만 방향이 반대였다.
   대칭 얼굴에서 좌우 면적을 비교하는 테스트가 2.66% 차이로 걸러냈다. 눈으로는 못 알아챘다.
2. **볼터치가 다크서클처럼 보였다.** 눈과 입 중간을 그냥 반으로 나누니 코 옆에 붙었다.
   얼굴 중심 반대쪽으로 얼굴 너비의 12%를 밀어야 광대 위에 온다.

### 7-4. 두 언어로 같은 계산을 한 이유

`core.js`(브라우저)와 `core.py`(대량 생성)가 **같은 계산을 두 번 구현**하고 있다. 보통은 피해야 할 일이다.
그래도 그렇게 한 이유는 이렇다.

- 브라우저: 팀원이 눈으로 보며 파라미터 감을 잡는 용도. 설치가 필요 없다
- 파이썬: 수천 장을 찍어내는 용도. 브라우저로는 못 한다

대신 **`parity.py`가 둘이 어긋나면 즉시 잡는다.** 시드 500개에서 파라미터·부위 순서·면적·폴리곤 좌표를
소수점까지 대조한다. 자바스크립트의 `Math.imul`과 `>>>`(32비트 연산)를 파이썬에서 그대로 재현해야 했다.
