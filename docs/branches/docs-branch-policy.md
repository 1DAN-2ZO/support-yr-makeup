### #96 브랜치 규칙 정리 + 강제 푸시 차단 (2026-09-18 사고 대응)
- 브랜치: `docs/branch-policy` · 병합 2026-09-18 · +207 −4
- 한 일: 브랜치 규칙을 정리했다. 작업은 자기 모듈 브랜치에서 직접 하고 작업마다 브랜치를 파지 않는다. `main` 으로 모으는 것은 금요일 리뷰일에 PR 하나로 한다(다른 모듈이 기다리는 것은 끝나는 대로 바로 PR). 내 브랜치가 뒤처지면 내가 `git merge origin/main` 하고, 남의 브랜치를 대신 맞추지 않는다. 그리고 강제 푸시를 막는 장치 두 겹을 넣었다.
- 결과: 시험 완료 — 보호 브랜치 강제 푸시 차단, 삭제 차단, 일반 브랜치 `FORCE_OK=1` 경로를 확인했다. 보호 브랜치는 `FORCE_OK` 로도 뚫리지 않는다.
- 트러블슈팅:
  - 사고(2026-09-18): 모듈 브랜치를 main 에 맞추려고 `git branch -f` + `git push -f` 를 돌렸고, 그 사이 올라온 팀원 커밋 두 건이 원격에서 사라졌다. 07:14(UTC) 에 `capture` · `model` 을 덮어써 jeakeun 의 `31642ba`, JW020799 의 `b5aa584` 가 유실됐고, 07:33 에 `model` · `score` · `guide` · `server` 를 덮어써 `6aa8dc7` 이 유실되고 PR #92 가 변경 0건으로 닫혔다.
  - 원인: 저장소에 그런 스크립트나 Action 은 없었다. 세션에서 손으로 친 명령이 원인이었다.
  - 복구: jeakeun 의 커밋은 `rescue/capture-jeakeun` 브랜치에 보존했다. 모듈 브랜치에 임의로 되돌려 넣지는 않았다.
  - 재발 방지 1: `.githooks/pre-push` — 원격 커밋이 내 커밋의 조상이 아니면 푸시를 거부하고, 보호 브랜치 삭제도 거부한다. `setup.sh` 가 자동 설치한다. 푸시 직전에 막는다.
  - 재발 방지 2: `.github/workflows/guard.yml` — 강제 푸시 · 보호 브랜치 삭제를 사후에 감지해, 덮기 전 SHA 와 복구 명령을 Summary 에 남긴다. 막지는 못하는 안전망이다.
  - `poc/full` 표현 정정: "기준 · 정답" → "초기 데모". 전체 흐름을 처음 끝까지 돌려 본 것이고 TS 이전의 출발점일 뿐이다. 옮기고 난 뒤로는 `client/src/core` 가 현행이고, 둘이 갈리면 현행이 맞다.
