### #352 [app][server] 그림 만들기 잇기 — 앱 → 백엔드 POST /transfer → GPU 의 FLUX 서버 (꺼진 채로 미리 만듦)
- 브랜치: `app-transfer-wire` · 열림 · +678 −5
- 한 일: 앱에서 정답사진 · 옮긴 그림을 만들어 달라고 서버에 부르는 길(앱 → 우리 백엔드 `POST /transfer` → GPU PC 의 FLUX 서버 → 그림 한 장)을 미리 만들었다. GPU 서버 주소(`DHE_FLUX_URL`)를 넣어야 켜지고, 이 PR 은 그 설정(`compose.yml`)을 건드리지 않아 병합해도 지금 동작은 그대로다.
- 결과: 서버에 `server/app/flux.py` 와 `POST /transfer`(`bare` · `ref` 두 장을 받아 그림을 돌려줌)를, 앱에 `core/transfer-client.ts` · `core/picture-maker.ts`(`makeAnswer` · `makeMoved`)를 만들었다. ⑤ 모델/UI 담당의 파일 `client/nginx.conf` 에 `/transfer` 를 백엔드로 넘기는 칸을 더했다(올리는 크기 40MB · 기다리는 시간 200초). 서버 테스트 `test_transfer` TR1~TR11(가짜 FLUX) · 앱 테스트 `transfer-client` TC1~TC6 · PM1~PM6 을 먼저 쓰고 실패를 본 뒤 구현했다. 가짜 FLUX 서버와 진짜 백엔드를 띄워 실제 HTTP 로 한 바퀴 돌렸다: 사진 두 장 올림 → 그림 그대로 돌아옴(200) · 맨얼굴 내용이 FLUX 까지 그대로 감 · 주소 없음 503 `off` · GPU 서버 죽음 502 `down` · 사진이 아님 422. `scripts/check.sh` 통과(pytest 135 · vitest 1213 · 타입 · 린트) · 배포용 빌드 통과.
- 트러블슈팅:
  - 문제: FLUX 서버(Gradio)에는 로그인이 없다 → 푼 방법: 바깥에 열지 않고 백엔드만 닿게 했다.
  - 문제: 그림 한 장을 받으려면 세 번 오가야 한다(요청 → 번호 → 결과 기다리기 → 파일 받기) → 푼 방법: 그 방식을 백엔드에 가뒀다. 앱은 "사진 두 장을 올리면 그림 한 장이 온다" 만 안다.
  - 문제: GPU 가 한 대라 요청이 몰릴 수 있다 → 푼 방법: 한 번에 한 장만 보내고, 줄이 꽉 차면(그리는 중 1 + 기다림 6) 더 세우지 않고 503 `busy`(`Retry-After`)를 낸다. 만드는 중에 또 부르면 새로 보내지 않아서 버튼을 두 번 눌러도 GPU 는 한 번만 돈다.
  - 문제: 정답사진과 옮긴 그림이 같은 설정이어야 견줄 수 있다(#328 지킬 것 2) → 푼 방법: 단계 수 · 강도 · seed 를 고정했다.
  - 문제: 앱에서 실패 까닭을 알아야 안내할 수 있다 → 푼 방법: 실패를 던지지 않고 까닭으로 돌려준다(`off` · `busy` · `down` · `rejected` · `too_large` · `timeout` · `network`).
- 남긴 것: 진짜 FLUX 서버와는 이어 보지 못했다(이 PC 에는 그래픽카드 · 모델이 없고 Tailscale 밖). 가짜 서버는 ② 가이드 담당의 시험 페이지(`makeup-extract-probe.ts` `callAi`)가 부르는 방식을 흉내 낸 것이라, 진짜 Gradio 의 답 모양이 다르면 `down` 으로 나온다. 돌아온 그림이 맨얼굴과 픽셀까지 같은 크기인지, 폰에서 원본 크기 사진 두 장을 올리는 시간, ① 이 #341 에서 부탁한 것은 켜진 뒤에 잴 수 있다. 켜려면 도커 안의 백엔드에서 `100.110.57.95:7861` 로 닿는지 확인 · `compose.yml` 에 `DHE_FLUX_URL` 넣기 · GPU PC 에 #342 버전 서버 올리기 · 화면 3 이 필요하다. `makeMoved()` 는 만들어 뒀지만 아무도 부르지 않는다(③ 채점 담당의 라이너 수정 뒤에 잇는다). 참고 사진은 줄이지 않고 올려서 폰 사진첩의 큰 사진(15MB 넘음)은 `too_large` 가 된다 — 올리기 전에 줄이는 것은 화면 3 을 붙일 때 넣기로 했다. FLUX 서버에 사진이 2분쯤 남으니 동의 문구의 "바로 지워요" 표현을 맞춰야 한다. `/transfer` 는 로그인이 없고 줄 한도(7명)가 유일한 보호라 공개 전에 요청 수 제한이 필요하다.

## PR 을 올린 뒤 — 병합 전 코드 검토에서 나온 것 (2026-10-08, PR 댓글)

얼굴 사진이 오가고 로그인 없이 열리는 길이라, 병합 전에 따로 코드 검토를 받았다. 검토는 가짜 그림 서버(진짜 소켓)와 진짜 백엔드를 띄워 직접 돌려 문제를 재현했다.

- 트러블슈팅:
  - 그림 서버가 그리다 멈추면 줄이 영영 막혔다 → 그림 서버는 그리는 동안 "기다리는 중" 신호를 계속 보내서, 읽기 시간 한도(150초)가 신호마다 새로 시작됐다. 잠금이 안 풀려 뒤 요청이 전부 "바쁨" 이 됐다 → 줄에서 기다린 시간까지 합친 전체 한도(85초)를 두었다. 한도를 2초로 두고 돌리니 2.0초 만에 끊기고 줄이 비었다.
  - 앱이 연결을 끊어도 백엔드는 끝까지 그렸다 → 요청 처리가 취소되지 않았다. 3개를 0.3초 만에 끊어도 3건이 모두 그래픽카드까지 갔다 → 앱이 끊었는지 1초마다 보고, 끊었으면 줄에서 뺀다. 고친 뒤에는 이미 시작한 1건만 갔다.
  - 크기 한도(15MB)가 몸통을 다 받은 뒤에야 걸렸다 → 웹 프레임워크가 처리 함수를 부르기 전에 올린 파일 전체를 받아 둔다. 200MB 를 올리면 200MB 를 다 받은 뒤 거절했다 → 몸통을 받기 전에 `Content-Length` 로 거른다. 고친 뒤에는 몸통을 보내기도 전에 413 이 나왔다. 줄이 꽉 찼을 때도 사진을 읽기 전에 돌려보낸다.
  - 기다리는 한도가 Cloudflare 가 끊는 시간(100초)보다 길었다 (앱 180초 · nginx 200초) → 백엔드 85초 < 앱 95초 < nginx 100초로 맞췄다. 100초는 알려진 기본값이고 이 배포에서 직접 재지는 못했다.
  - 그림 서버의 모든 오류가 "그릴 수 없는 사진" 으로 안내되고 내부 오류 문장이 응답에 실릴 수 있었다 → "얼굴을 못 찾음" 만 사진 탓으로 알리고(정해 둔 문장), 그 밖은 서버 고장으로 답한다. 그림 서버가 한 말은 백엔드 로그에만 둔다.
  - 사진 종류를 올린 쪽이 적은 글자 그대로 그림 서버에 넘겼다 → 내용의 첫머리(JPEG · PNG · WebP)로 정한다.
  - 만드는 중에 다른 사진으로 또 부르면 앞 사진의 결과를 새 사진의 결과처럼 돌려줬다 → 같은 사진일 때만 같은 결과를 기다리고, 다른 사진이면 "만드는 중" 으로 답한다.
  - 끝내기가 폰을 비운 뒤 서버 답이 도착하면 얼굴 그림이 폰 저장소에 다시 써질 수 있었다 → 끝내기 · 맨얼굴 다시 찍기 · 시도사진 다시 찍기에서 "버림" 을 표시하고, 그 뒤 도착한 그림은 넣지 않는다.
- 결과: 서버 테스트 25개 · 앱 테스트 22개. `scripts/check.sh` 통과 (pytest 144 · vitest 1218).
- 남긴 것: 그래픽카드가 이미 그리기 시작한 한 장은 앱이 끊어도 끝까지 그린다 (그림 서버에 "그만" 을 보낼 길이 없다). 요청 수 제한이 없어 공개 전에 nginx 나 Cloudflare 에서 제한이 필요하다. 진짜 그림 서버와는 아직 이어 보지 못했다.
