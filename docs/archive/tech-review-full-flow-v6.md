당화응 · 기능 정의서 F-01 ~ F-11 순서 · 2026-09-17
근거: `feature-spec-v6.md`(+ jeakeun 정정 7cb58cd), `impl-screen1-5-definition-v6.md`, `impl-screen6-review-v6.md`, POC 브랜치 `poc/screen2` 475bc93 · `poc/screen3` 1c39dc6 · `poc/screen4` baebc39 · `poc/screen5` 91c6f7c · `poc/screen6` d50a7fa · `poc/full` 53a1c2b, 결정 `189e42c`(mm→비율), 데이터 계획 4차(`data-plan-v6.md`), 화면 5 검토(2026-09-16), 화면 6 검토(`tech-review-screen6-v6.md`)

> **한눈에**
전체 흐름 **동의 → 촬영 4장 → 룩 10개 → 전체 완성 예상 → [완성본 → 실시간 테두리 → 결과] × 6부위 → 전체 리뷰 → 끝내기**가 `poc/full`에서 끝까지 돈다(Node 16개 + 각 화면 POC 검증 26·27·24개). 기능 정의서의 MVP 기능 11개 중 **기술이 없어서 막히는 것은 없다.**
>
> 정의서대로 **안 되는 것은 여섯**이고 전부 대안이 있다: ① 브라우저 노출·화이트밸런스 고정(불가 → 보정·게이트) ② 서버 법선 맵(비상업 라이선스·미구현 → 랜드마크 근사로 이미 화면이 뜸) ③ 512 렌더 줌 완성본(7.4배 뭉개짐 → 원본 + 화장 레이어) ④ 468점 메시 워핑(POC는 3점 아핀 → WebGL로 구현 필요) ⑤ 손 픽셀 마스크(모델이 점 21개만 → 프레임 제외) ⑥ 자체 학습 분할 모델(5주 내 위험 → **MVP에서 뺌**, 데이터 계획 4차). 여기에 **정의서에 없던 "안 되는 것" 하나** — 촬영 4장 중 **눈 감음 장과 좌우 45° 장은 찍기만 하고 아무 데도 안 쓴다**(법선·눈꺼풀 기준이 미구현이라).
>
> 막히는 곳은 기술이 아니라 셋이다: **실제 조건에서 한 번도 안 돌려 본 것**(거울 다녀온 두 장, 폰 실기기, 색 변동), **가정값 30여 개가 전부 미검증**, **POC 6개 + 팀원 브랜치 3개를 하나로 합치는 일**. 자체 학습 모델은 분할 모델 대신 **얼굴형 분류기**로 정했고(데이터 계획 4차), 이것이 F-02의 판정을 바꾼다.

### 안 되는 것과 대안

**① 노출·WB 고정 불가** — 화면 5 검토 §3-①과 같은 문제의 뿌리. 대안 세 겹: (a) 되는 기기는 `getCapabilities()`로 잠근다 (b) 눈 흰자 참조를 실제로 구현해 a*·b*까지 보정 (c) 게이트에 a*·b* 변동 조건을 넣어 색이 밀리면 "확인만". 1주차 검증 2번이 밝기만 재게 돼 있어 **색 변동 측정을 추가**해야 이 위험이 보인다.

**② 눈 감음·45° 장이 놀고 있다** — 정의서는 4장을 다 쓴다고 적었지만 실제로 쓰는 건 정면 뜸 1장뿐이다. 쓰려면 눈꺼풀 기준점(아이라이너 가이드의 눈꺼풀 경계를 감은 눈에서 잡기)과 법선·메시 워핑(§3)이 구현돼야 한다. 대안: **MVP에서는 정면 2장만 찍는다**로 정의서를 줄이든가, 45° 장을 "쌩얼 vs 내 화장" 비교나 얼굴형 분류기 입력(§2)으로 쓰는 용도를 새로 정한다. 사용자에게 60초 동안 4장을 찍게 하고 2장을 버리는 건 정직하지 않다.

**③ 서버 법선 + 파싱** — §5-②.

## 2. F-02 얼굴형 판정

| # | 기술 | 판정 | 근거 |
| --- | --- | --- | --- |
| 1 | 랜드마크 2D 비율 → 5분류 | **가능 · 구현됨** | `looks.js estimateFaceShape`: 가로세로비 1.55, 턱 폭 0.78 등 임계 4개 |
| 2 | 화면 비표시, 쉐딩 멘트로만 | **가능 · 구현됨** | 화면 3-c 멘트 5종, 숫자 없음 검증 |
| 3 | 정확도 | **미검증** | 논문상 랜드마크 규칙 36~65%. 우리 사진 라벨 0장 |
| 4 | (4차) 분류기 학습으로 교체 | **가능 · 데이터 필요** | Kaggle Face Shape 5,000장 1차 학습 + 자체 라벨 50~100명 파인튜닝 |

**바뀐 판정 (데이터 계획 4차):** 정의서는 "별도 분류 모델은 두지 않는다"였다. 분할 모델을 MVP에서 빼면서 **우리가 학습하는 유일한 모델이 얼굴형 분류기**가 됐다. 규칙은 그대로 두고 모델은 "이 얼굴이 어느 형인가"만 맡는다. 필요한 것: 규칙 정확도 기준선(자체 라벨로 먼저), Kaggle 셋(라벨 근거·라이선스 불명 → 1차 학습까지만), 팀원 2인 독립 라벨 + 일치율, AI Hub 한국인 안면(승인 시). 정의서 F-02 "검증(선택)" 문장을 "학습(필수)"로 고친다.

| 7 | 룩 전환 0.5초 | **가능** | 레이어를 폰에 캐시하면 즉시 |
| 8 | 서버 장애 시 재시도 안내 | **가능 · 미구현** | 폴백 미리보기 없음(정의서) |

### 안 되는 것과 대안

**① 메시 워핑이 아직 아핀이다** — 3점 아핀은 얼굴 전체를 한 장으로 붙이므로 웃으면 입술 레이어가 입에서 벗어난다. 대안 순서: (a) 부위별 아핀(눈·입·볼 각각 3점) — 코드 작음, 표정 절반 해결 (b) MediaPipe `FACE_LANDMARKS_TESSELATION` 삼각형 단위 텍스처 매핑, WebGL — 정의서 방식, 1주 (c) three.js `BufferGeometry`로 같은 것. 30fps는 (b)에서 저가 기기 실측이 필요하다.

**② 화장 레이어 추출이 조명을 탄다** — 서버 결과(512, 서버 조명 없음)와 원본 정면을 뺀 차이에는 확산 모델이 바꾼 피부 톤·그림자까지 섞인다. 대안: (a) 부위 마스크(파싱 또는 랜드마크 폴리곤) 안에서만 ΔLab을 취하고 마스크 밖은 0 (b) 알파를 ΔE 크기로 두어 약한 변화는 안 입힘 (c) 라이브 프레임 이마 L*로 레이어 밝기를 매 프레임 스케일. 정의서가 "조명이 크게 바뀌면 어긋남"을 이미 한계로 적었다.

**③ 동시 사용자** — GPU 1장, 룩당 2.5초면 시연 1명은 되고 발표장 3명이면 밀린다. 대안: 고른 룩부터 생성(순서 우선), 256 저해상 먼저, SPIGA 랜드마크 캐싱(같은 얼굴에 룩 10개면 얼굴 구조 추출 1회), LCM-LoRA 4~8 step. 이건 §8-C 서버 절.

**④ 참조 사진이 없다** — 기술이 아니라 콘텐츠. 이게 정해지기 전에는 룩 10개 전이·정체성 평가·LoRA 전부 못 돈다. 이번 주 결정 항목(데이터 계획 10번).

## 13. 먼저 할 것 — 순서

1. **팀원 실촬영 세트** (데이터 계획 2번). 20명 × 10장 단계별 + 일부러 벗어난 장 + 조명 3종. 부위별 사람 판정, 얼굴형 2인 라벨. 이것 없이는 §12의 값이 하나도 안 정해지고 발표 숫자 3개가 안 나온다.
2. **HTTPS 실기기 환경** (iOS 1 · 저가 Android 1). §1·§6·§7·§9의 "미실측"이 전부 여기서 풀린다. WB 잠금 지원 기기 표를 같이 만든다.
3. **룩 참조 사진 10장 방법 결정**. F-03·F-04·F-06 완성본 소스·정체성 평가·LoRA가 전부 이 뒤에 있다.
4. **정의서 정정 5건** (아래). 특히 눈 감음·45° 장 용도와 법선 제외를 정해야 촬영 화면이 정직해진다.
5. **공통 모듈 통합** (§10-E). 그다음 화면을 붙인다. 화면부터 붙이면 브랜치 9개의 복제본이 제품에 들어간다.
6. **확인받기 프레임 평균 + 손 프레임 제외 + 눈 흰자 보정 + 채점 값 두 개(colorAb·눈썹 lrDiff)**. 각 반나절~하루. 화면 5·6 검토의 "고쳐야 함"이 전부 채점 모듈 한 곳이다.
7. **얼굴형 분류기 1차 학습** (Kaggle → 자체 라벨). 규칙 기준선을 먼저.
