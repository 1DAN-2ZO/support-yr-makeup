## 0. 외울 것 10줄 — 누가 물어보면 이렇게 답한다

1. **화면 3은 "다 그리면 이렇게 됩니다" 를 보여주는 정지 이미지 화면이다.** 카메라 안 켠다.
2. **완성본은 부위별로 따로 만들지 않는다.** 전체 완성 렌더 한 장을 그 부위로 줌한다 (v6 확정).
3. **새 모델은 0개.** 크롭 계산·칩·문장·저장 전부 웹 표준과 규칙으로 된다.
4. **랜드마크 재검출 안 한다.** 촬영 1에서 저장한 468점을 읽어 크롭 박스만 계산한다.
5. **제일 큰 문제는 해상도.** 서버 렌더가 512라 눈 단계는 7.4배 확대 → 선이 뭉개진다.
6. **해결 순서는 C → D → 512줌.** C = 원본 사진에 화장 레이어 얹기(3.6배, 새 모델 없음), D = 타일 업스케일 1024(3.7배, Apache-2.0).
7. **결정은 ΔE 숫자 하나로.** 1주차 검증 5에서 C의 색 차이와 D의 처리 시간을 잰다. 룩당 3초 제약은 화면 3엔 안 걸린다.
8. **쉐딩·하이라이트(3-c)는 렌더에 없다.** 얼굴형 규칙으로 점선 테두리만 그린다. 규칙 5종이 아직 없다 — 기술이 아니라 콘텐츠 문제.
9. **근거 한 줄은 LLM 안 쓴다.** 55문장을 사람이 미리 쓴다. 방향은 iOS 잠금 불가라 안내만 한다.
10. **어떤 경우에도 빈 화면은 없다.** 서버·레이어·문장·규칙이 다 없어도 맨얼굴 사진 + 기본 문장으로 뜬다.

## 1. 화면 3이 뭐 하는 화면인가

부위 단계에 들어오면 **"다 그리면 이렇게 됩니다"** 를 정지 이미지로 먼저 보여주는 화면. 카메라 안 켬.

```
[진행 칩 6개]  눈썹 · 아이라이너 · 섀도우 · 입술 · 볼터치 · 쉐딩
┌──────────────────────┬────────────────┐
│                      │ 완성본          │
│  완성본 이미지         │ 아이라이너       │
│  (전체 완성 예상을      │ 근거 한 줄       │
│   이 부위로 줌)        │ 지금 필요한 것    │
│                      │ [그리러 가기]    │
└──────────────────────┴────────────────┘
눈썹·아이라이너·섀도우 = 가로 화면 / 입술·볼터치·쉐딩 = 세로 화면
```

**v6 확정:** 부위만 따로 합성하지 않는다. 화면 2-b의 **전체 완성 렌더 한 장을 그 부위로 줌**한다. 그래서 지나온 부위도 화장된 채로 보인다.

## 3. 쓰는 기술 — 새 모델은 0개

| 요소 | 쓰는 것 | 되나 |
|---|---|---|
| 진행 칩 | 순수 JS 상태(`poc/screen6/core.js` 재사용) + CSS Flexbox 가로 스크롤 + `localStorage` | ✅ |
| 방향 감지 | `matchMedia('(orientation: portrait)')` + `change` 이벤트 | ⚠️ iOS는 잠금 불가, 안내만 |

| 크롭 박스 | 촬영 1의 랜드마크 468점으로 **순수 JS 기하 계산**. 재검출 없음 | ✅ 구현됨 (`crop.js`, 검증 29개) |
| 3-c 테두리 | Canvas 2D `Path2D` + 점선 | ⚠️ 규칙 5종이 없음 |
| 근거 한 줄 · 제품 | 룩 템플릿 JSON 고정 문장. **LLM 안 씀** | ✅ 콘텐츠 55문장만 쓰면 됨 |
| 완성본 보관 | 메모리(`ImageBitmap`) → IndexedDB → OPFS. 세션 끝나면 삭제 | ✅ |

**화면 3이 안 쓰는 것:** 카메라, 손 검출, 분할 모델, 실시간 추적, 30fps 루프. 전부 화면 4·5 것.
**랜드마크 검출도 안 한다** — 촬영 1에서 저장해 둔 걸 읽기만 한다. 그래서 "검출 실패하면?" 차선책이 필요 없다.

## 4. 제일 큰 쟁점 — 완성본 해상도

눈 단계는 양쪽 눈을 가로 화면에 꽉 채운다. 그런데 서버 렌더는 **512×512** 다.

| 완성본 원본 | 화면 채우려면 | 판정 |
|---|---|---|
| 서버 렌더 512 (지금 문서 방식) | **7.4배 확대** | 아이라이너 선이 뭉개짐 |
| 서버 렌더를 1024로 타일 업스케일 | 3.7배 | 가능 |
| **원본 사진 1080×1920 + 화장 레이어** | **3.6배** | ★ 추천 |
| 원본 사진 1440×1920 + 레이어 | 2.7배 | 더 좋음 |

### 대안 5개와 순위

| 순위 | 방법 | 배율 | 새 모델 | 라이선스 | 언제 |
|---|---|---|---|---|---|
| **1** | **C. 원본 사진 + 화장 레이어** — F-03이 이미 만드는 레이어를 정면 사진에 한 번 씌움 | 3.6배 | 없음 | — | ΔE가 받아들일 만하면. 비용 0이라 먼저 |
| **2** | **D. 타일 확산 업스케일 512→1024** (MoD Control Tile Upscaler SDXL) | 3.7배 | SDXL 1회 | Apache-2.0 | C의 ΔE가 크면. 2-b 로딩 10~20초 감수 |
| 3 | 서버 렌더 512 줌 (지금 방식) | 7.4배 | 없음 | — | 위 둘 다 안 되면 |
| 발표용 | E. 눈 부위만 따로 생성 (FRAM, CVPR 2026) | 무손실 | 확산 1종 | **비상업** | 데모 품질용. v6 결정("전체 줌")을 다시 열어야 함 |
| 최후 | 룩 참조 이미지 그대로 | — | 없음 | — | 빈 화면보다 낫다 |
| ✗ 비권장 | 초해상 (GFPGAN 등) | — | 1종 | Apache-2.0 | 8배 근처에서 없는 디테일을 지어냄. 따라 그리는 기준선이라 위험 |

**결정은 숫자 하나로:** F-03 수용 기준의 "서버 렌더 대비 색 차이 ΔE 평균". 1주차 검증 5에서 C의 ΔE와 D의 처리 시간을 같이 잰다.
**룩당 3초 제약은 화면 3에 안 걸린다** — 그건 화면 2 썸네일 10개 얘기. 화면 3은 확정 후 한 장.

**그전까지:** 512 줌으로 만들어 두되, 완성본 소스를 읽는 함수를 한 군데로 모아 나중에 갈아끼운다.

## 5. 쟁점 2 — 쉐딩·하이라이트(3-c)는 렌더에 없다

룩 템플릿은 눈썹·라이너·섀도우·입술·볼터치만 담는다. 쉐딩은 **얼굴형 규칙**에서 오므로 완성 렌더에 없다.
→ 3-c 는 얼굴 아래쪽으로 줌 + **규칙 자리를 점선 테두리로만** 표시.

| 필요한 것 | 상태 |
|---|---|
| 얼굴형 5분류 | 랜드마크 비율 규칙. **학술 정의 있음** (Zhao 2020: 하트·장형·계란·원형·각진, 우리와 이름까지 같음) |
| 쉐딩 원리 | 논문 있음 (2021 CHM: 어두운 색 후퇴, 밝은 색 돌출) |
| **얼굴형별 쉐딩 위치 5종** | **미정.** 업계 교재 3곳 모아 공통분모 → 규칙 담당 B |
| 서버 법선 맵 | 라이선스 위험 → MediaPipe 3D 메시로 대체 검토 |

기술이 어려운 게 아니라 **규칙 콘텐츠가 없는 것**이다.

**⚠️ 특허:** US 10,650,224 B2 (Anastasia, 2036년까지 유효) — 얼굴 측정으로 컨투어 가이드라인, **홍채 지름 척도**, 가이드 준수 점수. 우리 3-c·mm 척도·채점과 겹친다. 발표는 무관, 사업화 시 회피 설계.

## 6. 쟁점 3·4 — 짧게

- **근거 한 줄:** LLM 안 쓴다. 룩 10개 × 5부위 = 50문장 + 얼굴형 5문장 = **55문장을 사람이 미리 쓴다.**

## 7. 서비스 중 실패하면 — 빈 화면은 절대 없다

## 10. 한 문장 결론

**화면 3에 새로 만들 모델은 없다.** 남은 결정은 ① 완성본 원본(C→D→512줌) ② 문장 55개 ③ 쉐딩 규칙 5종이고, 셋 다 막혀도 맨얼굴 사진 + 기본 문장으로 화면은 뜬다. 그래서 다른 화면보다 먼저 만들 수 있다.
