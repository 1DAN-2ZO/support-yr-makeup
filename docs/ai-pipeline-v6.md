# 당화응 AI 파이프라인 — 호출 경로 · 평가 하네스 · 버전 · 서빙 지표

당화응 · 2026-09-18 · 분업안(`work-split-modules-v6.md`)의 보완. 담당은 ⑤ 모델·데이터·평가(하네스·버전·실험 기록)와 ⑥ 앱·콘텐츠·통합(호출 그래프·서빙 지표·로그)으로 나뉜다.

> **한눈에**
분업안에는 "모델을 무엇으로 고르고 어떻게 잴지"가 있다. 여기에는 **모델이 시스템 안에서 어떻게 불리고, 실패하면 어디로 떨어지고, 바뀌면 어떻게 다시 재고, 지금 무엇이 돌고 있는지 어떻게 아는가**를 적는다. 네 가지: ① 호출 그래프 ② 골든 세트 기반 자동 재평가 ③ 버전 규칙 ④ 서빙 지표. 전부 코드보다 규칙과 스크립트다.

## 1. 호출 그래프

### 1-1. 클라이언트 (폰 브라우저, 세션 하나)

```
[카메라 프레임]
   │
   ▼
MediaPipe Face Landmarker (478점, VIDEO 모드, GPU→CPU 폴백)        ── 매 프레임, 목표 30fps
   │  실패(얼굴 없음) → 테두리 숨김, 3초 지속 시 presence=away, 카메라 저속
   ▼
(매 프레임) 비화장 참조(이마) 급변 감지 → occluded        ── 모델 없음, 0바이트 (#148)
   │
   ▼
게이트 evaluateGate(각도·부위 가시·가림·선명·밝기·a*b* 변동·기준과 각도 차·안정 5프레임)
   │  첫 실패 조건 하나 → 문구 한 줄, 버튼 비활성
   ▼ 통과
"확인받기" → CaptureBundle(3~5프레임 + pts + occluded + foreheadL)
   │
   ▼
정합 alignToBaseline(안정점 유사변환) ── 잔차 > 눈 폭 5% → status=check_only(reason=align)
   │
   ▼
샘플링·ΔE (Lab, 이마 L* 보정 + 눈 흰자 a*b* 보정) ── 가림 프레임 제외 → 중앙값, 전부 더러우면 check_only(reason=occluded)
   │                                              ── a*b* 이동 > 임계 → check_only(reason=lighting)
   ▼
채점 scorePart → PartResult(score | check_only + reason, codes, oneLiner, metrics)
   │
   ▼
세션 applyResult → (마지막 부위면) computeSummary → 리뷰
```

| 단계 | 모델/규칙 | 실행 위치 | 시간 예산 | 실패 시 |
| --- | --- | --- | --- | --- |
| 랜드마크 | Face Landmarker (Apache-2.0) | 클라이언트 WASM/WebGL | 33ms/프레임 (30fps) | GPU delegate 실패 → CPU. 모델 로딩 실패 → "다시 시도" 화면 |
| 가림 | 비화장 참조(이마) 급변 — 모델 없음 | 클라이언트 | 프레임 내 | 참조를 못 재면 unknown → 게이트 통과시키되 채점은 중앙값으로 밀어낸다 (#148) |
| 얼굴형 | 규칙 → 분류기(S-2 결과) | 클라이언트, 세션당 1회(촬영 직후) | 100ms | 모델 실패 → 규칙으로 폴백, `FaceShape.method='rule'` 기록 |
| 게이트 | 규칙 | 클라이언트 | 프레임 내 | — |
| 정합·채점 | 규칙(순수 함수) | 클라이언트 | 확인받기 → 결과 500ms | 정합 실패 → check_only(reason). 절대 거짓 점수 없음 |
| 합산 | 규칙 | 클라이언트 | ms | measured=0 → total=null |

### 1-2. 서버 (세션 시작 시 1회, 룩 10개)

```
[정면 사진 1장(WebP 1024)] ──POST /jobs──▶ API(FastAPI)
                                            │ 작업 ID 발급, 사진은 tmpfs
                                            ▼
                                       Redis 큐 (우선순위: 사용자가 고른 룩 > 나머지)
                                            │
                                            ▼
                     GPU 워커 (모델 상주, GPU당 1)
                       ├─ SPIGA 랜드마크·얼굴 구조 1회 (같은 얼굴 룩 10개에 재사용)
                       ├─ 룩 i: Stable-Makeup fp16, 8~10 step (또는 S-1 선정 결과)   ── 룩당 ≤3초
                       ├─ ArcFace 코사인(원본 vs 결과) ── < 임계 → 결과 폐기, status=fallback
                       ├─ 화장 레이어 추출 (부위 마스크 ∩ ΔLab, 알파)
                       └─ finally: 입력·중간 파일 삭제, 로그엔 작업 ID만
                                            │
   클라이언트 ◀──GET /jobs/{id} 폴링(1초)──┘  LookJob{status, resultUrl, layer, identity.cos, ms}
```

| 단계 | 모델 | 시간 예산 | 실패 시 |
| --- | --- | --- | --- |
| 큐 대기 | — | 첫 룩 3초 안에 시작 | 대기 > 20초 → 클라이언트에 "잠시 후" + 진행률 |
| 전이 | Stable-Makeup (Apache-2.0) | 룩당 3초, 10개 30초 | 예외 → 그 룩만 status=error, 나머지 계속. 워커 죽음 → 헬스체크 재시작, 작업 재큐 |
| 닮음 검사 | ArcFace | 50ms | 임계 미달 → fallback(썸네일에 "이 룩은 준비 중") |
| 레이어 추출 | 규칙 | 200ms | 실패 → 결과 이미지만 주고 layer=null (클라이언트는 3점 아핀으로 폴백) |
| 삭제 | 규칙 | 응답 직후 | 삭제 실패는 오류 로그 + 크론이 TTL 2시간으로 정리 |

**원칙**: **룩 하나가 죽어도 나머지는 고를 수 있다** — 실패는 룩 단위이고, 사용자는 `fallback`(닮음 미달)과 `error`(예외)를 똑같이 "준비 중"으로 본다(할 수 있는 게 없어 구분하지 않는다).

**서버 전체가 죽으면 이용 불가다** (2026-09-21 **결정 #8**). 룩 없이 진행하는 대체 흐름은 없다 — 우리 서비스는 "고른 룩을 따라 그리기"라, 룩이 없으면 가르칠 것이 없기 때문이다. 정의서 §39·`client/src/screens/processing.ts` 가 이것을 따른다.

## 2. 평가 하네스 — 한 명령으로 전부 다시 재기

### 2-1. 구조

```
eval/
  golden/                 # 골든 세트 (고정, 버전 있음)
    manifest.json         # 파일 목록 + 라벨 버전 + 사람 단위 분할
    photos/               # 실촬영 30장 (git LFS 또는 저장소 밖 경로만)
    labels/               # 사람 판정 3단계, 얼굴형 2인 라벨, 손 걸림 플래그
  score/    run.mjs       # E-1·E-7: PartResult vs 사람 판정 → 일치율·혼동·반복 편차
  faceshape/ run.py       # E-2·S-2: 규칙 vs 후보 모델 → 정확도·κ
  transfer/  run.py       # E-3·S-1: 시간·ArcFace·부위 ΔE·실패 분류
  region/    run.py       # E-4·S-3: EasyPortrait·Periorbital IoU
  gate/      run.mjs      # E-5: 게이트 첫 실패 분포, 색 변동 폭
  live/      run.mjs      # E-6: 떨림 표준편차, fps
  funnel/    run.mjs      # E-8: Event 로그 → 퍼널 표
  results/               # 실행마다 results/<날짜>_<커밋>_<모델버전>.csv
  report.mjs             # results/*.csv → docs/eval-results-v6.md 자동 생성
  run-all.sh             # 전부 순서대로
```

### 2-2. 규칙

- **골든 세트는 고정한다.** 실촬영 200장 중 30장(사람 6명 × 5장, 조명·각도·"일부러 벗어난 장" 포함)을 `golden/`에 넣고 `manifest.json`에 버전(`golden-v1`)을 적는다. 바꾸면 버전을 올리고 이전 결과와 비교하지 않는다.
- **사람 단위 분할.** 같은 사람 사진이 학습과 검증에 같이 들어가지 않게 `manifest.json`의 `person_id`로 나눈다. 얼굴형 모델·임계 조정 전부 이 분할을 쓴다.
- **채점 코드가 바뀌면 `eval/score/run.mjs`를 돌린다.** 일치율이 떨어지면 PR을 막는다(수동이라도). 이게 회귀 테스트다. 기존 단위 테스트(27+24+26+16)는 그대로 두고, 골든 세트는 "실사진에서 나빠지지 않았나"만 본다.
- **결과 파일 이름에 커밋·모델 버전·골든 버전**이 들어간다. `results/2026-10-02_a1b2c3d_score-v0.3_golden-v1.csv`.
- **결과표는 손으로 안 쓴다.** `report.mjs`가 최신 결과를 `docs/eval-results-v6.md`에 붙인다. 발표 표는 여기서 복사.
- **선정 평가(S-1~S-4)도 같은 스크립트**에 `--candidate` 옵션으로 돌린다. 후보별 CSV가 남고 탈락 후보도 표에 남는다.

### 2-3. 실험 기록 (얼굴형 학습·전이 설정·임계 실험)

| 남기는 것 | 어디 | 형식 |
| --- | --- | --- |
| 설정 | `eval/<모듈>/configs/<이름>.json` | 모델 이름·하이퍼파라미터·데이터 버전·시드 |
| 결과 | `eval/results/` | 위 CSV 규칙 |
| 가중치 | 저장소 밖(`C:\data\danghwaeung\models\<이름>-<버전>`) | 해시를 CSV에 |
| 한 줄 결론 | `docs/eval-results-v6.md` "실험 노트" 절 | 날짜 · 설정 이름 · 바뀐 것 · 결과 · 채택 여부 |

도구는 CSV + JSON이면 충분하다. MLflow·W&B는 6주 안에 배울 비용 대비 효과가 작다. 규칙만 지키면 나중에 옮길 수 있다.

## 3. 버전 규칙 — 지금 무엇이 돌고 있나

| 대상 | 버전 이름 | 어디에 적나 | 올리는 때 |
| --- | --- | --- | --- |
| 채점 규칙·임계값 (`PARAMS` → JSON) | `score-v0.N` | `rules/score.json`의 `version` | 임계 하나라도 바뀔 때 |
| 가이드 템플릿·룩 값 | `look-v0.N` | `rules/looks.json` | 룩 값 확정·수정 |
| 얼굴형 모델 | `faceshape-rule-v1` / `faceshape-model-v0.N` | 모델 파일 이름 + `FaceShape.method` | 재학습 |
| 전이 서버 | `transfer-v0.N` (모델 + 샘플러 + step) | 서버 응답 `LookJob.ver` | 모델·설정 변경 |
| 골든 세트·라벨 | `golden-v1`, `labels-v1` | `eval/golden/manifest.json` | 사진·라벨 추가 |
| 앱 | git 커밋 짧은 해시 | `Event.ver` | 배포마다 |

- `Event.ver`는 `{app, score, look, faceshape, transfer}` 다섯을 한 객체로 찍는다. 로그 한 줄만 보면 그때 무엇이 돌았는지 안다.
- 결과 카드(결과 저장 이미지) 구석에 `score-v0.3`처럼 작게 넣는다. 사용자 실험 때 사진만 봐도 버전을 안다.
- 버전이 올라가면 골든 세트를 다시 돌린다(2-2). "v0.2 → v0.3에서 일치율 61 → 68%"가 발표 그래프가 된다.

## 4. 서빙 지표 — 운영 중에 보는 숫자

전부 `Event` 로그(클라이언트)와 서버 로그에서 `eval/funnel/run.mjs`·서버 집계 스크립트가 뽑는다. 대시보드는 마크다운 표면 된다.

### 4-1. 서버

| 지표 | 출처 | 보는 이유 | 경고선(안) |
| --- | --- | --- | --- |
| 룩 1개 생성 시간 p50 / p95 | `look_job.ms` | 3초 목표 | p95 > 5초 |
| 큐 대기 시간 p95 | 작업 생성 → 시작 | 동시 사용자 체감 | > 10초 |
| 실패율 (error / fallback 분리) | `look_job.error`, `status` | 모델·닮음 검사 문제 구분 | error > 2%, fallback > 15% |
| 닮음 점수 분포 (ArcFace 코사인) | `look_job.identity_cos` | 정체성 유지가 실제 사용자에서 얼마나 | 중앙값 < 0.6 |
| GPU 메모리·워커 재시작 횟수 | 워커 로그 | 상주 안정성 | 재시작 > 1회/일 |
| 삭제 확인 | 크론 로그 | 원칙 준수 | 잔존 파일 > 0 |

### 4-2. 클라이언트

| 지표 | 출처 | 보는 이유 | 경고선(안) |
| --- | --- | --- | --- |
| 랜드마크 프레임 시간 p50 / p95, fps | 내부 상태 → `Event` 샘플링(10초에 1회) | 30fps 유지, 기기별 | p95 > 50ms |
| 얼굴 놓침 비율·시간 | `landmark_lost` | 조명·자세 문제 | 세션의 10% 이상 |
| 게이트 첫 실패 조건 분포 | `gate_fail` | 어느 조건이 사용자를 막나 | 1위 조건 > 50% |
| 채점 시간, 확인만 비율과 이유 분포 | `score` | 거짓 점수 금지 + 너무 자주 못 재면 임계 재검토 | check_only > 30% |
| 정합 잔차 분포 | `score.metrics.alignResidual` | 화장 편향·자세 차 | 중앙값 > 눈 폭 3% |
| 복원 성공률 | `restore` | iOS 리로드 대응 | < 90% |
| 퍼널 (E-8) | `screen_enter/leave`, `session_end` | 이탈 지점 | 리뷰 도달률 첫 측정 후 |

### 4-3. 모델 품질 회귀 (배포 후)

| 지표 | 방법 |
| --- | --- |
| 골든 세트 일치율 | 배포 전 `run-all.sh`, 결과표에 버전별 줄 |
| 사용자 실험 세션의 "확인만" 이유 상위 3개 | 로그 집계 → 임계·게이트 재검토 회의 |
| 전이 닮음 점수 분포 변화 | 주 1회 서버 집계 |

## 5. 데이터 파이프라인 (⑤)

```
촬영 세션 → 원본(저장소 밖) → 익명화 ID(person_id) → 라벨(사람 판정·얼굴형 2인)
   → labels-vN.json (라벨러 ID·시각 포함) → manifest.json 사람 단위 분할
   → golden-vN (30장 고정) / train-vN (나머지)
   → 학습 configs/*.json + 시드 → 모델 파일 + 해시 → eval/run → results CSV → report → docs
```

- 원본 사진은 저장소에 넣지 않는다(동의서 범위·용량). 저장소에는 `manifest.json`(경로·해시·라이선스·동의 범위)만.
- 라벨은 라벨러별로 따로 저장하고 합의본을 따로 만든다. 일치율(κ)은 합의 전 파일에서 계산.
- 학습 재현: `python train.py --config configs/faceshape-b-v0.1.json` 한 줄이면 같은 결과가 나와야 한다(시드 고정, 데이터 버전 명시).

## 7. 발표에서 이 문서가 되는 슬라이드

1. **시스템 그림 한 장**: 1-1·1-2 호출 그래프를 합친 것. "폰에서 도는 것 / 서버에서 도는 것 / 실패하면 어디로"가 한눈에.
2. **평가 하네스 한 장**: `eval/` 구조 + "코드가 바뀌면 골든 30장을 다시 돌린다" + 버전별 일치율 꺾은선(score-v0.1 → v0.3).
3. **모델 선정 표 한 장**: S-1·S-2 후보별 CSV에서 나온 표, 탈락 후보 포함.
4. **운영 지표 한 장**: 사용자 실험 10명의 퍼널 + 서버 p95 + 확인만 이유 분포.

이 네 장이 있으면 "모델 API를 붙였다"가 "AI 시스템을 설계하고, 재고, 운영했다"로 읽힌다.
