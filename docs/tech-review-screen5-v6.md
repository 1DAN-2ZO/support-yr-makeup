# 당화응 — 화면 5 기술 검토 (v6, 2026-09-17 1차)

> 2026-09-16~17 · 화면 5(부위 결과, F-08 인식 · F-09 채점)를 실제로 구현할 때 **필요한 기술이 무엇이고, 되는지 안 되는지, 안 되면 대안이 무엇인지**를 적은 문서. 근거는 `feature-spec-v6.md` F-08·F-09, `impl-screen1-5-definition-v6.md` 3-5·5-1~5b-2, 브랜치 `poc/screen5`(검증 27개), `poc/full`(2026-09-17 PC 웹캠 실기기 테스트). 데이터 항목 번호(A-2, B-1 …)는 `data-plan-v6.md`의 것을 그대로 쓴다.
>
> **전제 (데이터 계획 4차와 같음)**: 채점의 정답은 우리가 그 사람 얼굴에 맞춰 그려 주는 **개인화 가이드 자체**다. 그래서 정답 데이터셋이 필요 없고, 화장 영역 분할 모델은 MVP에서 뺀다. 채점은 맨얼굴 대비 색 차이(ΔE) + 랜드마크 468점으로 잡은 부위 영역으로 한다.
>
> **쉽게 말하면** 화면 5는 "네가 그린 화장이 우리가 그려 준 테두리랑 얼마나 맞는지" 점수를 주는 화면이다. 그 계산에 필요한 기술은 **이미 브라우저에서 돌아가고 자동 검증 27개를 통과했다.** 기술이 없어서 막히는 곳은 없다. 막히는 곳은 두 가지 — **진짜 사람이 거울에 다녀와서 찍은 두 장으로는 한 번도 돌려 보지 않았다**는 것과, **POC 6개가 따로 놀아 하나로 합쳐야 한다**는 것. 둘 다 모델이 아니라 순서의 문제다.
>
> 판정: **가능** = 돌아가고 검증됨 · **부분** = 돌아가지만 구멍 있음 · **미구현** = 아직 없음, 대안 있음 · **보류** = 4차 결정으로 MVP 제외 · **안 됨** = 현재 설계로는 불가, 정의를 바꿔야 함.

## 1. 화면 5가 하는 일

> **쉽게 말하면** 확인받기를 누르면 그 순간 사진을 찍고, 처음 찍어 둔 맨얼굴과 비교해서 "어디 색이 얼마나 변했나"를 잰다. 변한 곳이 우리가 그려 준 테두리 안에 잘 들어가 있으면 점수가 높고, 밖으로 나갔거나 비어 있으면 낮다. 숫자(mm·각도·%)는 화면에 안 보이고 점수와 한 줄 평만 보인다.

```
두 장 입력 (촬영 1 맨얼굴, 확인받기 프레임)
→ 안정점 유사변환으로 맨얼굴 랜드마크를 현재 프레임에 정렬
→ 같은 격자로 두 장에서 Lab 샘플 → 이마 L* 비율로 L 보정
→ ΔE → 겹침·번짐·두께·꼬리·좌우 차 → 점수 → 진단 코드 → 한 줄 평
```

**정합이 핵심이다.** 화장을 하면 그 부위의 랜드마크가 화장을 따라 밀린다 — 입술을 크게 그리면 입술 점이 커진 입술로 이동한다. 그러면 "가이드대로 그렸다"고 잘못 나온다. 그래서 화장 부위 점은 쓰지 않고, **안정점만으로 유사변환(크기·회전·이동)을 구해 맨얼굴 랜드마크를 현재 프레임으로 옮긴다.** 편향량(재검출값 vs 정렬값)은 내부 지표에 px로 남는다(A-6). 문서에 없던 문제를 POC가 찾아 해결한 것이다.

| 부위 | 측정하는 것 | 출력 |
|---|---|---|
| 아이라이너 | 밴드 안 감지율, 밖 번짐, 두께, 꼬리 길이·편차 방향, 좌우 차(맨얼굴 비대칭 차감) | 점수 + `LINER_WING_HIGH_R` 등 |
| 눈썹 | 24×9 매개변수 격자 겹침, 꼬리 커버, 밖 번짐 | 점수 + 코드 |
| 입술 | 윤곽 60점 × 오프셋, 위·아래 경계 밖 | 점수 + 코드 |
| 섀도우 · 볼터치 | 유무, 세션 내 지수, 좌우 지수, 목표 밴드, 방향(섀도우) | 점수 또는 "확인만" |
| 쉐딩 · 하이라이트 | 좌우 지수 차만 | 항상 "확인만" |

## 4. 안 되는 것과 대안

### ① 조명 정규화 — 화이트밸런스

> **쉽게 말하면** 폰 카메라는 조명이 바뀌면 색을 알아서 다시 맞춘다(화이트밸런스). 브라우저에선 그걸 못 막는다. 거울 갔다 오는 사이 카메라가 색을 바꿔 버리면, 화장을 안 한 곳도 "색이 변했다"고 잡힌다. 지금은 밝기만 보정하고 색은 안 보정한다.

ΔE는 L·a·b 셋을 다 쓴다. 보정은 **이마 L\* 스케일 하나**뿐이다. `Baseline.lighting.scleraWhite`(눈 흰자 참조)가 문서에 선언돼 있지만 **저장소 어디에서도 쓰이지 않는다.**

| | 대안 | 비용 · 효과 | 상태 |
|---|---|---|---|
| (a) | 선언만 된 눈 흰자 참조를 실제로 구현해 a\*·b\*까지 보정 | 촬영 1에 이미 눈 흰자가 있음. 구현 소 | 미정 |
| (b) | 부위 색을 **인접 비화장 피부 대비**로 재정의 — 같은 프레임 안 차이라 WB가 상쇄 | 강도 부위(5b-2)는 이미 이 방식. 형태 부위만 맞추면 통일됨. 점수식 그대로, `d` 정의만 교체. 임계값 전부 재보정, 노이즈 √2배, 부위별 참조 위치 규칙 필요 | 미정 |
| (c) | a\*·b\* 이동량이 임계를 넘으면 "확인만" | 가장 싸다. 거짓 점수 금지와 일치 | 미정 |
| 기기 | `MediaStreamTrack.getCapabilities()`로 `whiteBalanceMode: manual` 지원 감지 → 되는 기기는 잠금 | Android Chrome 일부만. **iOS Safari 미지원** | 미정 |

```
지금:  d = ΔE( 부위_now , 부위_base )
(b):   d = | (부위 − 인접피부)_now  −  (부위 − 인접피부)_base |
```

**A-3 ★(조명 변화 세트)에서 이마 밝기뿐 아니라 a\*·b\* 변동을 같이 재야 이 위험의 크기가 보인다.** 1주차 검증 2번 항목은 밝기만 재게 돼 있다.

### ② 손 마스크

> **쉽게 말하면** 손이나 브러시가 얼굴 앞에 있으면 그 자리 색이 확 달라져서 "화장을 진하게 했다"로 잡힌다. 문서는 "손 부분 픽셀을 빼라"고 했는데, 손 인식 모델은 손가락 관절 점 21개를 줄 뿐 "여기가 손이다"라는 픽셀 영역을 주지 않는다.

문서는 손을 두 정밀도로 쓴다: 품질 게이트(화면 1·4)는 **박스**, 채점(화면 5)은 **픽셀 마스크**. 마스크를 만들려면 21점의 볼록껍질 근사가 필요한데 접힌 손·브러시에서 어긋난다.

**권장 — 마스크를 만들지 않는다.** 확인받기는 게이트가 손을 막은 상태에서만 눌리고 직후 3~5프레임을 찍는다. 유일한 구멍은 **버튼을 누르는 손 자체**가 첫 프레임에 걸치는 경우 → 손 박스가 부위 크롭과 겹치는 **프레임을 평균에서 버린다.** 전부 더러우면 "확인만". F-08의 "손 마스크 제외"를 "손이 걸린 프레임 제외"로 바꾸면 슬롯 하나가 사라진다. 손 검출은 3~5프레임에 1회면 충분(문서 3-5).

### ③ 화장 영역 분할 → §6 (보류)

### ④ "이탈 최대 mm"

> **쉽게 말하면** 가이드에서 5mm 벗어나게 그리면 지금 방식은 "벗어났다"는 건 알지만 "얼마나"는 모른다. 샘플을 가이드 주변 ±3mm 안에서만 뽑기 때문이다.

문서 5-3은 *감지 골격선에서 가이드까지 최대 거리*를 요구한다. POC는 `wingDevMm`(±3mm 안 중심 오프셋) + `gapRatio` + `present`로 우회했고, 완전히 벗어나면 "감지되지 않음 → 확인만"으로 떨어진다.

**대안:** 격자를 ±6~8mm로 넓히면 실사용 범위는 거의 덮는다. 그 밖은 "확인만" — 거짓 점수 금지와 일치. 화면에 숫자를 쓰지 않으므로 **방향(위·아래·밖)과 구간**만 있으면 한 줄 평이 나온다. 5-3의 정의를 그 수준으로 낮춘다.

### ⑤ 표정 변화

유사변환은 크기·회전·이동만 잡는다. 웃음·눈 크게 뜸은 못 잡는다(랜드마크 편향과 별개).
**대안:** 게이트에 "기준과 같은 표정" 조건 — EAR(눈 뜸 비율)·MAR(입 벌림 비율)이 촬영 1과 임계 이내일 때만 확인받기 활성. §3의 각도 차 게이트는 넣었고 표정은 다음 차례.

### ⑥ 픽셀 단위 ΔE 성능

ΔE를 2D 마스크로 가면 JS가 느리다(1080×1440 × 5프레임).
**대안:** 부위 크롭 안에서만 계산하고 WebGL 프래그먼트 셰이더로, 또는 OpenCV.js(WASM) 모폴로지.

## 6. 분할 모델 — 왜 뺐나, 꺼내게 되면 빠른 길

> **쉽게 말하면** "화장 발린 곳을 오려내는 모델"을 직접 가르치려면 가짜 사진 수천 장으로 배우게 하고 진짜 사진 수백 장에 정답을 손으로 칠해야 한다. 5주에 한 사람이 하기엔 무겁고, 가짜로 배운 게 진짜에서 안 될 위험이 크다. 4차에서 뺐고, 이 절은 "나중에 꺼내게 되면 이렇게"다.

**빼는 게 맞는 이유** (B-3 보류 판단의 기술 근거):

1. **합성→실제 도메인 갭.** 절차적으로 그린 라이너는 실제 젤 라이너의 번짐·반사·피부 결과 다르다. 실패를 4주차에 알게 된다.
2. **라벨 200~500장이 병목.** 픽셀 마스크는 장당 5~15분, 300장이면 25~75시간.
3. **대상이 얇다.** 아이라이너 1~2mm는 512px 얼굴에서 2~4px. 눈썹은 털과 펜슬이 섞여 정답이 애매하다.
4. **성공 기준이 없었다.** ΔE 임계만 썼을 때보다 얼마나 나아야 도입하는지가 없다.

**꺼내는 조건** (B-3과 같음): A-2 시험에서 부위별 ΔE 채점 일치율이 목표에 못 미칠 때.

**꺼내게 되면 — 시간순**

| 단계 | 방법 | 시간 |
|---|---|---|
| 0 | A-2 200장을 ΔE 임계만으로 돌려 **어디서 틀리는지** 본다. 그림자·경계 잡음이 아니면 여기서 끝 | 하루 |
| 1 | **학습 없이 후처리.** ΔE 임계 → 모폴로지 → 가이드 밴드와 겹치는 연결 성분만 유지 | 반나절 |
| 2 | **학습 없이 얼굴 파싱 ∩ ΔE.** BiSeNet 부위 마스크와 교집합 — 부위 밖 그림자 오탐이 잘린다 | 하루 |
| 3 | **학습하되 라벨 0.** FFHQ-Makeup 108,000장 쌍 차이가 곧 정답. LR-ASPP MobileNetV3 파인튜닝, 단일 GPU 2~3시간 | 2~3일 |
| 4 | 문제를 좁힌다 — ΔE 후보 영역 안 패치만 "화장 / 잡음" 이진 분류 | — |
| 5 | 제로샷 — MobileSAM에 ΔE 후보 중심을 프롬프트로. 서버에서 정지 사진 한 장 | 하루 |

권장 0 → 1 → 2, 이틀. 절차적 합성 생성기(`poc/synth`)는 B-3 재료로 보존하되 새로 짜지 않는다.

**짚을 것:** 화면 5 채점은 정지 사진 한 장이지 실시간이 아니다. 서버에서 돌리면 온디바이스·INT8·WASM 변환 위험이 통째로 사라진다. 다만 문서 원칙이 "서버는 얹어보기·쉐딩 위치에만"이라 확인받기 프레임 전송은 **원칙 확장**이고, 팀이 정할 일이다.

## 8. 실제 구현에서 생길 문제 — POC가 전제한 것이 깨지는 곳

> **쉽게 말하면** POC는 "사진 한 장, 같은 조명, 사용자 한 명"을 가정한다. 진짜 앱은 폰 브라우저에서, 거울 갔다 오는 사이 조명이 바뀌고, 탭이 닫히고, 여러 명이 동시에 쓴다. 그때 무엇이 깨지고 어떻게 막는지.

### A. 모바일 브라우저 카메라

| 문제 | 해결 | 기술 |
|---|---|---|
| 노출·화이트밸런스 고정 불가 (§4-①) | 되는 기기는 잠그고, 아니면 보정·게이트 | `getCapabilities()` → `applyConstraints()`. iOS Safari 미지원 |
| Face + Hand Landmarker 동시 30fps가 저가 기기에서 안 나옴 | 손은 3~5프레임에 1회. 랜드마크 입력은 다운스케일, 크롭만 원본 | MediaPipe `delegate: "GPU"`, `runningMode: VIDEO`, `OffscreenCanvas` |
| iOS Safari: 백그라운드 전환 시 스트림 끊김, WebGL 컨텍스트 손실, 방향 잠금 없음 | 세션 복원(F-07)이 여기서 실제로 필요. 방향은 잠금 대신 안내 + 감지 | `visibilitychange`, `webglcontextlost`, `matchMedia('(orientation)')` |
| 폰을 두고 거울로 가면 화면이 꺼짐 | 화면 유지 요청 | Screen Wake Lock API (Android Chrome, iOS 16.4+) |

### B. 세션·데이터

| 문제 | 해결 | 기술 |
|---|---|---|
| 탭 종료·리로드로 세션 유실. 사진·Lab 맵은 localStorage 5MB에 안 들어감 | 기준 데이터·부위 상태·사진 Blob을 IndexedDB에, 상태가 바뀔 때마다 저장 | IndexedDB (`idb`), Blob. `beforeunload`는 믿지 않는다 |
| "끝내기" 삭제 보장 — 그냥 탭을 닫으면 서버·기기에 남음 | 서버 세션 TTL 자동 만료. 재방문 시 만료 세션 정리 | Redis TTL + 파일 삭제 크론 |
| 정면 3장 업로드가 모바일 망에서 느림 | 전송 전 리사이즈·재인코딩 | `canvas.toBlob('image/webp', 0.85)`, 긴 변 1024 |
| 모바일 Safari 메모리 한계 — 탭이 리로드됨 | 원본은 기준 생성 후 즉시 폐기(문서 원칙). Lab 맵은 부위 크롭만 | `ImageBitmap.close()` |

### C. 서버·생성 모델

| 문제 | 해결 | 기술 |
|---|---|---|
| 룩 10개 × 3초 = 30초, GPU 1장, 동시 사용자 → 큐 대기 | 고른 룩부터 생성(순서 우선). 저해상 미리보기 먼저, 나머지는 백그라운드 | FastAPI + Redis + RQ, 작업 ID 폴링(문서 1-5), 우선순위 큐 |
| 화장 전이가 얼굴을 바꿈 (정체성 손실) | 유사도 임계 미달 시 폴백(문서 리스크) | InsightFace 임베딩 코사인 (C-1) |
| 화장 레이어 → 메시 워핑 30fps (F-03) | 메시 밖(머리카락·입안)은 처리하지 않음을 명시 | WebGL 텍스처 매핑, `FACE_LANDMARKS_TESSELATION` |
| 서버 즉시 삭제 검증 — 로그·백업·임시 디렉터리에 남으면 원칙 위반 | 삭제를 운영 규칙으로: 업로드는 tmpfs, 응답 후 `finally`에서 삭제, 로그에 파일명 미기록 | nginx `client_body_temp_path` tmpfs |

### D. 로딩·배포

| 문제 | 해결 | 기술 |
|---|---|---|
| MediaPipe WASM + 모델 ~10MB 첫 로딩, CDN 의존 | 자체 호스팅 + 캐시. 로딩 실패를 사용자에게 알린다 | Service Worker + Cache API, `float16` 모델(~4MB) |
| 카메라는 HTTPS 필수 — localhost 밖에서 테스트가 안 됨 | 개발 중에도 TLS. 팀원 폰 실기기 테스트에 필수 | mkcert(로컬). 배포는 정적 호스팅 + 자체 GPU API |

### E. 통합 — 실제 구현의 첫 작업

| 문제 | 해결 | 기술 |
|---|---|---|
| **POC 6개가 따로 논다.** 부위 id·랜드마크 인덱스·가이드 기하가 브랜치마다 복제 — `poc/screen5`의 `guides.js`·`landmarks.js`가 "화면 4 POC와 같은" 복사본 | 공통 모듈 하나로 모으고 테스트도 합친다. 화면별 코드는 그 위에 얇게 | `src/core/`(순수 함수) + `src/screens/`, `tests-cases.js` 패턴 유지, Vite |
| `189e42c` mm→비율 결정이 POC에 미반영 (`poc/screen3` `mmPerPx`, 밴드 폭 mm, 테스트 상수) | 통합할 때 한 번에. 척도 함수 하나만 두고 전부 거치게 | 눈 폭 27mm·입술 폭 50mm·얼굴 폭 140mm 환산은 표시용에만 |
| 임계값 전부 가정값 (§9) | A-2를 먼저 만들고, 임계값은 `PARAMS` 한 곳에서 데이터로 | 코드 상수 → JSON 규칙 파일(문서의 "규칙 DB") |

## 10. 1주차에 시작할 것 (★)

1. **A-2 실촬영 쌍.** 거울에 다녀와서 찍은 전/후 두 장 × 3명부터. §9의 값 전부와 §7의 게이트 문턱이 여기 걸려 있다. 데이터 계획대로 **일부러 벗어나게 그린 장**을 포함 — 틀린 걸 틀렸다고 하는지.
2. **A-3 조명 세트에서 a\*·b\* 변동을 같이 잰다.** 밝기만 재면 §4-①의 위험이 안 보인다.
3. **HTTPS 실기기 환경.** §7의 문제들은 데스크톱 크롬에서 하나도 보이지 않았다. iOS와 저가 Android 각 1대.
4. **카메라 제어 기능 감지 표.** 어떤 기기가 WB 잠금을 지원하는지.

통합(§8-E)은 그다음이다. 화면부터 붙이면 브랜치 6개의 복제본이 그대로 제품에 들어간다.
