# 1-2 공부 기록 — 폰 실기기 4장 자동 촬영 실측 (2026-09-21)

> 이슈 #10. 브랜치 `capture`. **커밋 없이 검증만**. 이 문서도 미커밋.
> 형식은 1-1 과 같다: 목표 → 기술(최선·차선·왜) → 데이터 → 스킬 → 방법 → 결과 → 문제 → 1-3 조건.

## 1. 1-2 가 하는 일 한 줄

1-1 의 규칙(`shotGate`)을 **진짜 폰 카메라 프레임**에 붙여 iPhone 1대·Android 1대에서 4장을 자동으로 찍고, 시간·장별 재촬영·45° 판정이 걸린 각도를 잰다. 통과 기준은 F-01 의 "4장 60초 이내".

## 2. 들어가는 기술 — 최선·차선·왜

| 요소 | 최선 (쓴 것) | 차선 | 왜 최선인가 |
|---|---|---|---|
| 폰에서 카메라 열기 | vite dev 서버 + **https(자체 서명, openssl)** | mkcert(신뢰된 로컬 인증서) / ngrok 같은 터널 | 브라우저는 https 또는 localhost 에서만 `getUserMedia` 를 허용. mkcert 가 이 PC 에 없어 openssl 로 만들었다. 폰에서 경고 1번 넘기면 되고 외부 서비스에 얼굴 영상이 안 나간다. mkcert 는 경고가 없어 팀 공용으로는 더 낫다 (`docs/dev-stack-v6.md`) |

| 선명도 | 얼굴 상자를 **96px 폭**으로 줄여 라플라시안 분산 (POC `sharpnessOf` 와 같은 스케일) | 원본 해상도에서 계산 | 1-1 문제 3: 값이 해상도에 따라 달라지므로 게이트 임계 `sharpMin=30` 은 이 스케일 기준. 폰에서 실제 값을 봐야 30 이 맞는지 안다 |
| 밝기 | 프레임을 320px 로 줄여 `foreheadLab()` (color.ts, 이마 다각형 평균) | 랜드마크 10 주변 8×8 (POC) | 1-6 에서 만든 진짜 코드를 그대로 씀. 다각형 평균이라 한 점 노이즈에 덜 흔들림 |

## 4. 공부할 스킬

| 스킬 | 왜 | 어디서 |
|---|---|---|
| `getUserMedia` 제약(`facingMode`, `ideal` 해상도)과 https 요구 | 폰 카메라가 왜 http 로는 안 열리는지, 요청 해상도와 실제 해상도가 왜 다른지 | `capture-probe.ts start()` |
| MediaPipe VIDEO 모드 (`detectForVideo(video, timestamp)`) | 타임스탬프가 단조 증가해야 함, IMAGE 모드와 차이 | 같은 파일 `frame()` |
| `requestAnimationFrame` 루프에서 측정 → 게이트 → 촬영 | 화면 갱신 주기와 검출 시간의 관계(프레임당 ms) | `frame()` |
| 캔버스 `drawImage` 축소 + `getImageData` | 선명도·밝기를 작은 캔버스에서 계산해 프레임 비용을 줄이는 법 | `sharpnessOf`, `foreheadLOf` |
| 회전 행렬의 row-major / column-major | 같은 16개 숫자를 어떻게 읽느냐에 따라 yaw 가 다른 축으로 나온다 (1-1 문제 1) | `yawFromMatrix` |
| vite `server.https` + `configureServer` 미들웨어 | 로컬 https 와 dev 전용 수신 엔드포인트 | `vite.config.ts` |

## 5. 검증 방법

1. PC: `cd client && npx vite --host` → `https://<PC IP>:5173/capture-probe.html` (인증서 경고 → 계속)
2. 폰: **시작** → 카메라 허용 → 화면 안내대로 정면(눈뜸) → 정면(눈감음) → 왼쪽 45° → 오른쪽 45°. 5프레임 안정되면 자동으로 찍힘
3. 틀리게 찍혔으면 **마지막 장 다시** (재촬영 횟수로 집계)
4. **끝 → PC 로 보내기** → `client/.probe/probe-*.json` 생김. 화면에 1-2 표 한 줄도 나옴
5. 기기 2대(iOS·Android) 이상, 가능하면 사람 2명

기록되는 것: 4장 총 시간, 장별 통과까지 초, 장별로 **어떤 조건에서 몇 프레임 막혔나**, 촬영 순간의 yaw(랜드마크·행렬 2해석)·눈·얼굴비·선명도·이마 L*, 재촬영 횟수, 프레임당 ms, 모델 로딩 ms, 1-3 잠금 표 한 줄, 1-5 이벤트 로그.

## 7. 발견한 문제

| # | 문제 | 근거 | 어떻게 할까 |
|---|---|---|---|
| 1 | **행렬 yaw 는 column-major 로 읽어야 랜드마크와 부호가 맞는다** (1-1 문제 1 종결) | 좌 45°: 랜드마크 −52.2, col −34.7, row +33.5. 우 45°: 42.5 / +32.2 / −32.6 | `anglesFromMatrix` 는 column-major(`data[c*4+r]`) 로 고친다. 단 크기가 랜드마크 값의 약 0.7배(33~35 vs 42~52) — 행렬이 실제 회전각에 가깝고 랜드마크 식은 과장. 게이트는 랜드마크 값 기준으로 이미 맞춰져 있으니 유지, 행렬을 쓰려면 45° 범위를 15~40 으로 다시 잡아야 함 |
| 2 | 오른쪽 45° 가 18초 — **밝기 조건이 104프레임 막음** (1-1 문제 2 가 폰에서 재현) | 기준 L* 53.7 → 우 45° 로 돌리는 동안 |차| > 12. 찍힌 순간엔 44.7(차 9.0). 왼쪽은 50.8(차 2.9)로 안 막힘 | 1-1 제안 그대로: 밝기 조건은 정면 2장에만, 45° 장은 허용폭 18~20. 1-4 조명 3종 실측으로 확정 |
| 3 | 오른쪽 45° 에서 **얼굴 검출이 52프레임 끊김** | 720 폭 세로 프레임에서 고개를 돌리면 얼굴이 가장자리로 빠짐 (얼굴비 0.58 → 0.47) | 안내 문구에 "얼굴을 가운데 두고 고개만" 추가. 검출이 끊기면 안정 카운트가 0 으로 돌아가 시간이 더 든다 |
| 4 | 45° 에서 **먼 쪽 눈 blink 가 0.45** 까지 오른다 (임계 0.5 바로 아래) → 눈 9프레임 막힘 | 우 45° blinkB 0.45, EAR B 0.11(임계 0.12 아래!) | 45° 장의 눈 조건은 "두 눈 다 감김" 일 때만 막거나, 가까운 쪽 눈만 본다. EAR 차선책은 45° 에서 못 씀(1-1 문제 4 확인) |
| 5 | **눈 감음 판정 blink 값이 사진(0.73~0.86)보다 낮다** (0.65~0.68) | 폰 실시간 프레임, 눈을 꽉 안 감음 | 0.5 임계로 통과는 됨. 여유가 0.15 뿐이라 0.4 로 내리는 건 4번 문제와 충돌 → 유지 |
| 6 | 선명도 값이 236~877 로 **`sharpMin=30` 보다 10배 이상** 크다 | 96px 스케일, 720×1280 프레임 | 30 은 사실상 아무것도 안 막는다. 흔들린 프레임을 일부러 찍어 값을 보고(다음 폰 측정 때 "흔들기" 버튼) 임계를 100~150 근처로 올릴지 결정 |
| 7 | 정면 눈감음 장의 이마 L* 가 첫 장보다 7.4 낮다 (53.7 → 46.3) | 잠금(WB·노출 manual) 성공했는데도 변함. 눈 감으며 고개가 살짝 숙여져(pitch −7.5) 이마 각도가 바뀐 듯 | 1-4 에서 3명 × 조명 3종으로 폭을 재고 brightTol 을 정한다. 지금은 12 안 |
| 8 | 프로브 버그: 끝 버튼이 눌릴 때마다 전송돼 같은 결과가 20개 저장, 시작이 두 번 눌려 consent 2번 | 이벤트 로그 | 고침 (버튼 즉시 비활성). "4장째까지 시간" 을 따로 기록하도록 추가 |
| 9 | Android Chrome UA 가 기종을 숨긴다 ("Android 10; K") | UA 축소 정책 | 1-3 표에는 기종을 손으로 적는다. 필요하면 `navigator.userAgentData.getHighEntropyValues` |
