# 화면 1·2 기술 정의 — 실제 구현 기준 (2026-09-16)

> POC(`poc/look-tryon/`) 검증 결과를 바탕으로, 프로덕션 구현 관점에서 다시 정리. POC 단계에서는 문제 없던 것도 실제 서비스(다수 동시 사용자, 다양한 기기, 개인정보 처리)에서는 별도 검토가 필요한 항목이 있음.

---

## 화면 1 — 얼굴 촬영

### 1) 필요한 기술 정의

| 영역 | 기술 | 검증 상태 |
|---|---|---|
| 클라이언트 랜드마크 | MediaPipe FaceLandmarker (468점+홍채, VIDEO 모드, WASM+GPU delegate) | POC 검증(`poc/app.js`) |
| 손 검출 | MediaPipe HandLandmarker | 스펙만, 미구현 |
| 자세 추정 | FaceLandmarker `outputFacialTransformationMatrixes` | 라이브러리 기능 확인, 임계값 미검증 |
| 눈 상태(EAR)·밝기(Lab)·선명도(라플라시안) | 자체 구현 | POC 검증 |
| 서버: 세션 에셋 생성 (`POST /jobs type:session_assets`) | 큐 기반 비동기 작업 서버 | **미구현** — Gradio 데모는 단일 요청·단일 프로세스라 프로덕션 큐 아님 |
| 서버: `normalMap` 생성 (쉐딩·하이라이트 가이드용) | 단안(monocular) 얼굴 노멀/뎁스 추정 모델 | **이번 세션에 전혀 검증 안 함** — 화면3 GuideSet의 쉐딩·하이라이트 source가 `normal_map`인데, 이걸 만드는 구체 모델을 아직 하나도 안 정함 |
| 사진 즉시 삭제 정책 | 스토리지 TTL/삭제 파이프라인 (개인정보보호법 대응) | **미구현** |
| HTTPS·카메라 권한 | 프로덕션 도메인 인증서 | 인프라 항목, 기술 검증 불필요 |

### 2) 불가능/애매한 기술
- **모바일 브라우저 카메라 제약**: iOS Safari는 `exposureMode`/`whiteBalanceMode` constraint를 아예 지원 안 함(정의서에 이미 "불가"로 명시된 부분과 동일 결론, 실기기 미검증).
- **iOS WebGL GPU delegate 안정성**: iOS Safari의 WebGL 컨텍스트 제약(백그라운드 전환 시 컨텍스트 loss 등)으로 FaceLandmarker GPU delegate가 불안정할 수 있음 — CPU delegate 폴백은 되지만 저사양 기기에서 실시간 468점 검출 프레임레이트가 애매함. **실기기 테스트 매트릭스 없음.**
- **각도 게이트(±5°/±45°) 재현성**: POC는 데스크톱 웹캠·정면광 1개 환경에서만 확인. 실기기·다양한 조명에서 이 허용오차가 재현되는지 미검증.
- **`normalMap` 생성 기술 자체가 미정**: 화면3에서 "얼굴형별 위치·방향"의 소스로 쓰이는데, 이게 실제 3D 노멀맵(딥러닝 단안 깊이/노멀 추정)인지 랜드마크 기반 근사인지 정의서 수준에서만 존재하고 구현 기술이 아직 없음. **가장 큰 미확인 리스크.**
- **동시 다수 사용자의 session_assets 큐 처리량**: 룩 10개에 대한 diffusion(화면2 lookLayers)까지 이 단계에서 만든다면, "왕복 목표 3초"가 룩 1개 기준인지 10개 전체 기준인지 스펙 자체가 모호함.

### 3) 대안
- iOS GPU delegate 불안정 → CPU delegate 강제 + 프레임 스킵(격프레임 검출, 예: 15fps로 다운) + 저해상도 입력으로 성능 확보. 실기기 QA 매트릭스(iOS Safari 최신 2버전, 안드로이드 중저가 기기 2~3종) 구성 필요.
- 각도 게이트 재현성 → 실측 실험으로 임계값 확정(정의서 "가정값" 표에 화면1 각도 게이트도 추가), 필요시 게이트를 완화(±5→±8 등)하고 서버 측에서 2차 보정.
- `normalMap` 미정 → 두 가지 현실적 경로:
  1. **랜드마크 기반 근사(권장, 빠름)**: 쉐딩·하이라이트는 어차피 "얼굴형별 규칙"(F-02, oval/round/square/heart/oblong)으로 위치·방향을 결정하므로, 실제 3D 노멀맵 없이 **랜드마크로 계산한 광대 최고점·턱선 방향 벡터**만으로 대체 가능. 정의서 3-2도 "없으면 랜드마크 근사"로 이미 폴백을 명시해 둠 — 이 폴백을 기본값으로 채택하고 정식 노멀맵은 다음 라운드로 미루는 걸 제안.
  2. **딥러닝 노멀 추정(정밀하지만 별도 검증 세션 필요)**: 단안 얼굴 노멀 추정 공개 모델(예: 3DDFA 계열, DECA 등 3D 얼굴 재구성 모델)을 추가로 벤치마크해야 함 — 이번 세션 범위 밖, 별도 라운드로 분리 권장.
- session_assets 큐 처리량 → 룩 10개를 세션 생성 시점에 전부 생성하지 않고, **선택 화면에서 lazy 생성**(사용자가 스크롤해서 보이는 룩부터 순차 생성 + 상위 몇 개만 프리페치)으로 전환. 큐(Redis/SQS 등) + GPU 워커 풀 오토스케일 아키텍처 필요.
- 사진 즉시 삭제 → 스토리지 lifecycle rule(예: S3 lifecycle 1일 삭제) + 처리 완료 직후 명시적 삭제 API 호출 이중화.

### 4) 라이선스 대안
전부 문제 없음. MediaPipe FaceLandmarker/HandLandmarker = **Apache-2.0**(Google 공식, 상업 무료). 자체 구현 로직(EAR·라플라시안·Lab)은 라이선스 대상 아님. `normalMap`을 딥러닝 모델로 갈 경우, 후보 모델(3DDFA/DECA 등)의 라이선스를 그때 별도 확인 필요(3DDFA는 MIT 계열이 일반적이나 버전별 확인 필요 — 지금은 확정 못 함, 별도 검증 세션 때 체크).

## 화면 2 — 룩 얹어보기

### 1) 필요한 기술 정의

| 영역 | 기술 | 검증 상태 |
|---|---|---|
| 서버 diffusion 화장 전이 | Stable-Makeup(SD1.5+ControlNet), fp16+10step | POC 실측 검증(3.15초·5.3GB, RTX 3060) |
| 얼굴 구조 조건(ControlNet 입력) | SPIGA + FaceLib | POC 검증 |
| 실시간 프리뷰 워핑 | 부위별 폴리곤 팬 삼각분할 + 3점 아핀(자체 구현) | POC 검증(데스크톱 1개 환경) |
| **프로덕션 추론 서버** | GPU 추론 API 서버(큐+오토스케일) | **미구현** — Gradio는 프로토타입 통신 확인용으로만 씀 |
| 동시 다수 사용자 처리 | GPU 인스턴스 풀, 요청 큐잉 | **미구현·미설계** |
| 룩 템플릿 콘텐츠(참조 이미지 10개, 제품 목록) | 기획/디자인 산출물 | 기술 아님, 별도 트랙 |
| 세션 이미지 삭제 정책 | 화면1과 동일 | 미구현 |

### 2) 불가능/애매한 기술
- **Gradio 프로덕션 사용 불가**: 데모 도구라 동시접속·인증·큐잉·헬스체크 등 프로덕션 요건 없음. 이번 POC 방식 그대로는 서비스에 못 씀 — 이건 "애매"가 아니라 확정적으로 교체 필요.
- **fullRender 픽셀 직접 이식(deltaLab 아님)**: 피부톤·조명 불일치 시 경계 티남 — 다수 사용자·다양한 기기 카메라에서 품질 편차가 클 가능성. POC는 개발자 본인 얼굴 1개, 참조 사진 몇 개로만 확인함 — **다양한 피부톤·조명에서 검증 안 됨.**
- **동시 GPU 처리량과 비용**: RTX 3060 1장 기준 3.15초/룩. 실 서비스 트래픽(동시 사용자 수)에 따른 필요 GPU 대수·비용이 전혀 산정 안 됨 — 이건 "기술"이라기보단 "용량 계획"이 안 된 상태.
- **표정 변화 시 부위 내부 왜곡, 눈썹 재형성 정밀 제어**: 지난 라운드에 지적한 그대로, 프로덕션에서도 동일 한계 — 다수 사용자가 다양한 표정으로 테스트하면 품질 편차 드러날 가능성.
- **실시간 워핑의 모바일 성능**: Canvas 2D 기반 팬 삼각분할을 저사양 모바일에서 30fps 유지 가능한지 미검증(데스크톱 개발환경에서만 확인).

### 3) 대안
- Gradio 교체 → **FastAPI + 자체 큐(Redis/Celery 또는 SQS)** 기반 추론 서버로 재작성. 모델 로딩은 워커 프로세스에 상주시켜(POC의 "모델 로드 17초는 1회성" 구조 유지) 요청마다 재로딩 안 함.
- GPU 용량 계획 → 예상 동시 사용자 수 기준으로 필요 GPU 인스턴스 수 산정(간단 산식: 초당 요청수 × 3.15초 = 필요 동시 처리 슬롯). 클라우드 GPU(Runpod/AWS 등, `comfyui-mcp`에 이미 runpod 연동 도구가 있는 걸 보면 후보로 고려 중인 듯) 오토스케일로 피크 대응.
- 피부톤·조명 편차 → 정식 QA로 다양한 피부톤·조명 샘플 확보해서 회귀 테스트셋 구성(이번 세션 범위 밖, 별도 라운드 필요). 단기적으로는 deltaLab 방식(피부 텍스처 보존)으로 전환하는 게 이 문제의 근본 완화책이기도 함.
- 모바일 워핑 성능 → 실기기 벤치마크 후, 필요시 Canvas 2D 대신 WebGL(GPU 가속) 렌더링으로 교체 검토(다음 라운드).

### 4) 라이선스 대안

| 구성요소 | 라이선스 | 프로덕션 판단 |
|---|---|---|
| Stable-Makeup | Apache-2.0 | 문제 없음 |
| SPIGA | BSD-3-Clause | 문제 없음 |
| FaceLib | MIT | 문제 없음 |
| **SD1.5 베이스 체크포인트** | CreativeML OpenRAIL-M | 상업 사용 허용, 단 용도 제한 조항(사칭·명예훼손·실존 인물 허위표현 등 금지) 있음 — **법무 검토 권장**, 업계 표준 라이선스라 대부분 서비스가 문제없이 운영 중이지만 확인 없이 넘어가면 안 됨 |
| SHMT | CC BY-NC-SA (비상업) | **미채택 확정** (지난 라운드) |

**대안 경로 (RAIL-M이 정말 문제가 된다면)**:
1. RAIL-M 없는 diffusion base를 찾기 — 실제로는 대부분의 오픈 diffusion 베이스(SDXL, SD3 등)가 유사한 "책임있는 AI" 라이선스를 채택하고 있어 완전히 조항 없는 대안을 찾기는 어려움. 업계 관행상 법무 검토로 해결하는 게 현실적.
2. 자체 데이터로 makeup transfer 모델을 처음부터 학습(파인튜닝 아님) — 라이선스 이슈는 원천 차단되지만 데이터셋 구축·학습 비용이 크고 로드맵상 후순위 항목.
