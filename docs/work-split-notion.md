# 당화응 분업안 — 모듈 6개와 성능 평가 (노션용, 2026-09-18)

📌 누가 무엇을 맡을지 정하기 전에, 일을 **여섯 덩어리(모듈)** 로 나누고 각 덩어리가 무엇을 받아서 무엇을 내놓는지, 그리고 우리가 만든 게 잘 되는지 **어떻게 잴지**를 적은 문서. 담당자는 아직 비어 있다. 기술 근거와 코드 위치는 저장소 `docs/work-split-modules-v6.md`에 있다.

---

## 1. 왜 화면이 아니라 모듈로 나누나

지금까지는 화면 1·2·3·4·5·6을 한 사람씩 맡아 각자 시제품을 만들었다. 그러다 보니 "얼굴 점 찍기", "가이드 모양 계산", "얼굴 자르기" 같은 공통 부품이 **사람마다 따로 복사돼** 여섯 벌이 됐다. 이걸 합치려면 전부 다시 맞춰야 한다.

모듈로 나누면 다르다. 각자 **"내가 받는 것 / 내가 주는 것"** 만 약속하면 따로 만들어도 나중에 끼워 맞춰진다. 예를 들어 채점 담당은 "얼굴 점과 가이드 모양을 받아서 점수와 한 줄 평을 준다"만 지키면 촬영 담당이 카메라를 어떻게 다루든 상관없다.

## 2. 분업 시작 전에 해야 하는 것 (1~2일)

| 순서 | 할 것 | 왜 |
|---|---|---|
| 1 | 공통 부품을 한 곳에 모은다 (전체 시제품의 부품이 가장 최신이라 그걸 기준으로) | 각자 자기 복사본에서 시작하면 합칠 때 전부 다시 |
| 2 | 화면 3(완성본)이 두 벌 있는데 하나로 정한다 | 두 벌을 들고 시작할 수 없다 |
| 3 | 모듈 사이에 주고받는 데이터 모양을 글로 못박는다 (아래 4번) | 모듈 경계의 언어 |
| 4 | 자동 검사를 한 번에 돌리게 합친다 (지금은 화면별로 따로) | 남의 모듈을 건드려도 바로 알 수 있게 |
| 5 | 폰에서 카메라가 열리는 테스트 환경 (https) | 카메라·실시간·저장은 폰 없이는 못 잰다 |
| 6 | 평가를 한 명령으로 다시 돌리는 틀 + 버전 번호 규칙 (아래 6번) | 코드를 바꿀 때 "진짜 사진에서 나빠졌나"를 첫 주부터 봐야 한다 |
| 7 | 기본 언어 정하기: **Python 3.11 + FastAPI**가 공통, 폰 브라우저에서 도는 것은 **TypeScript**. 서버 뼈대·평가 틀·클라이언트 뼈대(계약 타입·기록 함수)가 이미 만들어져 있어 각자 설치만 하면 된다(`docs/dev-stack-v6.md`) | 언어가 갈리면 합칠 때 두 벌이 된다 |

## 3. 모듈 여섯 개

### ① 촬영·기준 — "맨얼굴을 찍고 기준을 만든다" (브랜치 `capture`)

- **하는 일**: 동의 화면, 4장 자동 촬영, "조금 더 밝은 곳으로" 같은 조건 안내, 틀린 장만 다시 찍기, 맨얼굴 기준(얼굴 점·크기 기준·피부 밝기·눈 흰자 색) 만들기, 세션 저장·복원, 폰 카메라 제약 대응.
- **받는 것**: 카메라.
- **주는 것**: 맨얼굴 기준 한 묶음, 세션 저장소.
- **지금 있는 것**: 자동 촬영·조건 안내·틀린 장 다시가 시제품에서 돈다.
- **해야 할 것**: 눈 흰자로 색 보정(문서에만 있고 코드 없음), 사진 3장까지 저장해서 앱이 꺼져도 복원, 화면 꺼짐 방지, 폰마다 화이트밸런스 잠금이 되는지 표 만들기, **4장 중 눈 감은 장과 옆얼굴 2장을 어디에 쓸지 정하기**(지금은 찍기만 하고 안 씀).
- **안 되는 것**: 웹에서는 카메라 노출·색온도를 고정 못 한다(아이폰). 보정과 조건 안내로 막는다.
- **첫 주 산출물**: 폰에서 4장 찍는 데 몇 초 걸리는지 실측 + 기기별 카메라 잠금 지원 표.

### ② 가이드·실시간 — "어디에 그릴지 보여주고 따라다닌다" (브랜치 `guide`)

- **하는 일**: 룩과 얼굴 점으로 부위별 테두리 만들기, 얼굴형에 따른 쉐딩·하이라이트 자리, 완성본 화면(확대 이미지), 실시간 테두리(카메라 위에 붙어 따라다님), 흔들림 잡기, "정면을 봐 주세요" 같은 확인받기 조건, 확인받기 버튼 촬영.
- **받는 것**: 맨얼굴 기준, 룩 값, 얼굴형, 카메라 화면, 전체 완성 예상 이미지.
- **주는 것**: 부위별 테두리 모양, 확인받기 조건 결과, 확인받기 순간 사진 묶음(3~5장 + 손이 걸렸는지).
- **지금 있는 것**: 테두리·확대·조건 안내·방향 안내가 돌고, 웹캠 실기기에서 고친 것 7건.
- **해야 할 것**: 확인받기 때 사진 1장이 아니라 3~5장 연속으로, 손 검출 붙이기, 흔들림 잡기(순서: 확대 창 둔하게 → 필터 → 테두리를 한 번만 만들고 위치만 갱신 → 깜빡일 때 멈춤), 표정이 기준과 다르면 확인받기 막기, 완성본을 "원본 사진 + 화장 레이어"로(지금 방식은 7배 확대라 뭉개짐), 입술 확대가 실제로 확대되게(지금은 화면의 3%만 입술).
- **안 되는 것**: 거울 갔다 오면 테두리가 픽셀 단위로 똑같이 오는 건 불가. "눈에 안 띄는 수준"이 목표고 점수는 정지 사진으로 매기니 점수엔 영향 없음.
- **첫 주 산출물**: 흔들림 잡기 전후 비교 영상 + 사진 묶음 넘기는 방식 확정.

### ③ 채점·합산 — "잘 그렸는지 재고 점수를 낸다" (브랜치 `score`, 화면 5 담당)

- **하는 일**: 맨얼굴과 화장 후 사진 맞추기(정합), 색 차이 재기, 부위별 점수·한 줄 평·"확인만" 판정, 전체 합산·좌우 대칭·색 조화 보정.
- **받는 것**: 맨얼굴 기준, 테두리 모양, 확인받기 사진 묶음, 룩의 허용 범위.
- **주는 것**: 부위별 결과(점수·상태·한 줄 평), 전체 합산, **부위 결과 화면(화면 5)**.
- **화면 담당**: 프론트는 한 사람이 다 만들지 않는다. 화면 1은 ①, 2·2-b·6과 전체 껍데기는 ⑥, 3·4는 ②, **5는 ③**.
- **지금 있는 것**: 채점기 자동 검사 27개 + 합산 24개 통과. 단 전부 컴퓨터가 그린 가짜 화장 기준.
- **해야 할 것**: 사진 묶음 평균 + 손 걸린 장 빼기, 눈 흰자로 색 보정 적용, 색이 너무 밀리면 "확인만", 볼·입술 색값과 눈썹 좌우 차를 합산에 넘겨서 **꺼져 있는 보정 둘을 실제로 켜기**, 한 줄 평 문장표를 한 곳으로, 기준값을 코드 상수에서 설정 파일로.
- **안 되는 것**: "얼마나 멀리 벗어났는지 mm"는 못 잼 → 방향(위·아래·밖)과 구간만. 화장 영역 찾는 학습 모델은 첫 버전에서 뺌.
- **첫 주 산출물**: 위 수정 반영 + 진짜 화장 사진 첫 10쌍 채점 결과.

### ④ 서버·생성 — "룩을 내 얼굴에 얹어 보여준다" (브랜치 `server`)

- **하는 일**: 화장 얹어보기 서버(생성 AI), 대기열, 전체 완성 예상 이미지, 결과에서 화장만 떼어내기(화장 레이어), 그 레이어를 라이브 얼굴에 따라 붙이기, 얼굴이 그 사람 그대로인지 검사, 사진 즉시 삭제.
- **받는 것**: 정면 사진 1장, 룩 참조 사진 10장.
- **주는 것**: 룩별 결과 이미지, 전체 완성 예상 1장, 화장 레이어.
- **지금 있는 것**: 공개 모델(Stable-Makeup)로 한 장에 2.55초 실측(RTX 3060). 3점 기준으로 대충 붙이는 실시간 미리보기.
- **해야 할 것**: 대기열(고른 룩부터, 작은 미리보기 먼저, 같은 얼굴은 얼굴 분석 1번만), 화장 레이어 떼어내기, 표정까지 따라가는 정교한 붙이기(부위별 → 삼각형 단위), 얼굴 닮음 검사, 삭제 규칙(임시 폴더, 로그에 파일명 없음), 서버 죽었을 때 자동 재시작, **실패 시 경로**(기다림 20초 넘으면 안내, 룩 하나 실패해도 나머지는 계속, 닮음 미달이면 "준비 중", 레이어 실패면 이미지만), **서버 숫자**(한 장 시간 중앙값·상위 5%, 대기 시간, 실패율, 닮음 분포, 재시작 횟수, 삭제 확인). 시간 되면 우리 룩 10개 전용 추가 학습.
- **안 되는 것**: GPU 한 장이라 여러 명이 동시에 쓰면 밀린다 → 대기열로 체감만 줄임.
- **첫 주 산출물**: 대기열 붙여서 룩 10개를 30초 안에 + 화장 레이어 1장 떼어내기 시연.

### ⑤ 모델·데이터·평가 — "사진을 모으고, 얼굴형 모델을 가르치고, 잘 되는지 잰다" (브랜치 `model`)

- **하는 일**: 동의서·촬영 세션·라벨, 정부 데이터 신청, 공개 데이터 받기, 얼굴형 분류 모델 학습(우리가 학습하는 유일한 모델), **평가 데이터 공급과 결과표 취합**.
- **받는 것**: 팀 전체가 찍은 사진, 얼굴 점.
- **주는 것**: 얼굴형 판정 함수(폰에서 돌아가는 작은 모델), 평가 데이터(실촬영 200장 + 사람 판정 + 얼굴형 답지), 평가 결과표.
- **지금 있는 것**: 규칙으로 얼굴형 정하는 코드, 데이터셋 순위표, 공개 셋 2종 실측 코드.
- **해야 할 것**: 동의서 → 20명 × 10장 촬영(단계별, 일부러 삐뚤게 그린 장 포함, 조명 3가지), 부위별 "잘/조금/많이" 판정 + 얼굴형을 팀원 2명이 따로 적기, **모델 학습 전에 규칙 정확도 먼저 재기**, 공개 5,000장으로 1차 학습 → 우리 사진으로 다듬기, 정부 데이터 3종 신청, 부위 영역이 실제와 얼마나 겹치는지 측정, **평가 틀**(6번): 시험지 30장 고정, 한 명령으로 전부 다시 재기, 결과표 자동 생성, 실험 기록(설정·시드·결과 한 줄 결론).
- **안 되는 것**: 공개 얼굴형 사진은 누가 어떻게 적었는지 몰라 1차 학습까지만.
- **첫 주 산출물**: 촬영 세션 완료(20명) + 얼굴형 답지 + 규칙 정확도 숫자 + **시험지 30장 고정하고 채점 평가 첫 실행**.

### ⑥ 앱·콘텐츠·통합 — "전부 하나의 앱으로 만들고 내용물을 채운다" (브랜치 `app`)

- **하는 일**: 룩 고르기·부위 순서·진행 칩·제품 목록 화면, 전체 리뷰 화면·결과 저장·끝내기, 룩 10개 값·제품·문구 확정, 모듈 여섯을 화면으로 잇기, **기록 남기기(어느 화면에서 뭘 눌렀고 어디서 나갔는지, 각 모듈이 호출돼 얼마나 걸리고 왜 실패했는지)와 이탈 집계**, 배포, 폰 테스트 운영, 발표.
- **받는 것**: 모든 모듈의 출력.
- **주는 것**: 룩 값 10개, 화면과 흐름, **모두가 쓰는 기록 함수 하나 + 이벤트 목록 + 이탈 집계표**, 배포 주소.
- **지금 있는 것**: 11개 화면 흐름이 끝까지 돎, 룩 초안 10개, 리뷰 화면·결과 카드.
- **해야 할 것**: 2번의 통합 작업, 룩 값·제품·근거 문장 확정(콘텐츠 병목), **룩 참조 사진 10장을 어떻게 만들지 결정**, 리뷰 들어갈 때 정면 1장 새로 찍기, 결과 카드 미리 만들기(아이폰 공유 제약), 조명 다르면 안내 한 줄, 첫 로딩 캐시, 기능 정의서 정정 10건, 팀원 브랜치 문서 병합. **기록**: 이벤트 목록 확정, 기록 함수 뼈대(세션 번호·시각·화면·부위·버전은 자동으로 붙음), 기기 안 저장 + 내보내기, 이탈 집계(동의 거부 → 촬영 완주·장별 다시 찍기 → 룩 기다리다 나감 → 부위별 확인만·다시·건너뜀 → 리뷰 도달 → 저장 클릭). **호출 그림**(6번)대로 실패 시 어디로 떨어지는지 실제로 구현, **버전 번호**(채점 규칙·룩 값·얼굴형 모델·서버 모델·앱)를 기록과 결과 카드에 찍기, **운영 숫자**(프레임 시간·얼굴 놓침·조건 실패 분포·확인만 이유·복원 성공률) 집계.
- **안 되는 것**: 아이폰은 갤러리 자동 저장 불가 → 공유 시트에서 저장하라고 안내.
- **첫 주 산출물**: 공통 부품 통합 + 폰 테스트 환경 + 룩 사진 방법 결정 + **이벤트 목록과 기록 함수 뼈대 + 버전 번호 규칙**.

## 4. 모듈 사이 약속 (주고받는 데이터)

이것만 맞추면 따로 만들어도 된다. 바꿀 때는 주는 쪽·받는 쪽이 같이 바꾼다. 길이는 전부 "눈 폭·입술 폭·얼굴 폭 대비 비율"로, mm는 화면 표시용 환산에만.

**기록 규칙**: 모든 모듈이 기록 함수 하나만 부른다. **사진·얼굴 점 좌표·얼굴 데이터는 절대 안 남긴다.** 점수·걸린 시간·조건 이름 같은 숫자 요약만. 기기 안에 먼저 쌓고, 사용자 실험 때만 동의받아 내보낸다. 끝내기 때 같이 지운다(실험 동의 세션은 내보낸 뒤). 새 이벤트를 만들려면 표에 먼저 적는다.

| 약속 | 주는 → 받는 | 안에 든 것 |
|---|---|---|
| 맨얼굴 기준 | ① → ②③⑤⑥ | 얼굴 점 478개, 크기 기준(눈·입술·얼굴 폭), 이마 밝기, 눈 흰자 색(새로), 얼굴형, 쌩얼 사진 |
| 룩 값 | ⑥ → ②③④ | 부위 5개 모양·색·진하기 범위, 제품 5줄, 근거 5줄, 색 조화 허용 범위 |
| 테두리 모양 | ② → ③⑥ | 부위별 다각형·선·라벨 (기준 좌표계) |
| 확인받기 조건 결과 | ② → ①⑥ | 통과 여부, 처음 걸린 조건, 안내 문구 |
| 확인받기 사진 묶음 | ② → ③ | 사진 3~5장, 장마다 얼굴 점, 손 걸림 여부, 이마 밝기 (새로 — 지금은 1장) |
| 부위 결과 | ③ → ⑥ | 점수, 상태, 한 줄 평, 코드, 좌우 값, 색값 |
| 전체 합산 | ③ → ⑥ | 합산, 측정 부위 수, 대칭·조화 보정값 |
| 세션 | ⑥ ↔ ①③ | 화면·부위 상태·촬영 상태 + 사진 3장 |
| 룩 작업 | ④ → ⑥② | 작업 번호·상태·결과 이미지, 화장 레이어(새로), 얼굴 닮음 점수 |
| 얼굴형 | ⑤ → ② | 5종 중 하나, 확신도, 규칙인지 모델인지 |
| 기록(이벤트) | 전 모듈 → ⑥ | 자동으로 붙는 것: 세션 번호·시각·화면·부위·버전. 이벤트: 화면 들어감/나감, 버튼, 동의 여부, 촬영(어느 장, 성공, 다시 찍은 이유), 확인받기 조건 실패(처음 걸린 것), 얼굴 놓침 시간, 부위 상태 변화(점수), 채점(상태·확인만 이유·걸린 시간), 룩 생성(걸린 시간·닮음·오류), 복원 성공 여부, 세션 종료(끝내기/이탈/오류, 마지막 화면), 오류 |

## 5. 성능 평가 — "우리가 만든 게 되는지 어떻게 재나"

### 원칙

- 발표에 꼭 나갈 숫자 세 개가 목표: **① 채점기와 사람 판정이 얼마나 같은가 ② 얼굴형을 규칙으로 정할 때 vs 모델로 정할 때 정확도 ③ 얹어보기 속도·얼굴 닮음·룩 색 반영**. 여기에 사용자 실험의 **완주율·이탈 지점**(8번)이 "사용자 효과"로 붙는다.
- **데이터는 하나.** 아래 평가 일곱 중 넷이 "팀원·지인 20명 실촬영 세트"에서 나온다. 촬영 세션이 평가 전체의 병목이라 ⑤가 첫 주에 이것부터.
- **측정은 각 모듈이, 데이터와 결과표는 ⑤가.** 평가 코드와 결과는 한 폴더에, 결과표는 문서 하나에 자동으로. 발표 슬라이드는 그 표를 그대로 옮긴다.
- **고르는 평가 → 되는지 평가 순.** 후보가 둘 이상인 자리는 같은 잣대의 작은 데이터로 먼저 고르고, 고른 뒤 전체 데이터로 잰다.
- **기준선을 먼저.** 모델을 가르치거나 알고리즘을 고치기 전에 "지금 값"을 같은 데이터로 기록한다. 개선폭이 없으면 발표할 숫자가 없다.
- **통과 기준 숫자는 첫 측정 후 팀이 정한다.** 아래 "(안)"은 논의 출발점.

### 먼저: 어느 모델을 고를지 재는 평가 (1~2주차)

아래 "평가 일곱 개"는 **고른 것이 되는지**를 잰다. 그 전에 **무엇을 고를지**를 재야 하는 자리가 넷 있다. 같은 잣대를 쓰되 데이터를 조금만 써서 먼저 고르고, 고른 뒤에 전체 데이터로 통과 평가를 한다. 그래야 "왜 이 모델을 골랐나"가 발표에서 표 한 장으로 나온다. 떨어진 후보도 결과표에 한 줄씩 남긴다.

| 자리 | 후보 | 무엇으로 비교하나 | 데이터 | 고르는 규칙 | 모듈 | 언제 |
|---|---|---|---|---|---|---|
| **화장 얹어보기** | 지금 쓰는 확산 모델의 빠른 설정 3가지 · 더 가벼운 GAN 계열 2~3개 | 한 장 시간, 얼굴 닮음, 룩 색 반영, 메모리, 라이선스, 해상도 | 우리 맨얼굴 5명 × 룩 3 = 15장 (룩 사진 생기기 전엔 시간·메모리만) | 상업 가능 + 3초 안 중에서 닮음·색 반영이 제일 좋은 것 | ④ | 1~2주차 |
| **얼굴형 판단** | A 지금 규칙 · B 얼굴 점 비율 + 작은 분류기 · C 작은 이미지 신경망 · D 얼굴 인식 벡터 + 선형 | 정확도, 어떤 형끼리 헷갈리나, 모델 크기, 폰에서 걸리는 시간, 라벨이 얼마나 필요한가 | 우리 사진 50~100명 답지 (공개 5,000장은 C의 1차 학습에만) | 사람끼리 일치율의 90%를 넘는 것 중 가장 작은 것. B가 C와 3%p 안이면 B(폰에서 가볍고 설명 가능) | ⑤ | 기준선 1주차, 비교 2~3주차 |
| **부위 영역 잡기** | A 얼굴 점 다각형(지금) · B 공개 얼굴 파싱 모델 · C 공개 셀피로 학습한 작은 파싱 모델 · D 색 차이 후처리 | 영역 겹침, 채점 일치율이 얼마나 오르나, 서버가 필요한가, 라이선스 | 공개 셀피 200장 + 실촬영 30장 | **채점 평가(1번)가 목표에 못 미칠 때만 연다.** 열면 싼 것부터 D → B → C | ③⑤ | 채점 평가 직후 |
| **색 보정 방식** (모델은 아니지만 채점을 제일 크게 흔드는 선택) | A 이마 밝기만(지금) · B 눈 흰자로 색까지 보정 · C 옆 피부와의 차이로 재정의 · D 색이 너무 밀리면 "확인만" | 조명 바뀔 때 안 바른 곳을 발랐다고 하는 비율, 채점 일치율, "확인만" 비율, 기준값을 다시 잡아야 하는가 | 실촬영 조명 3가지 세트 | 오탐이 제일 적으면서 "확인만"이 30% 이하. C를 고르면 기준값 전부 다시 잡는 비용 포함 | ③ | 촬영 색 변동 측정 직후 (2주차) |

**고를 필요 없이 가는 것**(대안이 사실상 없음): 얼굴 점 찍기(MediaPipe, 웹에서 대안 없음), 손 검출, 얼굴 닮음 검사(표준 모델), 법선 추정(첫 버전에서 뺌).

| # | 무엇을 | 어떻게 재나 | 데이터 | 기준선 | 통과 기준(안) | 재는 모듈 | 언제 |
|---|---|---|---|---|---|---|---|

## 6. AI 파이프라인 — 모델이 어떻게 불리고, 다시 재고, 무엇이 도는지 아는가

> 자세한 건 저장소 `docs/ai-pipeline-v6.md`. 여기엔 왜 필요한지와 규칙만.

AI 엔지니어 관점에서 심사자가 보는 건 "모델을 골랐다"가 아니라 **모델이 시스템 안에서 어떻게 불리고, 실패하면 어디로 떨어지고, 코드가 바뀌면 어떻게 다시 재고, 지금 무엇이 돌고 있는지 아는가**다. 네 가지를 규칙으로 둔다.

| 무엇 | 규칙 | 누가 |
|---|---|---|
| **호출 그림** | 폰(얼굴 점 → 손 → 조건 → 확인받기 사진 묶음 → 정합 → 색 차이 → 채점 → 합산)과 서버(대기열 → 얹어보기 → 닮음 검사 → 레이어 → 삭제) 두 장. 단계마다 시간 예산과 "실패하면 어디로"가 적혀 있고, 코드가 그대로 동작해야 한다. 서버가 죽어도 촬영·가이드·채점은 돈다 | ⑥ (서버는 ④) |
| **한 명령 재평가** | 진짜 사진 30장을 "시험지"로 고정(버전 붙임, 같은 사람이 학습·시험에 같이 안 들어가게). 채점·가이드·기준값 코드가 바뀌면 한 명령으로 전부 다시 재고 결과표가 자동으로 문서에 붙는다. 결과 파일 이름에 코드 버전·모델 버전·시험지 버전 | ⑤ 틀, 각 모듈이 자기 것 |
| **버전 번호** | 채점 규칙, 룩 값, 얼굴형 모델, 서버 모델, 앱 — 다섯 개에 번호. 기록 한 줄과 결과 카드 구석에 같이 찍혀서 "그때 뭐가 돌았나"를 안다. 번호가 오르면 시험지를 다시 돌린다 → 버전별 일치율 그래프가 발표 자료 | ⑥ |
| **운영 숫자** | 서버: 한 장 시간 중앙값·상위 5%, 대기, 실패율, 닮음 분포, 재시작, 삭제 확인. 폰: 프레임 시간, 얼굴 놓침, 조건 실패 분포, 확인만 이유, 복원 성공률, 이탈 퍼널. 전부 기록에서 스크립트로 뽑고 표로 본다 | ⑥ (서버는 ④) |
| **실험 기록** | 학습·설정·기준값 실험은 설정 파일 + 시드 + 결과 CSV + 한 줄 결론. 도구는 CSV면 충분 | ⑤ |

발표에서는 이게 슬라이드 넉 장이 된다: 시스템 그림, 평가 틀과 버전별 그래프, 모델 선정 표(탈락 후보 포함), 운영 숫자.

## 8. 분업 시작 전에 팀이 정할 것

1. 담당자 배정 (이 문서는 모듈만).
2. 화면 3 구현 두 벌 중 하나.
3. 촬영 4장 중 눈 감은 장·옆얼굴 2장의 용도 — 쓸 곳이 없으면 정면 2장으로 줄인다.
4. 평가 1·2·3의 통과 기준 숫자 — 첫 측정 후 정하되, "낮으면 무엇을 바꿀지"(화장 영역 모델 꺼내기 / 기준값 조정 / 룩 사진 교체)만 미리 합의.
5. 룩 참조 사진 10장 방법 (직접 촬영 / 컴퓨터 생성 / 구매).
