### 0-4. 화면 3에서 직접 정해야 하는 것

**완성본 이미지를 무엇으로 만들 것인가.** 이게 화면 3의 가장 큰 결정이다 → 3장 참조.

```
① 서버 렌더(512) 줌      7.4배 확대. 지금 문서에 적힌 방식
② 원본 사진 + 화장 레이어  3.6배. F-03 것을 재사용, 새 모델 0개  ← 추천
```

판단은 1주차 검증 5의 ΔE 수치로 한다. **그전까지는 ①로 만들어 두고 나중에 갈아끼울 수 있게** 완성본 소스를
한 군데(`LookSelection.fullRender`를 읽는 함수 하나)로 모아 두는 것이 좋다.

### 0-5. 서버 없이 지금 시작할 수 있다

`fullRender`가 없어도 화면 3은 만들 수 있다. **정면 사진 한 장을 `fullRender` 자리에 그대로 넣으면** 된다.

| 필요한 것 | 지금 있는 것 |
|---|---|
| 정면 얼굴 사진 | `poc/samples/phone-portraits-20/person_*_front_open.jpg` |
| 랜드마크 468점 | `poc/synth/`가 뽑는다 (브라우저 "랜드마크 내려받기" 또는 `generate.py`) |
| 크롭 박스 계산 | `poc/synth/generate.py`의 `face_box()`가 같은 방식. 부위별로 바꾸면 됨 |
| 부위 비율 기준 | 눈 바깥끝↔바깥끝 = 얼굴 너비 0.683배 (3장 실측) |

**권장 작업 순서**

```
1  크롭 박스 계산 (부위 6개 × 가로/세로)  ← 순수 함수로. 테스트 가능
2  완성본 화면 레이아웃 (가로/세로 2종)
3  진행 칩 6개 + 상태 표시
4  방향 안내 (가로↔세로 전환)
5  근거 한 줄 · 지금 필요한 것 (더미 데이터로)
6  3-c 규칙 테두리        ← 규칙 5종이 나온 뒤
7  fullRender 연결        ← 서버가 나온 뒤
```

1번을 `core.js`처럼 **순수 함수 + Node 테스트**로 만들면 `poc/screen6`·`poc/synth`와 같은 방식이 되고,
서버·카메라 없이도 검증이 된다. 브랜치 이름은 `feat/screen3-finished-look` 정도가 무난하다.

## 1. 화면 3이 하는 일

사용자가 부위 단계에 들어오면 **"다 되면 이렇게 됩니다"**를 정지 이미지로 먼저 보여준다.
그리러 가기 전에 목표를 눈으로 확인시키는 화면이다.

```
[진행 칩 6개]                              ← 어느 단계든 이동
┌────────────────────────┬──────────────┐
│                        │  완성본       │
│   완성본 이미지          │  아이라이너    │
│   (이 부위로 줌)         │  근거 한 줄    │
│                        │  지금 필요한 것 │
│                        │  [그리러 가기] │
└────────────────────────┴──────────────┘
눈썹·아이라이너·섀도우 = 가로 / 입술·볼터치·쉐딩 = 세로
```

**v6에서 확정된 것**: 완성본은 **화면 2-b의 전체 완성 예상 렌더링을 그 부위로 줌한 이미지**다.
그 부위만 따로 합성하지 않는다. 그래서 이미 지나온 부위도 화장된 채로 보인다.

## 2. 필요 기술 — 요소별 1순위와 차선책

**새로 만들 모델은 하나도 없다.** 화면 3의 기술 부담은 전부 "이미 있는 것을 어떻게 쓰느냐"다.

### 2-1. 구체적으로 무엇을 쓰나

| # | 요소 | 기술·API | 종류 | 실현성 |
|---|---|---|---|---|
| 3-1 | 진행 칩 6개 | 순수 JS 상태(`poc/screen6/core.js` 재사용) · CSS Flexbox + `overflow-x` 가로 스크롤 · `scrollIntoView({inline:'center'})`로 현재 칩 끌어오기 · `localStorage` | 웹 표준 + 규칙 | ✅ |
| 3-2 | 화면 방향 감지 | **`window.matchMedia('(orientation: portrait)')` + `change` 이벤트** · `screen.orientation.type`(보조) | 웹 표준 | ⚠️ |
| 3-2 | 화면 방향 **잠금** | `screen.orientation.lock()` — **iOS 미지원.** 쓰지 않는다 | 웹 표준 | ❌ 불가 |
| 3-2b | 완성본 (1순위) | **WebGL2** 직접 — 468점 삼각 메시 워핑 + 곱하기·소프트라이트 블렌드. F-03이 만든 화장 레이어를 그대로 재사용. 직접 쓰기 부담스러우면 **PixiJS v8 `MeshGeometry`**(positions·uvs·indices를 그대로 받는 2D 메시, Three.js보다 가벼움) | CV + 웹 표준 | ⚠️ |
| 3-2b | 완성본 (차선) | `<img>` + CSS `transform`, 또는 Canvas 2D `drawImage(src, sx,sy,sw,sh, dx,dy,dw,dh)` · `createImageBitmap(blob, {resizeQuality:'high'})` | 웹 표준 | ✅ |
| 3-3 | 부위 크롭 박스 | **순수 JS 기하 계산.** MediaPipe 468점의 인덱스만 참조하고 라이브러리는 안 쓴다 | 규칙 | ✅ |
| 3-4 | 3-c 규칙 테두리 | Canvas 2D `Path2D` + `setLineDash()` (또는 SVG `<polyline>`) · 좌표는 얼굴형 규칙 × 서버 법선 맵에서 온다 | 규칙 | ⚠️ |
| 3-5 | 근거 한 줄 | 룩 템플릿 JSON의 고정 문장 + 얼굴형 5종 분기. **LLM을 쓰지 않는다** (5장) | 데이터 | ✅ |
| 3-6 | 지금 필요한 것 | 룩 템플릿 JSON의 `products[]`를 `partId`로 거른다 | 데이터 | ⚠️ 콘텐츠 |
| — | 완성본 보관 | `ImageBitmap` / `Blob` URL(세션 중) · IndexedDB · OPFS (2-5) | 웹 표준 | ✅ |
| — | 화면 전환 | "그리러 가기" → 화면 4. 상태는 세션 모듈이 넘긴다 | 규칙 | ✅ |

> ⚠️ **방향 감지에서 흔히 틀리는 곳.** `screen.orientation`의 `change` 이벤트는 **iOS 사파리에서 동작하지 않는다.**
> `matchMedia('(orientation: portrait)')`에 `change` 리스너를 다는 쪽을 1순위로 쓰고,
> `screen.orientation.type`은 보조로만 읽는다. 옛 `orientationchange` 이벤트는 폐기 예정이라 쓰지 않는다.

**화면 3이 쓰지 않는 것** — 카메라(`getUserMedia`), 손 검출, 분할 모델, 실시간 추적, 30fps 루프.
전부 화면 4·5 것이다. 화면 3은 **정지 이미지 화면**이다.

### 2-3. 런타임에 실패했을 때 — 차선책 사다리

개발 단계의 "무엇으로 만들까"와 **서비스 중에 실패했을 때 무엇을 보여줄까**는 다른 문제다.
화면 3은 **어떤 경우에도 빈 화면을 보여주지 않는다**를 원칙으로 한다.

| 무엇이 실패하면 | 1단계 | 2단계 | 절대 하지 않는 것 |
|---|---|---|---|
| **서버가 `fullRender`를 못 준다** | 촬영 1 정면 사진에 화장 레이어를 얹어 보여준다 | 레이어도 없으면 **맨얼굴 사진 + "완성 예상을 준비 중이에요"** | 빈 화면·무한 로딩 |
| **화장 레이어 추출 실패** | 서버 렌더를 줌해서 쓴다 | 맨얼굴 + 가이드 테두리만 | — |
| **랜드마크가 없다** | 화면 3은 **촬영 1에서 이미 저장해 둔 랜드마크**를 쓴다. 다시 검출하지 않으므로 실패할 일이 없다 (2-4) | 그래도 없으면 얼굴 중앙 고정 크롭 | 이 화면에서 재검출 시도 |
| **사용자가 폰을 안 돌린다** | 6초 안내 후 **그냥 보여준다**. "가로로 돌리면 더 크게 볼 수 있어요" 한 줄만 | — | 계속 막기 |
| **룩 템플릿 문장이 없다** | 부위별 기본 문장 | 문장 줄을 숨긴다 (레이아웃은 유지) | "설명 없음" 같은 빈 문구 |
| **세션 저장 실패** (사생활 보호 모드) | 메모리로만 진행 | — | 오류 화면 |
| **쉐딩 규칙이 없다** (3-c) | 랜드마크 근사 테두리 | 테두리 없이 얼굴형 멘트만 | 3-c 단계 자체를 건너뛰기 |

### 2-4. 화면 3에는 랜드마크 검출이 필요 없다

이건 짚어 둘 만하다. 화면 3은 **정지 이미지 화면**이다. 카메라를 켜지 않는다.

크롭 박스에 쓰는 랜드마크는 **촬영 1에서 이미 뽑아 `Baseline.photos.frontOpen.landmarks`에 저장해 둔 것**이다
(`impl-screen1-5` 1-3). 화면 3에서 다시 검출할 이유가 없다.

그래서 **"랜드마크 검출이 실패하면?"이라는 차선책이 아예 필요 없다.**
검출이 실패했다면 그건 화면 1에서 이미 걸러졌고, 화면 3까지 오지 못한다.

> 참고로 검출기 자체의 대안은 있다 — TensorFlow.js `face-landmarks-detection`(같은 MediaPipe 모델을 다른 런타임으로),
> face-api.js(가볍지만 68점이라 우리 부위 규칙에 부족), ONNX Runtime Web + 다른 모델.
> **화면 1의 이야기지 화면 3의 이야기가 아니다.**

### 2-5. 완성본 이미지를 어디에 두나

완성본(`fullRender`)은 **세션 내내 들고 있어야 한다.** 부위 6개가 전부 이 한 장을 줌해서 쓰기 때문이다.

| 방법 | 언제 |
|---|---|
| **메모리(`ImageBitmap`/`Blob` URL)** | **1순위.** 세션 중에만 필요하고, 끝나면 지워야 하므로 오히려 맞다 |
| IndexedDB | 앱이 꺼졌다 돌아올 때 복원이 필요하면 (F-07 세션 복원) |
| OPFS | 이미지가 커져서 IndexedDB가 버거울 때. iOS 17부터 용량 제한이 풀렸지만 **저장 공간이 부족하면 먼저 지워진다** |

세션이 끝나면 어느 쪽이든 **반드시 지운다** (F-11 "끝내기"). 남겨 두는 것이 우리 원칙 위반이다.

## 3. 쟁점 1 — 완성본 해상도 (가장 중요)

### 3-1. 문제

눈 단계(눈썹·아이라이너·섀도우)의 완성본은 **양쪽 눈을 눈 바깥 끝에서 끝까지** 확대해 가로 화면을 채운다.
그런데 원본인 `fullRender`는 **서버 확산 모델이 만든 512×512**다.

실측 랜드마크(샘플 1번) 기준으로 계산했다.

- 눈 바깥끝↔바깥끝 = 얼굴 너비의 **0.683배**
- 홍채 지름 = 얼굴 너비의 **0.0957배**
- 표시 영역 = 가로 폰 화면의 약 72% (iPhone 15 가로 2556 device px 기준 ≈ 1840px)

| 완성본 원본 | 렌더 속 얼굴 너비 | 크롭 폭 | 크롭 속 홍채 | **화면을 채우려면** |
|---|---|---|---|---|
| **SD1.5 기본 512** | 317px | 249px | 30px | **7.4배 확대** |
| 768로 올림 | 476px | 374px | 46px | 4.9배 |
| SDXL·FLUX 1024 | 635px | 498px | 61px | 3.7배 |
| **원본 사진 1080×1920** | 648px | **509px** | 62px | **3.6배** |
| 원본 사진 1440×1920 | 864px | 678px | 83px | **2.7배** |

**512를 줌하면 7.4배다.** 아이라이너 선이 뭉개져 "여기까지 그리세요"의 기준선 구실을 못 한다.
게다가 원본이 **확산 모델이 생성한 픽셀**이라 이미 실제 디테일이 아니고, 그걸 다시 7배 늘리면 흐림이 겹친다.

### 3-2. 대안 A — 초해상(super-resolution)으로 키운다

| 모델 | 라이선스 | 판단 |
|---|---|---|
| **GFPGAN** | **Apache-2.0 (상업 가능)** | 상업 가능한 유일한 1순위 후보 |
| CodeFormer | **NTU S-Lab (비상업)** | 사업화 불가 |
| Real-ESRGAN | BSD-3 | 얼굴 전용이 아님. 배경 보조용 |

**그런데 이 방향은 권하지 않는다.** 두 가지 이유다.

1. **배율이 위험 구간이다.** 얼굴 복원 연구들이 **8배를 넘으면 모델이 없는 디테일을 지어낸다(hallucination)**고 보고한다.
   우리 7.4배는 딱 그 문턱이다. 2025년에도 `AuthFace`, `HonestFace`, `DynFaceRestore` 같은 논문이 이 문제를 다루는 중이다.
2. **지어낸 디테일이 특히 위험한 화면이다.** 화면 3은 사용자가 **보고 따라 그리는 기준**이다.
   모델이 만들어낸 아이라이너 꼬리를 사용자가 따라 그리면, 그건 우리가 의도한 가이드가 아니다.
   화면 5에서 그 선으로 채점까지 한다.

### 3-3. 대안 B — 더 큰 해상도로 생성한다

SDXL·FLUX는 1024가 기본이라 3.7배로 내려간다. 하지만 **우리 1순위인 Stable-Makeup은 SD1.5(512)** 기반이고,
FLUX.1-schnell은 12B이라 **룩당 3초 목표와 정면충돌**한다 (`tech-stack-v6.md` 2-3).
SD1.5를 768로 올리는 것은 가능하지만 구도 붕괴가 잦고, 얻는 것은 7.4배 → 4.9배뿐이다.

### 3-4. 대안 D — 서버 렌더를 타일 확산으로 충실하게 키운다 (재조사로 추가)

3-2의 초해상과 다르다. 초해상은 **저해상 사진만 보고** 디테일을 지어내지만,
**타일 확산 + ControlNet Tile**은 원본 렌더를 조건으로 걸고 잠재 공간에서 타일별로 다시 그린다.
같은 확산 모델 계열이라 지어내는 방식도 렌더와 일관된다.

| 구현 | 라이선스 | 기반 | 판단 |
|---|---|---|---|
| **MoD Control Tile Upscaler for SDXL** (DEVAIEXP) | **Apache-2.0** | RealVisXL V5 + ControlNet Union, 잠재 공간 타일링 | **상업 가능.** 이음선 없음 |
| Tiled Diffusion / MultiDiffusion (A1111 확장) | **CC BY-NC-SA 4.0** | SD1.5·SDXL | 비상업. 발표용 |

512 → 1024로 키우면 3.7배가 된다. **단점은 SDXL 추론 1회가 더 붙는다**는 것이다.

> 그런데 **예산이 다르다.** 룩당 3초 제약은 화면 2 썸네일 10개에 걸린 것이고,
> 화면 3 완성본은 **룩을 확정한 뒤 한 장**이다. 2-b 로딩에 10~20초를 얹을 수 있다면 성립한다.
> 얼굴 정체성 보존 수치는 저장소에 없다 — 1주차 검증 5에서 같이 재야 한다.

### 3-5. 대안 E — 눈 부위만 따로 512로 생성한다 (재조사로 추가)

**부위별로 화장을 넣는 모델**이 2026년에 나왔다. 부위 단위로 생성할 수 있으면 눈 영역을 처음부터 512로 만들 수 있고,
그러면 확대 문제가 사라진다.

| 모델 | 발표 | 부위 제어 | 코드·가중치 | 라이선스 |
|---|---|---|---|---|
| **FRAM** — Facial Region-Aware Makeup | **CVPR 2026** | 학습 가능한 토큰으로 눈·입 등 부위별 화장 특징 추출, 어텐션 손실로 영역 제어 | **공개** (GitHub + HF) | **CC BY-NC-SA 4.0 (비상업)** · SD 2.1 base |
| MakeupMirror | 2026-06 | ControlNet 얼굴 기하 조건 + 피부·눈·입 영역 제어 + 피부톤 변조. Stable-Makeup 개선 | 미확인 | 미확인 |

**발표·과제용으로는 이게 최상이다.** 사업화 시 비상업 라이선스라 교체해야 한다 (Stable-Makeup은 Apache-2.0 코드).
"부위만 따로 생성" 자체가 기능 정의서 F-06의 v6 결정("전체 렌더를 줌, 별도 합성 없음")과 어긋나므로
채택하려면 그 결정을 다시 열어야 한다.

### 3-6. 대안 C — 원본 사진에 화장 레이어를 얹는다 ★ 추천

**F-03이 이미 이걸 만들고 있다.** 기능 정의서 F-03 "실시간 트래킹(폰)"을 그대로 옮기면,

> 서버 결과에서 화장 레이어만 추출한다. 생성 이미지와 원본 정면 사진을 같은 랜드마크 메시(468점 삼각화)에
> 정렬 → 부위 마스크별 색 차이(Lab)와 알파를 **메시 텍스처로 저장**.

즉 **"화장만 떼어낸 레이어"가 이미 폰에 있다.** 화면 2에서 매 프레임 카메라 영상에 씌우는 그 레이어다.
같은 레이어를 **원본 정면 사진(촬영 1)에 한 번 씌우면** 완성본이 된다.

| | 서버 렌더 줌 (지금 문서) | **원본 + 레이어 (대안 C)** |
|---|---|---|
| 확대 배율 | 7.4배 | **3.6배** (1440 촬영이면 2.7배) |
| 피부·속눈썹 디테일 | 생성된 픽셀 | **실제 촬영 픽셀** |
| 새 모델 | — | **없음. F-03 것을 재사용** |
| 서버 부하 | 그대로 | 그대로 |
| "다른 부위도 화장된 채" (v6 확정) | 만족 | **만족** (룩 전체 레이어를 씌우므로) |

**v6에서 확정한 의도를 깨지 않으면서 해상도만 2배 좋아진다.** 추가 모델도, 추가 서버 비용도 없다.

한계도 있다. 레이어는 Lab 색 차이와 알파의 근사라 **서버 렌더와 100% 같지는 않다.**
F-03 수용 기준이 이미 그걸 재고 있다 — "서버 정지 이미지 대비 색 차이 ΔE 평균".
**그 수치가 나오면 대안 C를 쓸지 판단할 수 있다.** 1주차 검증 5에서 같이 재면 된다.

### 3-7. 권고 — 재조사 반영판

| 순위 | 방법 | 확대 배율 | 새 모델 | 라이선스 | 언제 쓰나 |
|---|---|---|---|---|---|
| **1순위** | **원본 사진 + 화장 레이어** (대안 C) | **3.6배** | 없음 | — | ΔE가 받아들일 만하면. 비용이 0이라 먼저 시도 |
| **2순위** | **타일 확산 업스케일 512→1024** (대안 D, MoD) | 3.7배 | SDXL 1회 | **Apache-2.0** | C의 ΔE가 크면. 2-b 로딩 10~20초를 감수 |
| 3순위 | 서버 렌더(512) 줌 — 지금 문서 방식 | 7.4배 | 없음 | — | 위 둘이 다 안 되면. 눈 단계 여백을 늘려 확대율을 낮춘다 |
| 발표용 | **부위별 생성** (대안 E, FRAM) | 사실상 무손실 | 확산 1종 | **비상업** | 발표 데모 품질이 중요할 때. 사업화 시 교체 |

| 비권장 | 초해상(GFPGAN 등) | — | 1종 | Apache-2.0 | 원본을 조건으로 안 걸어 지어낸다 (3-2). D가 있으니 쓸 이유가 없다 |

**바뀐 것** — 재조사 전에는 "C 아니면 512 줌"이었다. 지금은 **C가 안 되면 D**가 있다.
D는 상업 가능하고 원본에 조건화되어 초해상보다 충실하다. 3초 제약이 화면 3에는 안 걸린다는 것도 이번에 확인했다.

**결정은 숫자 하나로 난다** — F-03 수용 기준에 이미 있는 "서버 정지 이미지 대비 색 차이 ΔE 평균".
1주차 검증 5에서 C의 ΔE와 D의 처리 시간을 같이 재면 1·2순위가 정해진다.

## 4. 쟁점 2 — 쉐딩·하이라이트(3-c)는 렌더에 없다

룩 템플릿 10개는 **눈썹·아이라이너·섀도우·입술·볼터치만** 담는다 (F-04).
쉐딩·하이라이트는 얼굴형 규칙에서 오므로 **`fullRender`에 아예 없다.**

그래서 3-c는 혼자 다른 방식이다.

```
fullRender를 얼굴 아래쪽(광대~턱)으로 줌
  + 그 위에 규칙 자리를 테두리로만 (색 면 채우기 없음, 라벨 "쉐딩"·"하이라이트")
```

| 필요한 것 | 지금 상태 |
|---|---|
| 얼굴형 5분류 (F-02) | 규칙만 정하면 됨. 랜드마크 비율 계산이라 모델 불필요. **학술 정의가 있다** (4-1) |
| **얼굴형별 쉐딩 위치 규칙 5종** | **미정.** 원리는 논문에 있고 구체 위치는 업계 교재에 있다 (4-1) |
| 서버 법선 맵 | **라이선스 위험 있음.** MediaPipe 3D 메시로 대체 검토 중 (`tech-stack-v6.md` 8-2) |
| 테두리 렌더링 | Canvas 2D 폴리라인. 확실 |

**여기가 화면 3에서 가장 덜 정해진 부분이다.** 기술이 어려운 게 아니라 **콘텐츠(규칙 5종)가 없다.**

### 4-1. 재조사로 찾은 학술 근거

앞서 "출처가 논문이 아니라 업계 교재"라고 적었는데, 다시 찾으니 **논문이 있었다.**

| 출처 | 무엇을 주나 | 우리 어디에 |
|---|---|---|
| **Zhao et al., *Cognitive Neurodynamics*, 2020** (PMC7501398) | 얼굴형 5종의 **기하학적 정의** — 하트(이마 넓고 턱 좁고 턱끝 뾰족) · 장형(광대 폭 < 얼굴 높이의 2/3) · 계란형(이마≈광대≈얼굴 폭) · 원형(이마=광대=턱 폭) · 각진형(이마 넓고 턱 각지고 짧음). 81점 랜드마크, 비율 특징 23개 | **F-02 5분류 규칙의 근거.** 우리 분류와 이름까지 같다 |
| **"The effects of contour and highlighting makeup on the perception of facial form"** (2021, 성형외과 문헌) | CHM의 원리 — **어두운 색은 후퇴, 밝은 색은 돌출**하는 착시로 얼굴 형태 인지를 바꾼다. 수술 결과를 흉내낼 정도 | **3-c 근거 한 줄의 원리 출처.** "왜 거기에 쉐딩을 넣나"에 대한 답 |
| 업계 교재·브랜드 가이드 | 얼굴형별 **구체 위치** (둥근형은 관자놀이~광대 아래 C자 등) | 규칙 5종의 좌표 |

즉 **원리(논문) → 분류(논문) → 위치(교재)** 세 층이다. 위치만 교재에서 3곳 이상 모아 공통분모를 뽑으면 된다.

## 5. 쟁점 3 — 근거 한 줄은 LLM을 쓰지 않는다

"눈꼬리를 살짝 올려 짧게 빼세요" 같은 문장을 어떻게 만드나.

**문장 템플릿으로 만든다.** LLM은 쓰지 않는다. 이유는 셋이다.

1. 기능 정의서 7장 "하지 않는 것"에 LLM이 없지만, 9장 모델 목록에도 없다. **계획에 없는 모델을 늘리지 않는다**
2. 이 문장은 **룩 템플릿마다 고정**이다. 사람이 미리 써 두면 된다. 매번 생성할 이유가 없다
3. 폰에서 LLM을 돌리면 30fps·용량 예산이 깨지고, 서버로 보내면 지연과 비용이 는다

| 부위 | 문장 출처 |
|---|---|
| 룩 5부위 | **룩 템플릿에 사람이 적어 둔 고정 문장** (룩 10개 × 5부위 = 50문장) |
| 쉐딩·하이라이트 | **얼굴형 5종별 문장 템플릿** ("둥근 얼굴형이라 턱선과 광대 아래에…") |

필요한 건 기술이 아니라 **50 + 5 = 55문장을 쓰는 일**이다. 룩 템플릿 콘텐츠 작업에 포함된다.

## 6. 쟁점 4 — 화면 방향

눈 단계는 **가로**, 입술·볼·쉐딩은 **세로**다. 화면 3·4·5가 모두 같은 방향을 쓴다.

**iOS 사파리는 화면 방향을 잠글 수 없다.** Screen Orientation API의 `lock()`이 없다.
그래서 v6는 **잠그는 대신 안내한다** — "폰을 가로로 돌리세요", 가로로 바뀌면 안내를 닫는다.
세로로 계속 들면 양쪽 눈을 세로 화면에 맞춰 작게 보여주되 **확대율이 낮다는 표시**를 한다.

이미 문서에 반영돼 있고, 기술적으로 더 할 수 있는 것이 없다. 안드로이드 앱으로 가면 잠글 수 있다.

## 8. 결론

| 요소 | 판정 | 차선책이 있나 |
|---|---|---|
| 진행 칩 · 크롭 박스 · 테두리 렌더링 · 보관 | ✅ 지금 기술로 확실히 된다 | 필요 없음 |
| 근거 한 줄 · 제품 한 줄 | ✅ 기술 문제가 아니다. **콘텐츠 55문장을 쓰면 된다** | 기본 문장 → 줄 숨김 |
| 화면 방향 | ⚠️ iOS 잠금 불가. 안내로 대체 — 이미 반영 | **유예 후 그냥 보여주기** |
| **완성본 해상도** | ⚠️ **512 줌은 7.4배.** 대안 C(원본+레이어)로 3.6배 | **4단계 사다리 (3-5)** |
| 쉐딩·하이라이트 규칙 | ⚠️ 기술이 아니라 **규칙 5종이 미정** | 랜드마크 근사 → 멘트만 |

**화면 3에 새로 만들 모델은 없다.** 남은 일은 ① 완성본 원본을 무엇으로 할지 정하기 ② 문장 55개 쓰기
③ 얼굴형 쉐딩 규칙 5종 정하기 — 셋 다 1주차 안에 결판난다.

**그리고 셋 다 막혀도 화면 3은 뜬다.** 맨얼굴 사진 + 기본 문장 + 테두리 없는 멘트로 내려앉을 뿐이다.
차선책 사다리(2-3)가 그것을 보장한다. 이게 화면 3이 다른 화면보다 먼저 만들 수 있는 이유이기도 하다.
