# 화면 6 기술 타당성 검토

당화응 · 전체 리뷰 화면 (F-10 합산 · 비교 · 결과 저장 · 끝내기) · 2026-09-17
근거: `feature-spec-v6.md` F-10, `impl-screen6-review-v6.md` A-1~A-5·C-1~C-3, `poc/screen6` @ d50a7fa, `poc/full` @ dd2fd06 (`lib/review.js`, `app.js` rReview·saveResultImage·faceCropUrl, `lib/flow.js` toReviewParts·stripImages)

> **한눈에**
화면 6은 **서버 없이 클라이언트 계산·표시·저장만 하는 화면**이라 새 모델도 새 기술도 없다. 합산·보정·한 줄 평·막대·비교·저장·끝내기 전부 **브라우저에서 돌아가고 Node 검증 24개(단독 POC) + 전체 POC 통합 테스트를 통과했다.** 불가능한 것은 없다.
>
> 정의서와 다른 것은 셋 — **조화 보정이 항상 0**(채점이 색값을 안 넘김), **눈썹 좌우 차가 대칭 보정에 빠짐**(채점이 값을 안 냄), **"내 화장" 사진이 새 촬영이 아니라 마지막 확인받기 프레임**. 셋 다 채점 모듈에서 값 한두 개를 더 넘기거나 게이트를 한 번 더 부르는 수준이다. 진짜 한계는 둘 — **iOS 갤러리 자동 저장 불가**(공유 시트에서 사용자가 저장), **세션 복원 시 사진 유실**(localStorage에 이미지를 안 넣음). 둘 다 대안이 있다.
>
> 가장 큰 구멍은 화면 5와 같다: 합산에 들어가는 점수와 보정값이 전부 **가상 화장 기준**이라, 대칭 보정이 실제로 한쪽만 진하게 바른 사진에서 음수로 나오는지는 아직 아무도 모른다.

## 2. 이미 증명된 것 — `poc/screen6` · `poc/full`

두 벌이 있다. 단독 POC는 시연 패널로 부위 결과를 손으로 넣어 화면 6만 검증했고, 전체 POC는 화면 5 채점 결과가 그대로 흘러들어 온다.

```
PartResult[] (화면 5 채점 → flow.applyResult)
→ toReviewParts → computeSummary(가중 평균 + 대칭 + 조화) → total 0~100 또는 null
→ 막대 6줄(oneLiner: diagnosis 우선, 없으면 코드표) → 비교 크롭 2장(faceCropUrl)
→ 결과 저장(캔버스 → Web Share / 다운로드) · 끝내기(clearSaved)
```

| 검증 항목 (정의서 A-5) | 단독 POC | 전체 POC |
| --- | --- | --- |
| 합산 8종(전부 통과·확인만·건너뜀·전부 확인만·덮어쓰기·−5 상한·가중치·4부위 룩) | A1~A8 통과 | P1·P2(부위 진행·덮어쓰기·쉐딩 확인만·건너뛰기) |
| 멱등성 | B1 | — |
| 대칭·조화 보정 | B2·B3 (합성 입력) | 실데이터로는 **미검증** |
| 쉐딩 확인만·합산 제외 | V1~V5 | P1 |
| 막대 탭 이동 | 토스트로 대체 | 화면 3 완성본으로 실제 이동 |
| 비교 정렬 3% | 사진 탭에서 % 표시 (기록 없음) | 스크린샷 육안 |
| 결과 저장 | 이미지 1장, 미리보기 | 데스크톱 다운로드만 확인 |

| 세션 복원 | 검증 탭 + 새로고침 (사진 제외) | draft JSON 왕복 P3 (이미지 제외) |
| 빈 상태 | A4 + 예시 | — |

> **이 검증이 보증하는 것과 보증하지 않는 것**
합산 수식·상태 규칙·화면 구성은 증명됐다. 보증되지 않는 것은 **입력의 질**이다. 대칭 보정은 아이라이너 `lrDiffMm`·섀도우/볼터치 `lrIndex`를 받는데 이 값들은 화면 5가 가상 화장으로 낸 것이다. 실제로 한쪽만 진하게 바른 사진에서 보정이 음수로 떨어지고 양쪽 같게 바른 사진에서 0~−1에 머무는지(정의서 A-5 "대칭 보정 방향")는 **팀원 자가 촬영 10장이 있어야 안다.** 결과 저장의 공유 시트와 세션 복원도 폰에서는 아직 안 눌러 봤다.

## 3. 안 되는 것과 대안

### ① 조화 보정 — 함수는 있고 입력이 없다

`harmonyPenalty`는 볼터치·입술의 `metrics.colorAb`(Lab a*, b*)와 템플릿 `harmonyRange.maxDeltaAb`를 받아 거리 초과분에 비례해 최대 −5를 준다. 그런데 화면 5 채점 모듈(`score.js`)은 `intensityResult`·`compareLip`에서 **색값을 metrics에 넣지 않는다.** 결과: 전체 POC에서 조화 보정은 언제나 0이고, `harmonyApplied: false`다. 화면에 안 보이는 보정이라 아무도 눈치채지 못했다.

|  | 대안 | 비용 · 효과 |
| --- | --- | --- |
| (a) | 채점에서 부위 평균 Lab(a*, b*) 한 값을 `metrics.colorAb`로 넘긴다 | 볼터치는 ΔE 계산 중에 이미 Lab을 갖고 있고 입술도 마찬가지. 각 3줄. **권장** |
| (b) | 룩 템플릿 허용 범위(`maxDeltaAb`)가 확정될 때까지 0으로 둔다 | 정의서 A-3 "템플릿에 범위 없으면 0"과 같으므로 규칙 위반은 아님. 다만 지금 기본 템플릿에 12가 박혀 있어 **"적용 중인 척"**이 된다 → 확정 전엔 null로 |
| (c) | 조화 보정 자체를 뺀다 | 화장 초보 대상이라 "볼과 입술 색이 안 어울림"은 룩이 정해 준 색을 썼으면 생기기 어렵다. 팀 결정 사항 |

### ② 대칭 보정 — 눈썹이 빠져 있다

정의서는 대칭 입력을 눈썹·아이라이너·볼터치로 적었다. 채점이 내는 값은 아이라이너 `lrDiffMm`(맨얼굴 비대칭 차감 후, 눈 폭 비율 0.11 = 1), 섀도우·볼터치·쉐딩 `lrIndex`다. **눈썹은 `browResult`가 좌우 각각의 coverage·overflow를 내지만 좌우 차 한 값으로 묶지 않는다.** 그래서 대칭 보정은 아이라이너·섀도우·볼터치 3부위 평균이 된다. 입술도 `LIP_LR_DIFF` 코드는 내지만 수치는 없다.

**대안:** `browResult`에 `lrDiff = |R.coverage − L.coverage|` 또는 꼬리 높이 차(눈 폭 비율)를 하나 추가하고 `symmetryPenalty`가 `metrics.lrDiff`도 읽게 한다. 반나절. 정의서와 정확히 맞추려면 이것이고, 안 맞춰도 보정 방향은 유지된다. 이름은 `lrDiffMm`이 **비율 값**을 담고 있어(`189e42c` 이후) 통합 때 `lrDiffRatio`로 바꿔야 혼동이 없다.

### ③ "내 화장" 사진 — 새로 찍지 않는다

정의서 6-4는 "리뷰 진입 시 품질 게이트 통과 프레임 1장"이다. POC는 **마지막 부위의 확인받기 프레임**(`S.lastFrame`)을 그대로 쓴다. 보통은 쉐딩 확인받기 프레임이라 문제없지만, 마지막 부위를 건너뛰면 그 전 부위 프레임(예: 볼터치 단계, 아직 쉐딩 전)이 "내 화장"으로 나온다. 크롭은 그 프레임의 랜드마크(`S.result.pts`)로 잡으므로 정렬 자체는 맞다.

|  | 대안 | 비용 · 효과 |
| --- | --- | --- |
| (a) | 리뷰 진입 직전에 화면 4 게이트를 한 번 더 돌려 정면 프레임 1장을 찍는다 | 게이트·촬영 코드 재사용. 사용자에게 "정면을 봐 주세요" 1~2초. 정의서 그대로. **권장** |
| (b) | 마지막으로 **확인받기를 실제로 통과한** 부위의 프레임을 쓴다(건너뛴 부위 제외) | 코드 1줄. 다만 그 프레임은 부위 크롭 중심이라 얼굴 전체가 안 들어올 수 있음 → 비교 크롭이 잘릴 위험 |
| (c) | 내 화장 없음 상태를 허용하고 "정면을 보면 내 화장 사진을 찍어요" + 재시도 버튼 | 정의서 C-1이 이미 이 문구를 요구. (a)의 실패 경로로 같이 넣는다 |

**비교 정렬 3%:** 두 크롭은 각자의 랜드마크로 박스를 잡으므로 눈 중심은 박스 안 같은 비율 위치에 온다. 단, 박스 폭이 "랜드마크 x 최소~최대"라 고개를 조금 돌리면 폭이 달라져 가로 방향이 밀린다. 눈 중심 좌표 차를 실제로 찍어 보는 게 남았다(단독 POC 사진 탭에 계산기가 있음).

### ④ 결과 저장 — iOS는 "갤러리 자동 저장"이 없다

캔버스 한 장 → `navigator.share({files})` → 실패·미지원이면 `<a download>`. 동작 범위:

| 환경 | Web Share(파일) | 다운로드 폴백 | 결과 |
| --- | --- | --- | --- |
| Android Chrome | 지원 | 지원 | 공유 시트에서 "사진에 저장" 또는 다운로드 폴더. **갤러리에 남음** |
| iOS Safari 15+ | 지원 (HTTPS + 사용자 제스처 필수) | 파일 앱으로 감(사진 아님) | 공유 시트에서 사용자가 "이미지 저장"을 눌러야 사진 앱에 들어감. **자동 저장 불가** |
| 데스크톱 | 대부분 미지원 | 지원 | 다운로드 |

**대안:** 기술로 넘을 수 없다(브라우저가 사진 앱 쓰기 권한을 안 준다). 저장 버튼 옆에 "공유 시트에서 이미지 저장을 누르세요" 안내 한 줄, 그리고 공유 취소(`AbortError`) 시 토스트 없이 조용히 돌아오기(이미 구현). 정의서 6-5의 "갤러리 저장"을 "공유 시트로 저장"으로 고친다.

### ⑤ 세션 복원 — 사진이 없다

draft는 `stripImages`로 이미지를 뺀 JSON을 localStorage에 저장한다. 새로고침·탭 종료 뒤 돌아오면 점수·상태·한 줄 평은 살아 있지만 쌩얼·내 화장 캔버스는 사라져 비교 칸이 "사진 없음"이 되고, 결과 저장 카드도 사진 없이 나온다.

**대안:** 쌩얼 1장 + 최종 프레임 1장만 IndexedDB에 Blob으로 저장(긴 변 1024, WebP 0.85 → 장당 100~200KB). 전체 POC README "아직 못 하는 것"에 이미 적힌 항목이고, 화면 4·5의 세션 복원과 같은 저장소를 쓰면 된다. 끝내기 때 같이 지운다. 하루.

### ⑥ 진단 코드표 불일치

`review.js`의 `DIAG_TEXT`(11개)와 `score.js`가 실제로 내는 코드(`LINER_GAP_R`, `LINER_OUT_L`, `LINER_THIN`, `BROW_TAIL_SHORT_R`, `BROW_OUT_L`, `BROW_SPARSE`, `LIP_OUT_UPPER`, `LIP_UNDER`, `LIP_LR_DIFF`, `CHEEK_LR_DIFF_R`, `SHADOW_LR_DIFF_L`, `TONE_*` …)가 다르다. 지금은 `oneLiner`가 채점이 만든 `diagnosis` 문장을 우선 쓰므로 화면에는 문제가 없지만, 코드로 집계하는 순간(기록 화면 `topMisses`, 결과 카드) 절반이 빈다.

**대안:** 코드표를 `score.js` 한 곳에만 두고 `review.js`는 가져다 쓴다. 정의서 C-3 2번("코드 목록 합의")이 바로 이것. 통합(§4-E) 때 처리.

## 4. 실제 구현에서 생길 문제 · 해결 · 기술

화면 6은 카메라·서버가 없어 화면 5보다 조용하지만, **저장·삭제·복원**이 실기기에서 처음 부딪히는 곳이다.

### A. 저장 · 공유

| 문제 | 해결 | 기술 |
| --- | --- | --- |
| Web Share는 **사용자 제스처 안에서만** 호출 가능. 캔버스 그리기·이미지 로딩(`await loadImage`)이 끼면 iOS가 제스처를 잃고 `NotAllowedError` | 카드 이미지를 리뷰 진입 시 **미리** 만들어 두고, 버튼 클릭 핸들러 안에서는 `share`만 호출 | `toBlob` 결과를 `S.shareFile`에 캐시. 부위 재확인 후 리뷰 복귀 시 재생성 |
| 캔버스에 한글 폰트가 기기마다 달라 카드 줄바꿈이 깨짐 | `sans-serif` 대신 웹폰트를 명시하고 `document.fonts.ready` 후 그린다. 한 줄 평은 40자 잘라내기 대신 폭 기준 말줄임 | `measureText`로 폭 계산 |
| 1080×1350 JPEG 0.9가 300~500KB — 공유 시트로 넘기기엔 충분하지만 저가 기기 캔버스 메모리에 부담 | 해상도 유지, 품질 0.85. 그리기 끝나면 캔버스 참조 해제 | — |
| HTTP(개발 서버)에서는 `navigator.share`가 없어 **폴백만 테스트됨** | HTTPS 실기기 환경(화면 5 검토 §9-2와 같은 요구) | mkcert |

### B. 세션 · 삭제

| 문제 | 해결 | 기술 |
| --- | --- | --- |
| "끝내기"를 안 누르고 탭을 닫으면 draft가 남는다 | 시작 화면에서 오래된 draft(예: 2시간)를 자동 폐기하고, 남아 있으면 "이어서 할까요?"를 묻는다 | draft에 `updatedAt`, 시작 시 검사 |
| IndexedDB에 사진을 넣으면 **"끝내기 → 잔존 0"** 검증 범위가 넓어진다 | 끝내기에서 localStorage + IndexedDB 스토어 + 메모리 세 곳을 한 함수로 지우고 테스트에 IndexedDB 검사 추가 | `indexedDB.deleteDatabase` 또는 스토어 clear |
| 브라우저 저장소 정리(iOS 7일 미사용 삭제, 용량 압박)로 draft가 사라짐 | 유실은 허용. "처음부터"로 안내. 기록이 아니므로 손실이 작다 | `navigator.storage.persist()` 요청(효과는 기기 따라) |
| 사진 Blob을 리뷰까지 들고 있으면 모바일 Safari 메모리 한계 | 쌩얼 원본은 기준 생성 후 폐기(원칙), 비교용은 **크롭 360×440만** 보관 | `ImageBitmap.close()` |

## 5. 쓸 수 있는 기술

새 모델은 없다. 브라우저 API만이다.

| 역할 | 기술 | 지원 | 상태 |
| --- | --- | --- | --- |
| 합산·보정·한 줄 평 | 순수 JS 함수 | 전부 | **이미 씀** (테스트 포함) |
| 비교 크롭 | Canvas 2D `drawImage` + MediaPipe 랜드마크(화면 4·5 것) | 전부 | **이미 씀** |
| 결과 카드 | Canvas 2D → `toBlob` | 전부 | **이미 씀** |
| 갤러리 저장 | Web Share API Level 2 (`navigator.share({files})`) | Android Chrome, iOS Safari 15+, HTTPS 필수 | **이미 씀** · 폰 미검증 |
| 저장 폴백 | `<a download>` + Blob URL | 전부 (iOS는 파일 앱) | **이미 씀** |
| 세션 임시 저장 | localStorage(JSON) → **IndexedDB(Blob 포함)로 승격** | 전부 | JSON만 |
| 세션 삭제 | `localStorage.removeItem` · IndexedDB clear | 전부 | localStorage만 |
| 기록 화면(로드맵) | IndexedDB + Canvas 꺾은선 | 전부 | 단독 POC에 함수·테스트만 |

## 6. 가장 큰 미검증 구멍 — 보정값과 실기기

### 보정이 실제로 작동하는지

대칭 보정은 정의서 A-5에 "한쪽만 진하게 바른 사진 세트(팀원 자가 촬영 10장)에서 0 미만, 양쪽 같게 바른 세트에서 0~−1"이라는 통과 기준이 있다. 지금 통과한 B2·B3는 **숫자를 손으로 넣은 합성 입력**이다. 실제 사진에서는 화면 5가 내는 `lrIndex`가 좌우 조명 불균형(창가에서 한쪽 볼이 밝음)을 좌우 차로 오인할 수 있고, 그러면 대칭 보정이 **조명을 벌점한다.** 화면 5 검토 §3-①(b)의 "인접 피부 대비" 정의로 가면 이 문제가 같이 사라진다. 화면 6이 화면 5 결정에 종속된 유일한 지점이다.

### 실기기에서 아직 안 눌러 본 것

| 항목 | 지금까지 | 확인할 것 |
| --- | --- | --- |
| 결과 저장 공유 시트 | 데스크톱 다운로드 폴백만 | iOS·Android 각 1대에서 공유 시트가 뜨고 사진 앱에 들어가는지, 제스처 오류가 없는지 |
| 카드 렌더링 | 헤드리스 크롬 스크린샷 | 폰 폰트에서 한 줄 평 잘림·줄바꿈 |
| 세션 복원 | 새로고침 + JSON 왕복 | 백그라운드 전환 후 복귀(iOS 탭 리로드), 사진 유실 여부 |
| 비교 정렬 3% | 육안 | 눈 중심 좌표 차를 숫자로 (단독 POC 사진 탭 계산기) |
| 끝내기 잔존 0 | localStorage만 | IndexedDB 도입 후 세 저장소 모두 |

## 8. 먼저 할 것 — 순서

1. **채점 모듈에서 값 두 개 넘기기.** 볼터치·입술 `colorAb`, 눈썹 `lrDiff`. 각 몇 줄. 이걸로 정의서의 보정 둘이 실제로 켜진다. 조화 허용 범위는 룩 확정 전까지 null.
2. **리뷰 진입 시 정면 프레임 1장 촬영** (§3-③ a). 게이트 재사용. 실패 시 "정면을 보면 내 화장 사진을 찍어요" + 재시도.
3. **IndexedDB에 쌩얼·최종 프레임 저장** (§3-⑤). 끝내기에서 같이 삭제. 화면 4·5 세션 복원과 저장소 공유.
4. **HTTPS 실기기에서 결과 저장·복원 확인** (§6). iOS·Android 각 1대. 화면 5 검토가 요구하는 환경과 같으므로 같은 날.
5. **팀원 자가 촬영 10장으로 대칭 보정 방향 검증.** 화면 5의 실촬영 세트(전/후 두 장 × 3명)에 "한쪽만 진하게" 2장을 얹으면 된다.

### 정리

- **지금 확정 가능**: 합산·보정 수식, 막대·한 줄 평, 비교 크롭, 결과 카드, Web Share + 다운로드 폴백, 끝내기. 새 모델·새 라이브러리 없음
- **고쳐야 함**: 조화 보정 입력 연결, 눈썹 좌우 차, "내 화장" 프레임 새로 촬영, 사진 포함 세션 복원, 코드표 한 곳으로
- **넘을 수 없음(안내로 처리)**: iOS 갤러리 자동 저장 → 공유 시트 안내
- **문서에서 고칠 것**: 6-5 "갤러리 저장" → "공유 시트로 저장(iOS는 사용자가 저장)"; A-3 대칭 입력에 눈썹 좌우 차 **정의**(coverage 차인지 꼬리 높이 차인지) 명시; A-3 조화 보정 "템플릿 범위 확정 전 미적용" 명시; C-3 4번 세션 임시 저장을 "IndexedDB(사진 2장 포함)"로 고정; `lrDiffMm` → `lrDiffRatio` 이름 정리(`189e42c` 후속)
