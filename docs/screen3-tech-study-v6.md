# 화면 3 부위 완성본 — 기술 공부 노트 (v6, 2026-09-17)

> **목적:** 화면 3에 들어가는 기술 8개를 "왜 들어가나 → 어디에 들어가나 → 무엇을 쓰나 → 되나 → 안 되면" 순서로 하나씩 익히는 문서.
> 근거·출처 원문은 `screen3-tech-v6.md`, 한눈 요약은 `screen3-summary-v6.md`, 코드는 `poc/screen3/`.

## 0. 먼저 전체 흐름 — 기술이 어디에 끼는지

화면 3은 아래 한 줄짜리 파이프라인이다. **기술 8개가 각 화살표에 하나씩 붙는다.**

```
촬영 1에서 저장한                      화면 2-b에서 받은
정면 사진 + 랜드마크 468점              전체 완성 렌더(fullRender)
        │                                    │
        ▼ ① 크롭 박스 계산                     ▼ ② 완성본 이미지 만들기 (해상도 쟁점)
   "이 부위는 사진의 여기부터 여기"          "무엇을 줌할 것인가: 렌더? 원본+레이어?"
        │                                    │
        └──────────────┬─────────────────────┘
                       ▼ ③ 확대해서 화면에 그리기
                       ▼ ⑤ 방향 감지 (가로/세로 안내)
                ┌──────┴──────┐
                │  완성본 이미지 │  ← ④ 진행 칩 6개 (세션 상태)
                │             │  ← ⑥ 근거 한 줄 · 지금 필요한 것 (콘텐츠)
                │             │  ← ⑦ 3-c 쉐딩 테두리 (얼굴형 규칙)
                └─────────────┘
                       ▼ ⑧ 완성본 보관 (부위 6개가 같은 한 장을 씀)
                    [그리러 가기] → 화면 4
```

**기술 종류는 네 가지뿐이다.** 이 분류를 알면 "이게 어려운 기술인가"가 바로 보인다.

| 종류 | 뜻 | 화면 3에서 |
|---|---|---|
| **웹 표준** | 브라우저에 이미 있는 API. 라이브러리 설치 없음 | ③ ④ ⑤ ⑧ |
| **규칙(순수 함수)** | 입력→출력이 정해진 계산. 모델 없음, 테스트 가능 | ① ⑦ |
| **CV(컴퓨터 비전)** | 이미지 처리·모델. 화면 3에서는 **남이 만든 결과를 재사용**만 | ② |
| **데이터(콘텐츠)** | 사람이 써 두는 문장·목록 | ⑥ |

**새로 학습하는 모델은 없다.** 화면 3의 어려움은 "기술을 만드는 것"이 아니라 "이미 있는 것을 어떻게 이어 붙이느냐"다.

## ① 부위 크롭 박스 계산

| | |
|---|---|
| **왜 들어가나** | "눈썹 단계면 눈썹 주변만, 입술 단계면 입술 주변만" 보여줘야 한다. 완성본 한 장에서 **어느 사각형을 잘라낼지** 정하는 계산 |
| **어디에 들어가나** | 입력: 촬영 1의 랜드마크 468점 + 부위 ID + 화면 종횡비 → 출력: `{x, y, w, h}` 사각형. 화면 3에 들어올 때 한 번 |
| **기술 종류** | 규칙(순수 함수). 라이브러리 없음 |
| **무엇을 쓰나** | MediaPipe 468점 인덱스 중 부위별 점(눈 바깥끝 33·263, 입술 외곽 20점 등)의 최소·최대 좌표 → 여백 15~18% → 화면 비율에 맞춰 **넓히기만** 함(절대 줄이지 않음) → 사진 밖으로 나가면 안으로 밀기 |
| **실현 가능성** | ✅ **구현 완료.** `poc/screen3/crop.js`, 검증 29개 통과. 실측: 입술은 2~3배 확대되지만 눈 3부위는 양쪽 눈이 넓어서 1.0~1.1배 (문서의 "2~3배 확대"는 입술에만 해당) |
| **이유 (왜 이 방식)** | 랜드마크가 이미 있으므로 계산만 하면 된다. 모델을 돌리면 시간·실패 가능성이 생긴다 |
| **대안** | 없음이 정답. 굳이 들면 얼굴 파싱 마스크의 경계 사각형 — 하지만 서버 왕복이 생기고 화면 3엔 과함 |
| **차선책 (실패 시)** | 랜드마크가 없으면 **얼굴 중앙 고정 크롭**. 그러나 화면 1에서 검출 실패는 이미 걸러지므로 화면 3까지 오면 항상 있다 |
| **주의** | `faceWidth`(얼굴 윤곽 234↔454)와 `eyeSpan`(눈 바깥끝 33↔263, 얼굴 너비의 0.69배)을 구분할 것. 처음에 섞어 써서 고쳤다 |

## ② 완성본 이미지 만들기 — 가장 큰 쟁점

| | |
|---|---|
| **왜 들어가나** | 사용자가 **보고 따라 그리는 기준**이다. 선이 뭉개지면 화면 3의 존재 이유가 없다. 화면 5 채점도 이 기준으로 한다 |
| **어디에 들어가나** | 화면 2-b(룩 확정) 직후 한 장 만들어 두고, 화면 3 여섯 부위가 전부 이 한 장을 ①로 잘라 쓴다 |
| **기술 종류** | CV. 단 화면 3이 새로 만드는 건 없고 **F-03(실시간 트래킹)·F-04(서버 렌더)의 결과물을 고른다** |
| **문제** | 서버 렌더는 512×512. 눈 단계는 양쪽 눈을 가로 화면에 꽉 채우므로 **7.4배 확대**(iPhone 15 가로 기준). 아이라이너 선이 뭉개짐 |
| **실현 가능성** | ⚠️ 512 줌 자체는 되지만 품질이 안 나온다. 그래서 대안이 필요 |

### 대안 5개 — 무엇이 다르고 왜 이 순서인가

| 순위 | 방법 | 배율 | 새 모델 | 라이선스 | **왜 이 순위인가** |
|---|---|---|---|---|---|
| **1** | **C. 원본 사진 + 화장 레이어** | 3.6배 | 없음 | — | F-03이 이미 "화장만 떼어낸 레이어"를 만든다(카메라 영상에 매 프레임 씌우는 그것). 같은 레이어를 원본 정면 사진(1080×1920)에 **한 번** 씌우면 완성본. 실제 촬영 픽셀이라 속눈썹·피부가 진짜. v6 확정("전체 렌더 줌, 지나온 부위도 화장됨")을 안 깬다. **추가 비용 0** |
| **2** | **D. 타일 확산 업스케일 512→1024** | 3.7배 | SDXL 1회 | Apache-2.0 (MoD Control Tile Upscaler) | 초해상과 다르게 **원본 렌더를 조건으로 걸고** 타일별로 다시 그린다 → 지어내는 방식이 렌더와 일관됨. 단점: 서버에서 10~20초 더. **룩당 3초 제약은 화면 2 썸네일 얘기라 여기엔 안 걸림** |
| 3 | 서버 렌더 512 줌 (지금 문서 방식) | 7.4배 | 없음 | — | 가장 단순. 위 둘이 안 되면. 눈 단계 여백을 늘려 확대율을 낮추는 꼼수 가능 |
| 발표용 | E. 눈 부위만 따로 생성 (FRAM, CVPR 2026) | 무손실 | 확산 1종 | **비상업** | 부위별로 512로 만들면 확대 문제 자체가 사라짐. 하지만 v6 결정("따로 합성 안 함")을 다시 열어야 하고 사업화 불가 |
| 최후 | 룩 참조 이미지 그대로 | — | 없음 | — | 내 얼굴은 아니지만 빈 화면보다 낫다 |
| ✗ | 초해상 (GFPGAN·CodeFormer) | — | 1종 | GFPGAN Apache / CodeFormer 비상업 | **안 쓴다.** 저해상 사진만 보고 디테일을 지어낸다. 8배 근처가 위험 구간이라는 논문이 2025년에도 계속 나옴(AuthFace·HonestFace 등). 지어낸 아이라이너를 따라 그리면 우리 가이드가 아님. D가 있으니 쓸 이유 없음 |

| | |
|---|---|
| **결정 방법** | 숫자 하나. F-03 수용 기준에 이미 있는 **"서버 렌더 대비 색 차이 ΔE 평균"**. 1주차 검증 5에서 C의 ΔE와 D의 처리 시간·얼굴 유사도를 같이 잰다 |
| **그전까지** | 512 줌으로 만들어 두되 **완성본을 읽는 함수를 한 군데**(`LookSelection.fullRender` 읽는 곳)로 모아 나중에 갈아끼운다. PoC는 지금 정면 사진을 그 자리에 넣어 돌아간다 |
| **차선책 (런타임)** | 서버가 렌더를 못 주면 → 정면 사진 + 레이어 → 레이어도 없으면 **맨얼굴 + "완성 예상을 준비 중이에요"**. 절대 빈 화면·무한 로딩 없음 |

## ⑤ 화면 방향 감지 (가로/세로)

| | |
|---|---|
| **왜 들어가나** | 눈 3부위는 가로로 넓어서 가로 화면, 입술·볼·쉐딩은 세로 화면이 크게 보인다. 화면 3·4·5가 같은 방향을 쓴다 |
| **어디에 들어가나** | 화면 3 진입 시와 기기 회전 시. "폰을 가로로 돌리세요" 안내 → 맞으면 닫음 |
| **기술 종류** | 웹 표준 |
| **1순위** | **`window.matchMedia('(orientation: portrait)')` 에 `change` 리스너** |
| **실현 가능성** | ⚠️ 감지는 된다. **잠금(`screen.orientation.lock()`)은 iOS 사파리에 없다** → 잠그지 않고 안내만 |
| **이유** | `screen.orientation`의 `change` 이벤트가 **iOS 사파리에서 안 먹는다.** 옛 `orientationchange`는 폐기 예정. 그래서 `matchMedia`가 1순위 |
| **대안** | 안드로이드 네이티브 앱이면 잠글 수 있음 (웹에선 불가) |
| **차선책 (런타임)** | 6초 안내해도 안 돌리면 **그냥 보여준다** + "가로로 돌리면 더 크게 볼 수 있어요" 한 줄. 계속 막지 않는다. 확대율 손해는 "가로 부위를 세로로 볼 때"만 생김(짧은 변에 맞춰 들어가므로) |
| **상태** | `poc/screen3/orientation.js` **초안만** (순수 함수 4개). `app.js` 연결·검증 미완 |

## ⑦ 3-c 쉐딩·하이라이트 테두리

| | |
|---|---|
| **왜 들어가나** | 룩 템플릿은 눈썹·라이너·섀도우·입술·볼터치만 담는다. **쉐딩·하이라이트는 완성 렌더에 없다.** 얼굴형 규칙에서 오므로 따로 그려야 한다 |
| **어디에 들어가나** | 3-c 단계만. 완성본을 얼굴 아래쪽(광대~턱)으로 줌 + **규칙 자리를 점선 테두리로만** (색 면 채우기 없음, 라벨 "쉐딩"·"하이라이트") |
| **기술 종류** | 규칙 + 웹 표준 |
| **무엇을 쓰나** | Canvas 2D `Path2D` + `setLineDash()` (또는 SVG `<polyline>`). 좌표는 얼굴형 5분류(F-02, 랜드마크 비율 규칙) × 얼굴형별 쉐딩 위치 규칙 |
| **실현 가능성** | ⚠️ 그리기는 확실. **규칙 5종이 없다.** 기술이 아니라 콘텐츠가 막힘 |
| **근거는 있나** | 있다. 얼굴형 5분류 정의: Zhao 2020(Cognitive Neurodynamics) — 하트·장형·계란·원형·각진, 우리와 이름까지 같음. 쉐딩 원리: 2021 CHM 논문 — 어두운 색 후퇴·밝은 색 돌출. **구체 위치**만 업계 교재 3곳 모아 공통분모 |
| **대안** | 서버 법선 맵(DSINE)은 라이선스 위험 → MediaPipe 3D 메시로 대체 검토 |
| **차선책 (런타임)** | 규칙 없음 → 랜드마크 근사 테두리 → 테두리 없이 **얼굴형 멘트만**. 3-c 단계를 건너뛰진 않는다 |
| **⚠️ 특허** | US 10,650,224 B2 (Anastasia Ipco, 2036년까지 유효). 얼굴 측정으로 컨투어 가이드라인 · **홍채 지름 척도** · 가이드 준수 점수 — 우리 3-c·mm 척도·채점과 겹침. 발표는 무관, 사업화 시 회피 설계 |

## 10. 자주 받는 질문 — 이렇게 답한다

**Q. 화면 3에 AI 모델이 들어가나요?**
A. 새로 만드는 건 없습니다. 서버가 만든 완성 렌더와 F-03이 만든 화장 레이어를 **가져다 쓰기만** 합니다. 화면 3 자체는 계산·표시·콘텐츠입니다.

**Q. 왜 랜드마크를 다시 안 뽑나요?**
A. 촬영 1에서 이미 뽑아 저장했고, 화면 3은 정지 이미지라 얼굴이 안 움직입니다. 다시 뽑으면 시간과 실패 가능성만 생깁니다. 검출 실패는 화면 1에서 이미 걸러졌습니다.

**Q. 512 렌더를 그냥 키우면 안 되나요?**
A. 눈 단계는 7.4배라 아이라이너 선이 뭉개집니다. 사용자가 **따라 그리는 기준**이라 품질이 곧 기능입니다. 원본 사진에 레이어를 얹으면(대안 C) 3.6배로 절반이고 추가 비용이 없습니다.

**Q. 초해상(업스케일 AI)을 쓰면 되지 않나요?**
A. 초해상은 저해상 사진만 보고 디테일을 **지어냅니다.** 8배 근처가 위험 구간이라는 논문이 2025년에도 나옵니다. 지어낸 선을 사용자가 따라 그리면 우리 가이드가 아닙니다. 필요하면 원본을 조건으로 거는 타일 확산(대안 D)을 씁니다.

**Q. 룩당 3초 제약 때문에 큰 모델은 못 쓰지 않나요?**
A. 그 제약은 화면 2 썸네일 10개에 걸린 겁니다. 화면 3 완성본은 룩 확정 뒤 **한 장**이라 10~20초를 얹을 수 있습니다.

**Q. 근거 문장은 왜 LLM으로 안 만들죠?**
A. 룩마다 고정 문장이라 매번 생성할 이유가 없고, 계획에 없는 모델을 늘리지 않으며, 폰 예산과 서버 비용을 아낍니다. 55문장을 사람이 씁니다.

**Q. 쉐딩은 왜 완성본에 안 보이나요?**
A. 룩 템플릿에 쉐딩이 없어서 렌더에도 없습니다. 얼굴형 규칙으로 점선 테두리만 그립니다. 기술은 되는데 **얼굴형별 위치 규칙 5종이 아직 없습니다.**

**Q. 서버가 늦으면 화면 3은 못 만드나요?**
A. 아닙니다. 정면 사진을 완성본 자리에 넣으면 지금 바로 만들 수 있고, PoC가 그 상태로 돌아갑니다. 서버·레이어·문장·규칙이 전부 없어도 맨얼굴 + 기본 문장으로 화면이 뜨게 사다리가 있습니다.

**Q. iOS에서 화면을 가로로 고정할 수 있나요?**
A. 못 합니다. 사파리에 잠금 API가 없습니다. 안내하고, 6초 지나면 그냥 보여줍니다.

## 11. 1주차에 결판나는 것 3개

1. **ΔE 평균** (원본+레이어 vs 서버 렌더) → 대안 C 채택. 같이 D의 처리 시간·얼굴 유사도.
2. 눈 단계 완성본을 **실제 폰 가로 화면에서** 확인 — 7.4배가 정말 못 쓸 수준인지.
3. 얼굴형별 쉐딩 규칙 출처 3곳 → 공통분모 → 규칙 5종.
