# 화면 3 POC — 설계 (2026-09-16)

> 당화응 화면 3(부위 완성본) 브라우저 POC의 설계 문서. 구현 계획은 별도.
> 근거 문서: `docs/impl-screen1-5-definition-v6.md` 3-1·3-2, `docs/feature-spec-v6.md` F-05·F-06, `docs/screen-image-brief-v6.md` 화면 3·3-c.

## 1. 배경

화면 3은 부위마다 "이 부위가 다 되면 어떤 모습인지" 정지 이미지로 먼저 보여주는 화면이다. v6에서 이 이미지는 **전체 완성 예상 렌더링(화면 2-b)을 해당 부위 크롭 박스로 줌한 것**으로 확정됐다(별도 합성 없음). 따라서 화면 3에서 실제로 계산이 일어나는 곳은 두 군데뿐이다.

1. **부위별 크롭 박스** — 어디를 얼마나 확대해 잘라낼 것인가
2. **쉐딩·하이라이트 규칙 윤곽선** — 룩 렌더링에 없는 유일한 부위라 얼굴형 규칙으로 자리를 만들어 테두리로 그린다

나머지(근거 한 줄, 필요한 제품, 진행 칩, 방향 안내)는 템플릿 데이터 표시다.

문서에 적힌 크롭 수치는 아직 가정값이다 — 눈 단계 "양쪽 눈 끝에서 끝 + 여백 15%", 세로 부위 "2~3배". 이 값들이 실제 얼굴에서 성립하는지 확인된 적이 없다.

### 종횡비 충돌

샘플 세트(`danghaeung_poc_3x4_20/`)는 셀카 **3:4 세로(0.75:1)**, 1080×1440이다. 폰 화면은 **세로 9:19.5(0.46:1)** 또는 **가로 19.5:9(2.17:1)**다. 크롭 박스를 화면 종횡비에 맞춰 늘리면 원본 경계를 넘길 수 있다.

| 부위 | 개략 계산 | 예상 |
|---|---|---|
| 눈 단계(가로) | 눈 끝 폭 약 480px, +15% → 552px. 19.5:9이면 높이 255px. 눈+눈썹 약 120px | 성립 |
| 입술·볼(세로, 2.5배) | 크롭 폭 약 430px → 높이 932px 필요. 입술 중심 y 약 950 | 경계에 근접 |
| 쉐딩·하이라이트(광대~턱) | 위보다 아래에 있어 여유가 더 적음 | 잘릴 가능성 |

**이 POC의 1차 질문**: 문서의 여백·배수 가정값이 3:4 셀카에서 성립하는가. 성립하지 않으면 어떤 값으로 바꿔야 하는가.

## 2. 목적

1. 부위 6개 크롭 박스를 랜드마크로 계산하고, 샘플 20장에서 잘림·확대율을 실측한다
2. 얼굴형 label을 받아 쉐딩·하이라이트 윤곽선을 생성한다
3. 위 계산으로 화면 3·3-c 목업을 실제로 그려, 가로↔세로 전환을 포함한 흐름을 팀이 눈으로 확인한다

## 3. 범위

**한다**: 부위 6개 크롭 박스 계산 · 얼굴형 5종 쉐딩·하이라이트 윤곽선 생성 · 근거/제품 문장 · 화면 3·3-c 폰 목업(가로·세로) · 진행 칩 6개 · 방향 안내 · 샘플 20장 일괄 검증 표 · Node 자동 검증

**하지 않는다**: 실시간 카메라·추적(화면 4) · 채점(화면 5) · **얼굴형 판정(파트 1 담당, label을 입력으로 받는다)** · 서버 화장 전이 · 법선 맵(`source: 'landmark_only'` 고정) · 룩 10개(스모키 1개만) · 세션 저장·복원

## 4. 입력

| 입력 | 출처 | 비고 |
|---|---|---|
| 얼굴 이미지 | `danghaeung_poc_3x4_20/` 20장 바로 불러오기 + 업로드 슬롯 | 1080×1440, 홍채 약 70px로 척도 요건(25px) 충족 |
| 랜드마크 468+10점 | MediaPipe Face Landmarker (CDN) | 브라우저에서만. Node 테스트는 `fixtures.json` 사용 |
| 얼굴형 label | 드롭다운 5종 | **파트 1(F-02)이 주입할 자리.** POC에서는 수동 선택 |
| 룩 템플릿 | `rules.js` 스모키 1개 | 제품 목록·근거 문장 |

샘플 20장은 **맨얼굴**이다. 크롭 계산 검증에는 충분하지만 "완성본"으로는 보이지 않는다. 화장을 입힌 정면 이미지가 준비되면 업로드 슬롯으로 교체한다.

## 5. 구조

`poc/screen6/`의 관례를 따른다.

```
poc/screen3/
  core.js            순수 함수. 이미지·캔버스·MediaPipe를 모른다
  rules.js           데이터. 룩 템플릿·얼굴형 규칙·문장 템플릿
  fixtures.json      샘플 20장의 랜드마크 (Node 테스트 오프라인 실행용)
  tests.mjs          node tests.mjs
  tests-browser.js   같은 케이스의 브라우저 러너
  index.html         폰 목업 + 시연 패널
  app.js             MediaPipe 로딩·업로드·렌더 (DOM)
  style.css
  screenshots/
  README.md
```

`core.js`의 입력은 랜드마크 배열·이미지 크기·partId·faceShape이고 출력은 숫자뿐이다. 그래서 Node에서 픽스처로 돌아가고, 앱으로 옮길 때 그대로 간다.

## 6. core.js API

```js
cropSpec(landmarks, imgSize, partId, opts) -> {
  x, y, w, h,          // 원본 픽셀 좌표
  orientation,         // 'landscape' | 'portrait'
  aspect,              // 목표 종횡비 (19.5/9 또는 9/19.5)
  zoomRatio,           // imgSize.w / w — 몇 배 확대인가
  covered,             // 기준 랜드마크가 전부 박스 안인가
  clamped,             // 경계에 닿아 조정됐는가
  clampedSides         // ['top','bottom','left','right']
}

contourOutline(landmarks, faceShape, mmPerPx) -> {
  shading: [[x,y], ...],     // 폴리곤, 원본 이미지 픽셀 좌표
  highlight: [[x,y], ...],
  labels: [{ text: '쉐딩', anchor: [x,y] }, { text: '하이라이트', anchor: [x,y] }],
  source: 'landmark_only'
}

rationale(partId, faceShape) -> string      // 숫자 없는 근거 한 줄
products(partId) -> string                  // "지금 필요한 것: …"
```

`mmPerPx`는 홍채 지름 11.7mm 기준으로 계산한다(`poc/app.js`의 `irisScale`과 같은 방식).

## 7. 크롭 박스 규칙

### 기준 랜드마크

| partId | 방향 | 기준 랜드마크 |
|---|---|---|
| `brow` | 가로 | 양쪽 눈썹 전체 + 눈 바깥 끝(33·263) |
| `liner` | 가로 | 양쪽 눈 윤곽 + 눈 바깥 끝 |
| `shadow` | 가로 | 양쪽 눈 윤곽 + 눈두덩(눈썹 아래 ~ 눈 위) |
| `lip` | 세로 | 입술 외곽 20점 |
| `cheek` | 세로 | 양쪽 광대 다각형 |
| `contour` | 세로 | 광대 ~ 턱선 |

구체적 인덱스는 `core.js` 상수로 두고, 구현 단계에서 샘플 20장에 그려 눈으로 맞는지 확인한 뒤 확정한다(MediaPipe 인덱스는 문서마다 조금씩 달라 실물 확인이 필요하다).

### 알고리즘

1. partId의 기준 랜드마크로 바운딩 박스를 만든다
2. 여백을 적용한다
   - 가로 부위: 폭 양쪽에 각 15% (문서값)
   - 세로 부위: 목표 확대율(기본 2.5배)로 크롭 폭 = `imgW / 2.5`
3. 목표 종횡비에 맞춰 부족한 축을 중심 유지로 늘린다
4. 이미지 경계를 넘으면 **먼저 안쪽으로 이동**하고, 이동만으로 안 되면 **축소**한다. 축소가 일어나면 `clamped = true`
5. 기준 랜드마크가 최종 박스 안에 전부 있는지 확인해 `covered`를 채운다

이동을 먼저 시도하는 이유는 확대율을 최대한 유지하기 위해서다. 축소가 발생했다는 것은 곧 문서의 가정값이 이 사진에서 성립하지 않는다는 신호다.

## 8. 쉐딩·하이라이트 규칙 (초안)

`rules.js`에 **데이터로** 둔다. 얼굴형마다 `{앵커 랜드마크, mm 오프셋, 방향}` 목록이고, 코드는 그것을 폴리곤으로 변환만 한다. 규칙을 고칠 때 코드를 건드리지 않게 하기 위함이다.

| 얼굴형 | 쉐딩 | 하이라이트 |
|---|---|---|
| `oval` 계란형 | 광대 아래 얕게 | 광대 위, 콧대 |
| `round` 둥근형 | 턱선 + 광대 아래(길게) | 광대 위, T존 |
| `square` 각진형 | 턱 모서리 + 이마 양옆 | 광대 위, 턱 중앙 |
| `oblong` 긴형 | 이마 상단 + 턱 끝(가로로) | 광대 위(가로로 넓게) |
| `heart` 하트형 | 이마 양옆 + 턱 끝 | 광대 위, 눈 밑 |

근거 문장도 얼굴형별 템플릿으로 둔다. 확정 문구 예: "둥근 얼굴형이라 턱선과 광대 아래에 쉐딩을, 광대 위에 하이라이트를 넣었어요".

> **이 5종은 전문가 검증 전 가정값이다.** `docs/README.md`의 "이후 확정할 것"에 "얼굴형별 쉐딩·하이라이트 규칙 5종"이 미정으로 남아 있고, 이 POC가 그 초안을 제시한다. `rules.js` 상단에 같은 취지를 주석으로 남긴다.

## 9. 폰 목업

`poc/screen6`과 같은 390×844 검정 베젤 폰. 단 **화면 3은 부위마다 가로·세로가 바뀐다** — 눈썹·아이라이너·섀도우는 844×390, 입술·볼터치·쉐딩·하이라이트는 390×844. 이 전환과 안내를 실제로 돌려 보는 것이 데모의 핵심이다.

| 요소 | 내용 |
|---|---|
| 진행 칩 6개 | 눈썹·아이라이너·섀도우·입술·볼터치·쉐딩·하이라이트. 상태(미시작/진행 중/완료/확인만/건너뜀), 진행 중 강조, 탭 이동 |
| 방향 안내 | 가로 부위 진입 시 "눈 단계는 양쪽 눈을 같이 봐요. 폰을 가로로 돌리세요", 세로 부위로 올 때 "이제 폰을 세로로 돌리세요" |
| 완성본 | 이미지를 `cropSpec` 박스로 줌한 정지 화면. 칩 "완성본" |
| 카드 | 근거 한 줄(숫자 없음) · "지금 필요한 것: …" · 버튼 "그리러 가기" |
| 3-c | 세로. 위 구성 + 규칙 윤곽선(청록 점선, 면 채우기 없음) + "쉐딩"·"하이라이트" 라벨 |

"그리러 가기"는 화면 4가 없으므로 토스트로 대체한다(화면 6 POC의 막대 탭과 같은 처리).

스타일은 `docs/screen-image-brief-v6.md` A절 그대로: 배경 #F7F5F1, 카드 흰색, 본문 #2B2B2B, 보조 #6B6B6B, 강조 청록 #2A8C85, 모서리 12px, 오버레이는 2px 선·점선만.

## 11. 검증

### 실측 (검증 탭)

- **covered** — 목표 100%. 미달이면 기준 랜드마크 집합이 잘못된 것
- **clamped** — 목표 0%. 발생하면 **문서의 여백·배수 가정값을 고쳐야 한다는 뜻**이므로, 표에 어느 부위·어느 사진에서 몇 px 모자랐는지 남긴다
- **zoomRatio** — 부위별 최소·중앙·최대. 세로 부위가 문서의 2~3배 범위에 드는지

정면 눈 뜸·눈 감음이 주 대상이다(화면 3은 정면 렌더링 기준). 눈 감은 장은 섀도우 단계의 눈꺼풀 기준이라 실제로 쓴다. 좌·우 45°는 화면 4로 넘길 때 쓸 참고치로 함께 기록한다.

### 자동 검증 16개 (`tests.mjs`)

크롭 8개
1. 부위 6개 각각 기준 랜드마크를 전부 포함한다(`covered`)
2. `liner` 폭이 눈 끝 폭의 1.3배다(양쪽 15%). `brow`·`shadow`는 바운딩에 세로 성분이 있어 3번 단계에서 폭이 더 늘 수 있으므로 이 케이스에서 제외한다
3. `orientation`이 부위 정의와 일치한다
4. 박스 종횡비가 목표 종횡비와 1% 이내로 일치한다
5. 박스가 이미지 밖으로 나가면 `clamped`와 `clampedSides`가 채워진다
6. 랜드마크·이미지를 2배로 키우면 박스도 2배가 되고 `zoomRatio`는 같다
7. 알 수 없는 `partId`는 예외를 던진다
8. 세로 부위 기본 `zoomRatio`가 2.5다

윤곽선 5개
9. 얼굴형 5종이 서로 다른 폴리곤을 낸다
10. 정면 랜드마크에서 좌우 대칭이다(허용 오차 내)
11. 폴리곤이 얼굴 바운딩 박스 안에 있다
12. 모르는 label은 `oval`로 폴백한다
13. `shading`·`highlight` 둘 다 비어 있지 않다

문장 3개
14. 근거 한 줄에 숫자가 없다(mm·각도·% 금지 규칙)
15. `contour` 근거가 얼굴형마다 다르다
16. 제품 한 줄이 `partId`로 걸러진다

`tests-browser.js`는 같은 케이스를 검증 탭에서 돌린다.

## 12. 완료 기준

- `node tests.mjs` 16/16 통과
- 샘플 20장 × 부위 6개에서 `covered` 100%
- `clamped` 비율을 표로 기록. 0%가 아니면 **어떤 여백·배수 값으로 바꾸면 0%가 되는지 제안까지** 산출물에 포함
- 스크린샷 5장: 눈 단계 가로 / 입술 세로 / 3-c 윤곽선 / 방향 안내 / 검증 탭
- `README.md`에 문서 검증 항목 ↔ POC 대응 표
