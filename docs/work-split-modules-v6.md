## 0-1. 브랜치 규칙

**작업은 자기 모듈 브랜치에서 한다.** `capture` `guide` `score` `server` `model` `app` 여섯 개.

- 자기 모듈 브랜치에 **직접 커밋**한다. 작업마다 브랜치를 새로 파지 않는다.
- **준비되면 PR 을 올리고 리뷰를 요청한다.** 정기 병합일은 없다. 특히 다른 모듈이 기다리는 것(★ blocker)은 끝나는 대로 바로 올린다 — 들고 있으면 남이 그만큼 못 쓴다.
- **리뷰와 병합은 ⑥ 이 한다.** 가능할 때 작성자 브랜치를 받아 확인하고 `main` 에 머지한다. 확인은 로컬에서, 머지는 `gh pr merge` 로(로컬에서 합쳐 main 에 push 하지 않는다).
- **충돌은 작성자가 푼다.** 자기 브랜치에서 `git merge origin/main` 으로 풀고 다시 올린다. ⑥ 이 남의 코드를 대신 풀지 않는다.
- 내 브랜치가 뒤처지면 **내가** 따라간다: `git checkout <내 모듈> && git merge origin/main`. **남의 브랜치를 대신 맞추지 않는다.**
- 임시 실험은 `<모듈>-<무엇>`(예: `score-wb-test`)으로 만들고 끝나면 지운다.

```bash
# 평소
git checkout score && git pull
... 작업 ... && git commit && git push          # 강제 푸시 없이

# main 이 앞서갔으면
git merge origin/main                            # 충돌은 내가 푼다

# 준비되면
gh pr create --base main --head score            # 본문에 Closes #이슈번호
gh pr edit <번호> --add-reviewer <⑥ 계정>        # 리뷰 요청 = 병합 요청
```

**모듈 브랜치는 지우지 않는다.** 6주 내내 산다. PR 이 병합돼도 그대로 두고 계속 쓴다.

### 내 PR 이 머지된 다음 — 여기서 다들 막힌다

`main` 은 **squash 머지**다. 내 커밋 여러 개가 `main` 에서는 **새 커밋 하나**가 된다.
그래서 머지 직후 내 모듈 브랜치는 **반드시** `main` 과 갈라진다. 뒤처져서가 아니라 구조가 그렇다.

```
$ git pull
hint: You have divergent branches and need to specify how to reconcile them.
fatal: Not possible to fast-forward, aborting.
```

**정상이다.** 이렇게 따라간다:

```bash
git fetch origin
git merge origin/main --no-edit        # 머지 커밋 하나 생긴다. 그대로 둔다
git push origin score
```

`git rebase` 도 `git reset --hard` 도 쓰지 않는다. 둘 다 이력을 갈아서 강제 푸시가 필요해지고,
그게 2026-09-18 에 커밋을 날린 바로 그 길이다.

규칙만으로는 또 일어난다. 두 겹으로 막는다.

## 3. 성능 평가

### 3-1. 원칙

- **발표 숫자 3개**가 목표: ① 채점기와 사람 판정 일치율 ② 얼굴형 규칙 정확도 → 모델 정확도(+ 라벨러 일치율) ③ 화장 전이 시간·정체성 유지·색 반영도. 여기에 사용자 실험의 **퍼널(완주율·이탈 지점)** 이 "사용자 효과" 절로 붙는다(E-8).
- **데이터는 하나.** 아래 평가 다섯 중 넷이 실촬영 20명 세트에서 나온다. 촬영 세션이 평가 전체의 병목이라 ⑤의 1순위.
- **측정은 각 모듈이, 데이터와 결과표는 ⑤가.** 평가 스크립트와 결과 CSV는 `eval/<모듈>/run`에, 결과표는 `docs/eval-results-v6.md` 하나에 자동 생성(`ai-pipeline-v6.md` 2절). 발표 슬라이드는 이 표를 그대로 옮긴다.
- **골든 세트 30장은 고정하고, 채점·가이드·임계 코드가 바뀌면 다시 돌린다.** 결과 파일 이름에 커밋·모델 버전·골든 버전이 들어간다. 버전별 일치율 변화가 발표 그래프다.
- **선정 평가 → 통과 평가 순.** 후보가 둘 이상인 자리(3-2)는 같은 지표의 작은 데이터로 먼저 고르고, 고른 뒤 전체 데이터로 통과 평가(3-3)를 한다.
- **기준선을 먼저 잰다.** 모델을 학습하거나 알고리즘을 고치기 전에 "지금 값"을 같은 데이터로 먼저 기록한다. 개선폭이 없으면 발표 숫자가 없다.
- **통과 기준은 첫 측정 후 팀이 정한다.** 아래 "통과 기준(안)"은 논의 출발점.

### 3-2. 모델 선정 평가 (통과 평가보다 먼저, 1~2주차)

통과 평가(3-3)는 "고른 것이 되는가"를 재고, 선정 평가는 "무엇을 고를 것인가"를 잰다. **같은 지표·같은 데이터의 작은 부분집합**으로 먼저 돌려 고른 뒤, 통과 평가는 전체 데이터로 한다. 지표를 두 번 만들지 않고, "왜 이 모델인가"가 발표에서 표 한 장으로 나온다. 선정 결과는 `docs/eval-results-v6.md`의 "선정" 절에 후보별 한 줄씩 남긴다(탈락 후보도).

C를 고르면 임계 전부 재보정(비용 반영) | ③ | E-5 색 변동 결과 직후 (2주차) |

**선정 없이 가는 것(대안이 사실상 없음)**: 얼굴 랜드마크 MediaPipe Face Landmarker(웹 대안 부재, 홍채 12% 오차는 비율 척도로 우회 완료) · 손 검출 MediaPipe Hand Landmarker · 정체성 검사 ArcFace(표준) · 법선 추정(MVP 제외, 확장 시 Marigold-Normals vs MediaPipe z 근사 비교) · 분할 모델 학습 데이터(FFHQ-Makeup 라벨 0 vs 자체 합성 — S-3에서 C까지 갈 때만).
