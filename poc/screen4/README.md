# 화면 4 POC — 실시간 테두리 + fps 측정

라이브 화면에 아이라이너 가이드 테두리를 매 프레임 다시 그리면서, **30fps가 버티는지 숫자로 재는** 하네스다.
기능 정의서 13장 1주차 실기기 검증 3·5번과 `tech-stack-v6.md` 7장 확인 목록에 대응한다.

**mm 척도를 쓰지 않는다.** 두께·꼬리 길이는 전부 눈 너비 비율이다.

## 무엇을 재나

| 질문 | 어떻게 |
|---|---|
| 얼굴만 vs 얼굴+손, 30fps가 버티나 | 손 검출 모드 3가지(매 프레임 / 3프레임마다 / 끔)를 바꿔 가며 fps 비교 |
| 어느 단계가 예산을 먹나 | 얼굴·손·게이트·그리기 단계별 평균과 p95 (예산은 프레임당 33ms) |
| rVFC로 바꾸면 중복 추론이 사라지나 | 루프 모드를 바꿔 가며 **중복 프레임 비율** 비교 |
| 버전을 올려도 되나 | `?v=1.0.1`로 열어 같은 측정을 반복 (기본 0.10.14) |

## 실행

```
cd poc/screen4
node tests.mjs                 # 자동 검증 (브라우저 불필요)
python -m http.server 8000     # → http://localhost:8000
```

카메라는 `localhost` 또는 https에서만 열린다. 모델과 WASM은 첫 로딩 때 CDN에서 받는다.

폰에서 재려면 같은 네트워크에서 PC IP로 접속하되 **https가 필요하다**. `ngrok` 같은 터널이나 자체 서명 인증서를 쓴다.

## 측정 순서

1. **카메라 시작** → 얼굴이 잡히면 테두리가 뜬다
2. 얼굴을 정면으로 두고 **기준 잡기** — 지금의 선명도·이마 밝기를 세션 기준으로 저장한다
3. 손 검출 모드를 `끔` → `3프레임마다` → `매 프레임` 순으로 바꾸며 각각 10초쯤 두고 fps를 읽는다
   (모드를 바꾸면 측정값이 자동 초기화된다)
4. 루프 모드를 `requestAnimationFrame`으로 바꿔 **중복 프레임 비율**을 확인한다
5. **결과 복사** → 측정 결과가 클립보드에 텍스트로 들어간다. 그대로 문서나 로그에 붙인다

## 측정 결과 (2026-09-17 · Windows Chrome 152 · 640×480 · 얼굴·손 GPU · MediaPipe 0.10.14)

손 검출 매 프레임, 추가 스무딩 끔 조건에서 루프 방식만 바꿔 가며 쟀다.

| 루프 | 실제 처리 | 루프 여력 | 중복 프레임 | 얼굴 | 손 | 전체(평균/p95) |
|---|---|---|---|---|---|---|
| rVFC | 지표 수정 전 | 38.5fps | **0 / 10050 (0%)** | 15.7ms | 9.6ms | 26.0 / 38.1ms |
| rAF | **22.2fps** | 46.5fps | **304 / 533 (57%)** | 14.3ms | 6.5ms | 21.5 / 32.9ms |

게이트 0.6ms · 그리기 0.1ms는 모든 측정에서 같았다.

### 알게 된 것

1. **rAF 루프는 추론의 58%를 버린다.** 카메라가 새 프레임을 주지 않았는데 같은 화면을 다시 추론한다.
   기존 `poc/app.js`가 이 상태다(`performance.now()`로 프레임을 거르는데 그 값은 매번 다르다). rVFC로 바꾸면 0%가 된다.
2. **"루프 여력"은 실제 프레임 수가 아니다.** rAF 쪽 54fps 중 새 프레임은 42%뿐이라 환산하면 23fps 수준이다.
   숫자를 잘못 읽으면 느린 쪽이 빨라 보인다. 그래서 HUD의 큰 숫자를 **실제 처리 프레임/초**로 바꿨다(이 표는 그 이전 측정이라 환산값이다).
3. **그리기와 게이트는 공짜다** (0.1ms · 0.6ms). 비용은 전부 추론에 있고, 그중 얼굴이 손보다 약 1.7배 비싸다.
4. **1€ 필터 추가 스무딩은 PC에서는 필요 없어 보인다.** 꺼도 떨림이 거슬리지 않는다 —
   MediaPipe가 `numFaces:1`에서 이미 같은 계열의 시간 필터를 내부에 걸기 때문이다(Face Mesh 논문).
   기본값을 끔으로 두되 코드는 남긴다. **폰에서 다시 판단할 것**: 어두우면 센서 노이즈가 늘어 결론이 바뀔 수 있다.
5. **정면을 봐도 pitch가 −7.4°로 찍힌다.** 카메라 위치 때문에 중립 자세가 0이 아니다.
   정면성 게이트를 절대각(±10°)으로 잡으면 가만히 있어도 걸리는 사람이 생긴다.
   화면 1 촬영 때의 자세를 기준으로 저장하고 **그 대비 차이**로 재야 한다.
6. 두 측정 사이에 단계별 시간이 달라졌다(얼굴 15.7 → 11.4ms). 중복 프레임은 추적이 이미 맞아 있어 더 싸게 끝나는 것으로 보이나 확정은 아니다.
   실제 처리율을 직접 재도록 고쳤으니 다시 재면 깔끔하게 비교된다.

## A1 — 얼굴 후처리 옵션 선정 (2026-09-21 · Windows Chrome 152 · 640×480 · GPU · rVFC)

`outputFacialTransformationMatrixes`(변환행렬)와 `outputFaceBlendshapes`(블렌드셰이프)를
켤지 끌지 정하기 위한 측정. **판정 기준은 측정 전에 정했다** — 숫자를 보고 말을 맞추지 않기 위해.

| 사전 판정 기준 | |
|---|---|
| 변환행렬을 끈다 | 근사각과의 차이가 p95 2~3° 이내 |
| 블렌드셰이프를 끈다 | 눈감음 판정이 EAR과 95% 이상 일치 |
| 둘 다 | 추가 비용이 얼굴 추론의 10% 이상이면 정확도와 무관하게 재검토 |

### 비용 — 측정 불가능할 만큼 작다

손 검출·스무딩·루프를 고정하고 후처리만 바꿔 각 25초.

| 버전 | 블렌드 | 행렬 | **얼굴 avg** | V0 대비 |
|---|---|---|---|---|
| V0 | off | off | 13.99ms | — |
| V1 | off | **on** | 14.06ms | +0.07 (+0.5%) |
| V2 | **on** | off | **13.63ms** | **−0.36 (더 빠름)** |
| V3 | **on** | **on** | 14.58ms | +0.59 (+4.2%) |

**V2가 V0보다 빠르다.** 블렌드셰이프를 켰는데 빨라지는 건 불가능하므로 **효과가 잡음보다 작다.**
네 값의 폭이 0.95ms(약 7%)라 1ms 미만은 이 환경에서 구분되지 않는다. 사전 기준 10%에 한참 못 미친다.

→ **비용은 판단 근거가 못 된다. 정확도와 기능만으로 결정한다.**

### 자세 — yaw는 근사로 충분, pitch는 아니다

같은 프레임에서 행렬 분해와 랜드마크 근사를 동시에 계산해 차이를 쟀다.

| 조건 | yaw p95 | pitch p95 | pitch 최대 |
|---|---|---|---|
| 정면 정지 25초 | 1.07° | 3.11° | 3.22° |
| 정면 정지 25초 (재측정) | 1.34° | 4.21° | 5.09° |
| 움직임 포함 55초 | 1.29° | **6.45°** | 8.87° |

정지 상태의 3~4°는 **개인 고정 오차**(근사식의 `0.55` 상수 vs 실제 얼굴 비율)이고 상대 게이트에서 상쇄된다.
움직일 때 늘어나는 **약 3°가 상쇄되지 않는 부분**이며, 이는 `dPitch ±6°` 게이트 폭의 절반이다.

yaw의 `0.5`는 좌우 대칭이라 개인차에 강하고, pitch의 `0.55`는 얼굴 길이·코 위치에 그대로 노출된다.

### 눈 감음 — EAR로 충분

| 조건 | 일치율 | 불일치 |
|---|---|---|
| 정면 정지, 자연스러운 깜빡임 | **100.0%** (1188·1318판정) | 0 |
| 의도적으로 천천히 감았다 뜨기 | 98.8% (3150판정) | EAR만 38 · BS만 0 |

불일치는 **전부 EAR이 먼저 "감음"으로 판정**한 것. 임계 `0.15`가 이 피험자에게 약간 높다.
촬영 1의 눈 뜸·눈 감음 두 장으로 개인별 임계를 잡으면 더 올라갈 여지가 있다.

### 웃음 — 블렌드셰이프만 낼 수 있는 신호

| | mouthSmile |
|---|---|
| 무표정 정지 25초 | **0.000** (오탐 0) |
| 웃을 때 최대 | **0.754** |

EAR·MAR로는 만들 수 없다. 웃으면 눈은 반쯤 감기고 입꼬리가 올라가는데,
EAR은 "감는 중", MAR은 "입 다뭄"으로 읽는다.

## 폰 측정 (2026-09-17 · Galaxy S8+ / 2017년 기기 · Chrome 138 · 720×1280 · 카메라 30fps · 델리게이트 GPU · rVFC)

| 손 검출 | 실제 처리 | 얼굴 | 손 | 게이트 | 그리기 | 전체(평균/p95) |
|---|---|---|---|---|---|---|
| 매 프레임 | **2.4fps** | 225.0ms | 158.5ms | 7.2 / p95 36.3ms | 2.6ms | 393.6 / 475.3ms |
| 끔 | **4.1fps** | 231.5ms | — | 3.8 / p95 20.1ms | 0.9ms | 236.4 / 304.7ms |

PC 대비 **얼굴 16배, 손 24배** 느리다. 중복 프레임은 0이라 rVFC는 폰에서도 정상이다.

### 이게 뜻하는 것

1. **손을 빼도 못 쓴다.** 얼굴 하나만 돌려도 231ms(4.1fps)다. 손 검출은 원인이 아니라 가중치일 뿐이다.
2. **델리게이트 표시를 믿으면 안 된다.** HUD의 `GPU`는 "그 옵션으로 생성이 성공했다"는 뜻이지
   실제로 GPU에서 빠르게 돈다는 보장이 아니다. 225ms는 GPU 경로치고 비정상이다.
3. **비교 기준**: MediaPipe Face Mesh 논문은 Pixel 3(2018) 네이티브에서 7.4ms를 보고한다. 30배 차이다.
   기기 노후만으로는 설명되지 않고, 웹 런타임 경로나 이 기기의 드라이버를 의심해야 한다.
4. 해상도가 **720×1280**으로 잡혔다. PC(640×480)의 3배 픽셀이다.
5. 게이트 p95가 36.3ms로 튄다(PC 2.8ms). 모바일에서 `getImageData`는 GPU→CPU 읽기라 멈춤이 생긴다.
6. **기능 정의서의 "30fps 유지" 수용 기준은 이 기기에서 성립하지 않는다.**
   지원 기기 하한선을 정하거나, 앱(INT8 네이티브)으로 가야 한다는 뜻일 수 있다. 아래 실험 전에는 결론을 내리지 말 것.

### 해상도·델리게이트 실험 결과 (같은 기기, 손 매 프레임)

| 조건 | 실제 처리 | 얼굴 | 손 |
|---|---|---|---|
| 720×1280 · GPU | 2.4fps | 225.0ms | 158.5ms |
| **240×320** · GPU | 2.7fps | **207.7ms** | 146.5ms |
| 480×640 · **CPU** | 1.4fps | **223.6ms** | 492.8ms |

두 가지가 확정됐다.

1. **해상도는 범인이 아니다.** 픽셀을 12분의 1로 줄였는데 얼굴 추론은 8%밖에 안 빨라졌다.
   모델이 내부에서 고정 크기로 리사이즈하므로 당연한 결과다. 입력 해상도를 낮추는 최적화는 의미가 없다.
2. **얼굴 모델은 GPU 옵션에서도 GPU로 돌지 않는 것으로 보인다.**
   손은 GPU 146ms → CPU 493ms로 3.4배 차이가 나는데, **얼굴은 GPU 208ms → CPU 224ms로 거의 같다.**
   델리게이트를 바꿔도 안 변한다는 건 처음부터 그 경로로 돌고 있었다는 뜻이다.

### 다음 의심: 얼굴 후처리 두 개

얼굴 랜드마커에 `outputFaceBlendshapes`와 `outputFacialTransformationMatrixes`를 켜 두었다.
둘 다 랜드마크 뒤에 붙는 별도 계산이라 **GPU→CPU 읽기를 유발**할 수 있고, 그러면 매 프레임 파이프라인이 멈춘다.

```
?bs=0&mat=0     둘 다 끄고 측정
?bs=0           블렌드셰이프만 끄기
?mat=0          변환행렬만 끄기
```

얼굴 ms가 크게 떨어지면 원인이 확정된다. **그 경우 설계가 바뀐다.**

| 기능 | 지금 계획 | 후처리를 못 쓸 때의 대안 |
|---|---|---|
| 정면성 게이트 (yaw·pitch) | 변환행렬 분해 | 랜드마크 기하로 근사 |
| 눈 감음 판정 | 블렌드셰이프 `eyeBlink` | EAR 직접 계산 |

둘 다 `tech-stack-v6.md` 조사 때 이미 2순위 대안으로 적어 둔 방법이다.

## 기기 비교 (같은 조건: 480×640 · GPU · 손 매 프레임 · 후처리 on · rVFC)

| 기기 | 출시 | 실제 처리 | 얼굴 | 손 | 게이트 | 전체(평균/p95) |
|---|---|---|---|---|---|---|
| **Galaxy S23** | 2023 | **17.7fps** | 27.0ms | 19.1ms | 3.5 / p95 20.1ms | 49.9 / 66.4ms |
| Galaxy S8+ | 2017 | 1.4~2.7fps | 224ms | 159~493ms | 1.3ms | 359~719ms |
| PC (참고) | — | 22.2fps | 14.3ms | 6.5ms | 0.6ms | 21.5 / 32.9ms |

**기기 차이는 약 8배다.** S8+의 참사는 기기 노후가 주원인이고, 웹 런타임이 근본적으로 망가진 것은 아니다.

### 핵심 발견: 플래그십에서도 30fps가 안 나온다

S23에서 **전체 49.9ms**다. 30fps 예산 33ms를 1.5배 초과한다.

| 항목 | 비용 | 예산(33ms) 대비 |
|---|---|---|
| 얼굴 | 27.0ms | **82%** |
| 손 (매 프레임) | 19.1ms | 58% |
| 게이트 | 3.5ms (p95 20.1) | 11% |
| 그리기 | 0.2ms | 1% |

**얼굴 하나만으로 예산의 82%를 쓴다.** 손을 매 프레임 돌릴 여유가 없다.

### 33ms 안에 들어가는 방법

| 수단 | 절감 | 근거 |
|---|---|---|
| 손을 5~10프레임마다 | 19 → 2~4ms | 손 가림은 0.1초 만에 생겼다 사라지지 않는다. 초당 3회면 충분 |
| 게이트 주기 늘리기 (`?gate=15`) | 3.5 → 1.2ms | 선명도·밝기도 매 5프레임씩 볼 이유가 없다 |
| 얼굴 후처리 끄기 (`?bs=0&mat=0`) | 미측정 | S8+ 실험에서 제기된 의심. S23에서도 재 볼 것 |

앞의 둘만 해도 **27 + 3 + 1.2 + 0.2 ≈ 31ms**로 가까스로 들어온다. 여유가 거의 없다.

### 그래서 정해야 할 것

1. **"30fps 유지"라는 수용 기준이 맞는 숫자인가.** 이 값은 검증된 요구사항이 아니라 문서 작성 때의 가정이다.
   PC에서 22fps로 돌 때 테두리 추적은 눈으로 보기에 문제가 없었다. **사람이 보고 몇 fps부터 쓸 만한지 정하는 게 먼저다.**
2. **지원 기기 하한선.** S8+(2017)는 불가, S23(2023)은 최적화하면 가능. 그 사이 어디가 경계인지는 중급기로 재야 안다.
3. 손 검출을 **실시간 게이트에서 뺄지.** "확인받기"를 누른 순간에만 손을 확인하는 방법도 있다.

### 아직 안 잰 것

| 방법 | 무엇을 가리나 |
|---|---|
| S23에서 `?bs=0&mat=0` | 얼굴 후처리가 비용을 끌어올리는지 |
| S23에서 손 `10프레임마다` + `?gate=15` | 30fps에 실제로 도달하는지 |
| `python server.py 8000` 으로 띄우기 | 교차 출처 격리 → WASM 멀티스레드. 지금 **"불가 · 코어 8"** |
| `?v=1.0.1` | 런타임 버전 차이 |
| 중급기 (2020~2021년) | 지원 기기 하한선 |

### 아직 안 잰 것

- 손 `3프레임마다` 모드
- 해상도를 올렸을 때(640×480 → 1280×720) PC에서의 비용 변화

## 화면에 있는 것

- 상단 가운데: 품질 게이트 한 줄. 안 맞는 것 **하나만** 보여준다 (정면 → 양쪽 눈 → 손 → 선명 → 밝기 순)
- 테두리: **선만**. 면 채우기 없음 (v6 확정 규칙)
- 게이트가 연속 5프레임 통과하면 테두리가 진해진다 — 실제 화면 4에서는 이때 "확인받기"가 활성화된다
- 손이 잡히면 주황 점으로 표시된다 (디버그용, 실제 화면에는 없음)

## 파일

| 파일 | 내용 |
|---|---|
| `core.js` | 순수 함수 — 가이드 기하, 1€ 필터, 고개 각도 분해, 게이트 우선순위, 라플라시안 분산, Lab 변환, 측정 통계 |
| `tests.mjs` | Node 검증 (브라우저·카메라 없이 돈다) |

`core.js`는 DOM을 참조하지 않으므로 본 구현에 그대로 이식할 수 있다.

## 알려진 한계

- **고개 각도 부호**는 실기기에서 확인해야 한다. 좌우가 뒤집혀 나오면 `core.js`의 `matrixToEuler`가 아니라 게이트 비교 쪽에서 부호를 맞춘다.
- 손 모델은 웹 배포 번들이 하나뿐이라 논문의 Light/Full 구분을 그대로 고를 수 없다.
- 선명도·밝기는 5프레임마다만 잰다. 이 주기 자체가 실측으로 정할 값이다.
- 눈 감음 전환(섀도우 단계)은 아직 없다. 블렌드셰이프는 받아 두었고 쓰지만 않는다.
- 부위 확대 크롭이 없다. 지금은 전체 화면에 테두리만 그린다.
