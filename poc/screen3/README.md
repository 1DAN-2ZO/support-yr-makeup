# 화면 3 POC — 부위 완성본 (v6)

당화응 화면 3(부위 완성본)의 계산 로직을 브라우저에서 실측·검증하는 POC. **완성본 = 전체 완성 예상 렌더링(화면 2-b)을 그 부위 크롭 박스로 줌한 정지 이미지**이며, 이 화면에서 실제로 계산이 일어나는 곳은 두 군데뿐이다 — ① 부위 6개의 크롭 박스(어디를 얼마나 확대할지), ② 쉐딩·하이라이트 규칙 윤곽선(룩 렌더링에 없는 유일한 부위라 얼굴형 규칙으로 자리를 만들어 점선 테두리로만 그린다). 얼굴형 판정은 이 POC의 일이 아니다 — 파트 1(F-02)이 주는 label을 입력으로 받는다.

## 실행법

```bash
cd poc/screen3 && node tests.mjs     # 자동 검증 16개
cd poc/screen3 && node report.mjs    # 샘플 20장 × 부위 6개 실측 표
```

브라우저 목업은 **저장소 루트에서** 서버를 띄워야 한다.

```bash
cd C:/Users/hi/Desktop/support-yr-makeup && python -m http.server 8000
# → http://localhost:8000/poc/screen3/
```

`poc/screen3`에서 서버를 띄우면 `app.js`가 `../../danghaeung_poc_3x4_20/`으로 참조하는 샘플 이미지가 404가 난다.

## 목업이 보여주는 크롭

`.shot canvas`는 `object-fit: contain`이다(`cover`가 아니다). `cropSpec`이 계산한 박스를 통째로 보여주는 게 이 POC의 목적이라, `.shot` 실제 비율(가로 목업 기준 약 1.60:1)과 크롭 박스 목표 비율(19.5:9 ≈ 2.167:1)이 다르면 레터박스(빈 여백)가 생긴다 — `.shot` 배경색(`#e9e5de`)이 페이지 배경(`#F7F5F1`)과 가까운 톤이라 여백이 두드러지지 않는다. 이전에는 `cover`라 폭의 약 27%가 화면 밖으로 잘려 나가, 눈 단계에서 의도한 15% 여백이 사라지고 눈 바깥 끝이 화면 경계에 걸렸다(고쳐진 스크린샷 참고).

`rules.js`의 `ASPECT`는 **폰 화면 전체 비율**(19.5:9 / 9:19.5)이지, 실제 사진이 보이는 영역(진행 칩·카드를 뺀 `.shot`) 비율이 아니다 — 목표 종횡비가 사진 영역의 실제 비율과 다르다는 뜻이고, 이건 이 POC가 안고 가는 모델링 한계다. 위 "종횡비 충돌"(설계 문서 1절) 분석은 이 전제(화면 전체 비율 = 목표 비율) 위에서 한 것이라, 사진 영역만의 비율로 다시 계산하면 여백·확대율 결론이 달라질 수 있다.

| 부위 | 확대율(최소/중앙/최대) | covered | clamped |
|---|---|---|---|
| 눈썹 | 1.71 / 2.16 / 2.46 | 20/20 | 0/20 |
| 아이라이너 | 2.10 / 2.77 / 3.18 | 20/20 | 0/20 |
| 섀도우 | 1.71 / 2.16 / 2.46 | 20/20 | 0/20 |
| 입술 | 2.50 / 2.50 / 2.50 | 20/20 | 0/20 |
| 볼터치 | 2.06 / 2.49 / 2.50 | 20/20 | 0/20 |
| 쉐딩·하이라이트 | 1.91 / 2.11 / 2.19 | 20/20 | 0/20 |

**문제 케이스 0건. 문서의 여백·배수 가정값이 이 샘플에서 그대로 성립한다.** `PORTRAIT_ZOOM`을 낮춰 가며 재탐색할 필요가 없었다 — 이미 0건이라 `rules.js`는 문서값(2.5배, 여백 15%)에서 건드리지 않았다.

### covered/clamped 는 이 알고리즘에서 반증되기 어려운 지표다

위 표의 `covered=120/120`·`clamped=0/120`은 "아슬아슬하게 통과"가 아니다. 두 지표 모두 이 알고리즘의 구조 때문에 웬만해서는 실패하지 않는다.

- **covered 는 알고리즘의 항등식이다.** `cropSpec`이 여백을 적용한 뒤 "부위가 박스보다 크면 담을 수 있을 만큼 박스를 키운다"(`core.js`의 `if (b.w > w) { w = b.w; … }` / `if (b.h > h) { h = b.h; … }`)를 거치고 나서 중심을 맞추므로, **축소(clamped)가 일어나지 않는 한 기준 랜드마크는 항상 박스 안에 들어가도록 알고리즘이 설계돼 있다.** 측정값이 아니라 코드 구조가 보장하는 사실이다.
- **세로 부위(입술·볼터치·쉐딩·하이라이트)의 clamped=0 도 산술적으로 당연하다.** `w = imgW/zoom`, `h = w/aspect`는 랜드마크와 전혀 무관하게 정해지고, `h ≤ imgH`이기만 하면 축소가 없다. 실제로 **입술 박스는 20장 전부 정확히 432×936**(zoom 2.5 그대로)이다 — 사람마다 얼굴·입술 크기가 다른데도 박스 크기가 한 픽셀도 다르지 않다는 것 자체가, 이 박스가 "입술을 담았는지"가 아니라 "이미지 크기·목표 배율로 정해지는 상수"라는 뜻이다.

그래서 "얼마나 여유가 있는가"는 covered/clamped가 아니라, **닫힌 식으로 구한 축소 임계값 대비 현재값의 배수**로만 말할 수 있다. `report.mjs`가 이를 계산해 출력한다.

| 부위 | 현재값 | 축소 임계값(가장 빠듯한 샘플) | 여유 배수 |
|---|---|---|---|
| 눈썹 | 여백 15% | 여백 270.4% | 18.03배 |
| 아이라이너 | 여백 15% | 여백 344.0% | 22.94배 |
| 섀도우 | 여백 15% | 여백 270.4% | 18.03배 |
| 입술 | zoom 2.5 | zoom 1.625 | 1.54배 |
| 볼터치 | zoom 2.5 | zoom 1.625 | 1.54배 |
| 쉐딩·하이라이트 | zoom 2.5 | zoom 1.625 | 1.54배 |

가로 부위(눈썹·아이라이너·섀도우)는 여백을 18~23배까지 키워도 축소가 안 일어날 만큼 여유가 크다. 세로 부위(입술·볼터치·쉐딩·하이라이트)는 여유가 **1.54배**로 더 좁다 — `zoom` 임계값 1.625는 이미지 크기(1080×1440)와 목표 종횡비로만 정해지는 상수라 사람마다 다르지 않다(이 샘플 세트는 전부 같은 1080×1440이라 임계값도 20장이 동일).

`clampedSides`(박스가 축소 없이 이동만 된 횟수)도 지금까지 어디에도 집계되지 않았다. 이동 자체는 정상 동작(스텝 4 "먼저 안쪽으로 이동")이지만, 얼마나 자주 일어나는지는 실측해 볼 만하다.

| 부위 | 이동된 케이스 | 비율 |
|---|---|---|
| 눈썹 | 0/20 | 0% |
| 아이라이너 | 0/20 | 0% |
| 섀도우 | 0/20 | 0% |
| 입술 | 8/20 | 40% |
| 볼터치 | 0/20 | 0% |
| 쉐딩·하이라이트 | 14/20 | 70% |

입술·쉐딩·하이라이트는 꽤 자주(40%·70%) 이동이 일어난다 — 축소는 안 되지만 중심이 얼굴 중심과 어긋나 있다는 뜻이다.

### covered/clamped 는 "부위 확대 이미지로 쓸 만한가"를 재지 못한다

부위 bbox 면적을 크롭 박스 면적으로 나눈 값(중앙값)을 보면, 세로 부위 크롭이 실제로는 "그 부위를 확대"하는 게 아니라 "이미지 크기 기준으로 종횡비만 맞추는" 것에 가깝다는 게 드러난다.

| 부위 | 면적비 중앙값 |
|---|---|
| 눈썹 | 39.3% |
| 아이라이너 | 19.9% |
| 섀도우 | 43.2% |
| 입술 | 3.1% |
| 볼터치 | 12.6% |
| 쉐딩·하이라이트 | 33.4% |

**입술은 크롭 박스 면적의 3%만 실제 입술이다.** `screenshots/lip-portrait.png`가 "입술 완성본" 화면인데 입술이 화면의 극히 일부만 차지하고 사실상 얼굴 전체 사진으로 보이는 이유가 이것이다. `covered=true`·`clamped=false`는 "입술이 박스 안에 있고 축소되지 않았다"만 보장하지, "이게 확대된 입술 이미지로 쓸 만한가"는 전혀 재지 못한다.

### 설계 문서의 사전 예측은 빗나갔다

설계 문서(`docs/superpowers/specs/2026-09-16-screen3-poc-design.md` 1절)는 합성 계산으로 "쉐딩·하이라이트 부위가 3:4 원본에서 9:19.5 화면에 안 들어갈 가능성이 크다"고 예측했다. 실제 샘플 20장에서는 이 잘림이 한 번도 일어나지 않았다.

원인을 추적해 보니, 자동 검증(`tests-cases.js`)의 합성 얼굴 `fakeFace()`는 얼굴 가장자리(`faceEdge`)를 이미지 폭의 **64%**(x=0.18~0.82)로 두고 설계했는데, 실제 샘플 20장의 얼굴 폭은 이미지 폭의 **평균 44.8%(최소 38.1% / 중앙 45.6% / 최대 52.5%)**였다(`node report.mjs` "얼굴 폭 비율" 절, `IDX.faceEdge.r`↔`l` 거리 ÷ 이미지 폭으로 계산 — 아래 재확인 참고). 즉 **합성 픽스처가 실제 얼굴보다 훨씬 옆으로 넓게 설계돼 있어서, 자동 검증(C1~C8, N1~N5)은 실제보다 더 가혹한 조건을 검증하고 있었고, 그 결과 실측에서는 여유가 있었다.** 합성 픽스처가 실제보다 극단적이었다는 뜻이지, 문서 가정값이 우연히 맞았다는 뜻은 아니다 — 두 판단 모두 근거가 있다.

### 합성 얼굴에서는 그 예측이 실제로 재현된다

위 문단은 "실제 샘플 20장에서는 잘림이 한 번도 없었다"까지만 적고 멈췄는데, 이건 가장 강한 반례를 빠뜨린 것이다. **`fakeFace()`(`tests-cases.js`)를 1080×1440 이미지에 넣고 `cropSpec(lm, IMG, 'contour')`를 직접 돌리면, 설계 문서 1절이 예측한 실패가 실제로 재현된다:**

```js
cropSpec(fakeFace(), { w: 1080, h: 1440 }, 'contour')
// → { x: 207.7, y: 0, w: 664.6, h: 1440, zoomRatio: 1.62,
//     covered: false, clamped: true, clampedSides: ['bottom'] }
```

즉 665×1440, zoom 1.62, **covered=false, clamped=true, sides=[bottom]**. 이걸 실행해서 직접 확인한 값이다(위 숫자는 `node`로 재현 가능). 그리고 `C1`(크롭 검증 8개 중 하나)은 `c.covered || c.clamped`만 보므로, 이 "잘림"을 정상으로 통과시킨다 — `covered=false`인데도 `clamped=true`라 보고 계약(잘렸으면 반드시 드러난다)은 지켰고, 그래서 테스트는 실패하지 않는다.

**이게 말해주는 것**: 자동 검증 16개가 실제로 보증하는 것은 다음 네 가지이지,

1. **보고 계약** — 랜드마크가 잘렸으면 반드시 `clamped`로 드러난다(조용히 잘리지 않는다)
2. **불변식** — 종횡비가 목표와 일치한다, 스케일을 2배로 키우면 박스도 2배가 된다, 알 수 없는 partId는 예외를 던진다
3. **상수 고정** — 가로 여백 15%, 세로 확대 2.5배가 코드에 실제로 박혀 있다
4. **문장 규칙** — 근거 문장에 숫자가 없다, 얼굴형마다 다르다 등

**"가정값(여백 15%, 확대 2.5배)이 실제 사진에서 성립한다"는 보증하지 않는다.** 그건 자동 검증이 아니라 `report.mjs`의 실측(위 표들)만 말할 수 있다 — 그리고 그 실측은 "같은 촬영 조건 20장"이라는 좁은 샘플에 대해서만 성립한다(아래 "범위 한계" 참고).

### 이 결론의 범위 한계

**외적 타당도(촬영 조건이 다르면?)**: 샘플 20장은 모두 같은 촬영 조건이다 — 3:4 세로 셀카, 1080×1440, 얼굴이 프레임 중앙, AI 생성 인물. 이 조건을 벗어나면(사용자가 카메라에 더 가까이/멀리 서거나, 얼굴이 프레임 중앙을 벗어나거나, 셀카 종횡비가 다르면) 결과가 달라질 수 있다.

확대율 자체도 사람마다 꽤 벌어진다 — 예를 들어 아이라이너 단계는 같은 `SIDE_MARGIN=0.15` 가정값으로도 사람에 따라 2.10~3.18배로 **약 1.5배**(3.18/2.10) 차이가 난다(눈 사이 간격·얼굴 크기 개인차 때문). 부위를 가로질러 보면 차이는 더 커서, 눈썹·섀도우의 최소 1.71배부터 아이라이너의 최대 3.18배까지 **약 1.9배**(3.18/1.71) 차이가 난다. 세로 부위는 `PORTRAIT_ZOOM`을 고정 배수로 두므로 이 차이가 크롭 박스 크기(=화질 손실)로는 드러나지 않지만, 가로 부위(눈썹·아이라이너·섀도우)는 사람마다 확대율이 달라진다는 점은 문서에 남겨 둘 만하다.

**내적 타당도(지표 자체가 무엇을 재는가?)**: 위 "covered/clamped 는 이 알고리즘에서 반증되기 어려운 지표다" 절에서 본 것처럼, `covered=100%`·`clamped=0%`이라는 결과 자체가 알고리즘 구조상 나오기 쉬운 값이다. 그래서 "120/120·0/120"을 "가정값이 잘 맞았다"는 근거로 곧이곧대로 읽으면 안 되고, **실제 여유는 축소 임계값 대비 배수(가로 18~23배, 세로 1.54배)로 다시 읽어야 한다.** 또한 부위 bbox 면적 ÷ 크롭 박스 면적을 보면 **세로 부위 크롭은 그 부위를 "확대"한다기보다 이미지 크기 기준으로 "비율을 맞추는" 것에 가깝다**(입술 3.1%, 볼터치 12.6%) — covered/clamped 만으로는 "부위 확대 이미지로 실제로 쓸 만한가"를 전혀 재지 못한다는 뜻이다.

**요약**: 스펙 12절의 "`covered` 100%" 기준을 유지해도 된다는 근거가 이번 실측으로 생겼다. 다만 이 근거는 "같은 조건의 셀카 20장"이라는 좁은 샘플에 기반하고(외적 타당도), covered/clamped 자체가 반증되기 어려운 지표라는 한계도 있다(내적 타당도). 실기기 검증(문서 미정 항목의 "1주차 실기기 검증 7항목")에서 다른 촬영 조건(비대칭 구도, 다른 종횡비 업로드 등)을 마주치면 재확인이 필요하고, 세로 부위는 "화면에 담기는가"가 아니라 "확대 이미지로 쓸 만한가"를 별도로 봐야 한다.

**육안 확인 범위(B-4)**: 랜드마크 인덱스(`core.js`의 `IDX`)는 `person_1`의 3장(정면 눈 뜸·감음·좌 45°)에 그려서 확인했고, 이번 리뷰 수정 중 `person_1/3/4`로 추가 확인했다. `person_2`·`person_5`와 `right_45` 샷들은 `fixtures.json`(Node 테스트·리포트용 랜드마크 추출)만 됐을 뿐, 화면에 점을 찍어 눈으로 본 적은 없다 — 랜드마크 검출 자체는 됐지만(`covered`가 다 나온 것으로 간접 확인), 인덱스가 해부학적으로 맞는 자리를 가리키는지 육안 확인은 위 샷들로 한정됐다.

## 문서 검증표 대응

**API 편차(C-3)**: 스펙 6절은 `contourOutline(landmarks, faceShape, mmPerPx) -> { shading: [[x,y],...] }`로 적었지만, 실제 구현은 `contourOutline(landmarks, imgSize, faceShape) -> { shading: [폴리곤, ...] }`이다(인자 순서 다름, `mmPerPx`는 외부에서 받지 않고 내부에서 홍채 척도로 계산, `shading`은 점 하나짜리 배열이 아니라 좌우가 나뉠 수 있는 폴리곤 배열). **구현이 낫다** — 호출부가 mm 척도를 매번 계산해 넘길 필요가 없고, 좌우 분리 폴리곤을 유지해 `jawCorner`처럼 한 region이 두 다리로 나뉘는 경우를 표현할 수 있다. 스펙 문서는 고치지 않았다(이 POC가 논증한 근거 문서라 수정 대상이 아님).

## 이 POC가 확정하지 못한 것

- **얼굴형 판정**은 이 POC의 일이 아니다. 파트 1(F-02)이 판정한 label(`oval`/`round`/`square`/`oblong`/`heart`)을 입력으로 받을 뿐이다. 검증 탭·부위·상태 탭의 얼굴형 드롭다운은 이 자리를 수동으로 대신하는 것이다.
- `rules.js`의 `CONTOUR_RULES`(얼굴형별 쉐딩·하이라이트 규칙 5종 — 영역·밴드 폭·근거 문장)는 **전문가 검증 전 가정값**이다. `docs/README.md` "이후 확정할 것"의 "얼굴형별 쉐딩·하이라이트 규칙 5종"에 대한 초안일 뿐, 화장 전문가 검토를 거치지 않았다.
- 샘플 20장(`danghaeung_poc_3x4_20/`)은 **맨얼굴**이다. 크롭 계산·윤곽선 검증에는 충분하지만 "부위 완성본"으로는 보이지 않는다. 화장을 입힌 정면 렌더링(`fullRender`, 화면 2-b 산출물)이 준비되면 지금의 샘플/업로드 슬롯을 그 이미지로 교체해야 한다.

## 앱으로 옮길 때

- `core.js`는 그대로 이식한다 — DOM·캔버스·MediaPipe를 모르는 순수 함수라서 입력(랜드마크·이미지 크기·partId·faceShape)과 출력(숫자·폴리곤)만 맞으면 그대로 옮겨진다.
- `rules.js`의 `CONTOUR_RULES` 5종은 화장 전문가 검증 후 실제 값으로 교체한다(위 "확정하지 못한 것" 참조).
- 얼굴형 label은 앱에서는 드롭다운이 아니라 파트 1(F-02)의 판정 결과를 그대로 받는다.
- `fullRender`(화면 2-b의 전체 완성 예상 렌더링)가 생기면, 지금 `app.js`가 쓰는 샘플 20장 불러오기·업로드 슬롯을 그 이미지로 바꾼다. `cropSpec`은 이미지 크기와 랜드마크만 있으면 되므로 이미지 소스가 바뀌어도 계산 로직은 그대로다.
- `SIDE_MARGIN`·`PORTRAIT_ZOOM`은 위 실측으로 문서값이 이 샘플 조건에서는 성립함을 확인했지만, 실기기 검증에서 다른 촬영 조건을 마주치면 값을 다시 확인한다.
